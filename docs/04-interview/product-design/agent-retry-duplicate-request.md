# 请求超时后重试，怎样避免重复建单？

**难度**：⭐⭐⭐（进阶）  
**出现频率**：未统计／原创练习，非公司真实面试题

## 考察点

- 能否区分请求超时和业务执行失败。
- 能否设计幂等、结果查询、授权和取消之间的关系。
- 能否用业务对象和用户可见状态验收，而非只看错误码。

## 参考答案

“超时意味着调用方不知道结果，业务系统可能已经建单。我不会直接生成新请求再试，而是先用同一业务意图键查询执行结果。”

在内部IT助手中，E01确认27英寸显示器申请后，服务端已经创建REQ-DEMO-01，但网络返回丢失。助手如果生成新键重试，可能创建第二张申请。解决方案必须进入工具服务和业务接口契约，不能只在Prompt里写“不要重复”。

| 当前证据 | 下一步动作 | 用户看到什么 |
|---|---|---|
| 原key已对应一个申请 | 返回原ID，不再提交 | 已提交、待主管审批 |
| 权威系统明确未执行 | 权限和确认仍有效时有限重试同键 | 仍在提交，避免重复点击 |
| 查询也失败，结果不确定 | 保持核查中，转人工或等待可靠回查 | 不宣称失败或成功，不要求用户再建一个 |
| 权限已撤销或确认过期 | 阻断写操作；有未决结果则继续核查原请求 | 当前不能继续提交，解释下一步 |
| 用户改了地址等关键字段 | 旧确认失效，新草稿重新确认 | 展示变更，不静默修改已有申请 |

网络request_id可以每次不同；业务request_key代表同一意图，需要持久化到重启后仍可查询。相同key和相同内容应只产生一个业务对象；相同key却内容不同要拒绝，不能猜测是重试还是新申请。

还要检查取消：用户取消未提交草稿后，队列里的旧提交不能继续执行；已经提交的申请则需要业务撤回流程和回执。主管已经批准时，助手转IT人工处理，不能伪造撤回成功。

验收至少覆盖超时但已执行、并发双击、进程重启、同键改内容、结果查询失败、确认过期和取消竞态。最终应检查有效业务对象数量及状态，不仅是“接口返回200”或模型说“没有重复”。

## 追问延伸

- **下游接口不支持幂等怎么办？** 评估是否能增加原子业务去重与可查询回执；无法给出可靠保证时缩小自动化范围或转人工，不能用本地缓存承诺跨重启/并发安全。
- **是不是永远只能建一张申请？** 不是。同一业务意图只产生一份副作用；用户明确发起第二项真实需求，可以经新草稿和新确认形成新意图。
- **重试成功率怎么算？** 重试可以作为步骤指标，业务完成率仍以去重意图为分母，失败和转人工都保留在分母中。
