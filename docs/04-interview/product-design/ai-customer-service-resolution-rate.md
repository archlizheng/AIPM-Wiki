# AI 客服产品解决率停在 70% 上不去,怎么办?

**难度**:⭐⭐⭐ 进阶
**出现频率**:高(蚂蚁 AI 客服 PM 面经、牛客面经汇总帖)

## 考察点

- 能否用数据漏斗定位瓶颈,而非泛泛说「优化模型」
- 是否理解解决率的定义边界(什么算解决、什么必须转人工)
- 产品、运营、算法协作的迭代节奏是否清晰

## 参考答案

**一句话**:70% 往往不是模型上限,而是**意图覆盖、知识质量、转人工阈值、业务 API 接入**四个环节的叠加瓶颈——先拆漏斗,再按 ROI 逐个击破。

### 1. 澄清与界定

先定义「解决率」:**用户首次进线,AI 独立完成且未再次进线(或用户点「已解决」)的会话占比**。排除本就不该 AI 处理的场景(投诉仲裁、大额赔付),否则指标被稀释。

对齐目标:如果题目给出 70% 基线，可以把 75–85% 当作**本题的讨论区间示例**，不能称作行业成熟方案基准。真实目标要按自家解决率分母、意图分布、风险和人工兜底能力设定；从 70% 到 80% 是否更难，也必须用本产品的边际成本和长尾分布验证。

### 2. 方案设计:四层漏斗诊断

| 环节 | 典型症状 | 产品动作 |
|------|----------|----------|
| 意图未识别 | 「听不懂」类差评多 | 扩充意图树,合并近义问法 |
| 识别了但缺数据 | 反复追问订单号 | 登录态自动带订单,减少槽位追问 |
| 有数据但答错 | 政策/时效错误 | 修 RAG 切片,加业务 API 实时查 |
| 能答但不敢答 | 置信度阈值过高 | 分场景调阈值,低风险自动答 |

用 2 周数据拉出**转人工 Top 20 意图**,按「量 × 可自动化程度」排优先级,别平均用力。

### 3. 技术方案

- **知识类**(退换货规则):RAG + 引用,配合运营后台让客服可直接改 FAQ,分钟级生效
- **状态类**(物流/退款进度):优先接业务 API,模型只负责组织语言,不生成事实
- **多轮复杂**(比价、组合优惠):评估 Agent 或规则引擎,纯 Chat 难提解决率
- **生成质量**:对高频意图做 Prompt 模板 + 抽检;必要时对客服话术做 SFT

详见 [RAG vs 微调](../basics/rag-vs-finetuning.md):解决率瓶颈多在「检索/API 没接上」,不是模型不够聪明。

### 4. 风险与兜底

提解决率时警惕**错误解决率上升**:为冲 KPI 降低转人工阈值,会导致错答。设红线指标:**错误承诺率、差评率、二次进线率**。任一恶化则回滚阈值。

长尾问题维持「快速识别 + 优雅转人工」,转人工时**带全量上下文**,让人工解决率也算产品成功。

### 5. 衡量与迭代

建立周迭代闭环:漏斗报表 → bad case 标注(算法/运营/产品三方) → 改知识/API/Prompt → A/B 验证。对外汇报用**分意图解决率**,避免总体 70% 掩盖某个高频意图只有 40%。

蚂蚁面经常追问指标设计:除解决率外,加**人工节省工时、单次会话成本、用户 CSAT**,证明商业价值。

## 追问延伸

- **追问 1**:"运营说知识库已经最全了,为什么还不行?"
  → 查检索链路:切片是否切断上下文、同义词是否覆盖、Rerank 是否把正确文档排到前面。
- **追问 2**:"算法说模型已经 90% 准确率了?"
  → 离线准确率 ≠ 在线解决率;问评测集是否覆盖真实用户口语、是否包含多轮和 API 失败场景。
- **追问 3**:"老板要求一个月提到 85%?"
  → 给分阶段目标 + 资源清单(要多少 API 对接、多少标注人力),说明后 10% 的边际成本。
