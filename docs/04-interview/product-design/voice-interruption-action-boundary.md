# 用户打断语音时，已经发出的动作该怎么办？

**难度**：⭐⭐⭐（进阶）  
**出现频率**：未统计／原创练习，非公司真实面试题

## 考察点

- 能否区分停止播报、停止推理、停止排队任务和撤回业务动作。
- 能否在实时语音与后台执行之间维护清晰状态。
- 能否处理歧义、竞态和不可逆动作，并让用户理解当前结果。

## 参考答案

“用户打断时先停止播报，但不能据此断言已经取消后台任务。我要根据用户意图与动作发生阶段，判断停止、查询还是请求撤回。”

假设内部IT助手正在说“即将为你提交申请”，用户插话“等一下”。这可能是修改地点、补充信息，也可能是取消。若尚未提交，可以暂停并澄清；若提交已经发出，就应同时查询原意图键，不能悄悄再发一个请求。

| 动作阶段 | 处理方式 | 合适的用户反馈 |
|---|---|---|
| 只在播报制度 | 停止音频输出，继续听取问题 | 不再抢话；根据新问题回复 |
| 草稿待确认 | 暂停，不把沉默或含混应答当确认 | “草稿还没提交，你想修改还是取消？” |
| 提交已排队但尚未执行 | 对明确取消设置终态，执行前检查 | 有证据后说明已停止提交 |
| 提交已发出，结果未知 | 先查业务结果，暂不承诺取消 | “正在核实是否已经提交。” |
| 已取得待审批ID | 按业务规则展示撤回动作，重新确认 | “已提交，待审批；可继续申请撤回。” |
| 主管已批准或IT已交付 | 转人工，不自动回滚人类决定 | “当前需IT处理，我不能直接撤回。” |

对“等等，我改成北京地址”，应使旧确认失效，展示新草稿并重新确认。如果旧请求已生效，先说明已有申请，再按业务规则修改或撤回，不能让两个地址分别生成有效申请。

验收同时检查两条链：媒体链是否及时停止播报、是否识别插话；业务链是否记录取消时序、停止排队写操作、核查已发请求、保留正确回执。语音状态不能覆盖业务事实。供应商宣称支持“barge-in（插话打断）”，也不自动保证你的业务接口可撤回。

## 追问延伸

- **背景噪声被识别成“取消”怎么办？** 停止/降低播报和取消副作用使用不同阈值；写动作取消或新授权需要清晰意图，含混时暂停并澄清。具体阈值用真实音频和风险评测确定。
- **已经发送邮件怎么办？** 区分真实业务撤回能力与仅停止后续动作；没有撤回证据就不能说“已撤销”，应如实说明并提供补救选择。
- **是否必须固定毫秒级门槛？** 先定义首包、停播、后台回执等各自预算，再根据设备、网络、语言和任务风险测试，不能借用某厂商演示值当产品SLA。
