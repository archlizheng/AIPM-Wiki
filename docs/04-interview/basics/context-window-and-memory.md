# 大模型的上下文窗口和记忆机制是什么?

**难度**:⭐⭐ 入门必备
**出现频率**:高,抖音校招面经出现

## 考察点

- 能否解释上下文窗口的含义和限制
- 是否理解"记忆"在 LLM 中的实现方式(并非真正的记忆)
- 能否从产品角度设计长对话和跨会话的体验

## 参考答案

**上下文窗口(Context Window)**:模型单次能"看到"的最大 token 数量,包括输入(用户问题、系统 Prompt、检索内容)和输出(模型回答)。超出部分会被截断,模型无法感知。

**关键认知**:
- 上下文窗口 ≠ 记忆:模型不会"记住"上次对话,每次请求都是独立的
- 窗口越大,能处理的文档/对话越长,但成本越高、推理越慢
- 不同模型的窗口大小差异很大,选型时需考虑业务需求

**"记忆"的三种产品实现**:

| 方式 | 原理 | 适用场景 |
|------|------|----------|
| 对话历史拼接 | 把历史消息塞进上下文窗口 | 短对话(窗口够用时) |
| 摘要压缩 | 定期把历史对话压缩成摘要 | 中长对话,节省 token |
| 外部记忆库 | 关键信息存入数据库,需要时检索注入 | 跨会话记忆、用户画像 |

**产品设计要点**:
1. **长对话管理**:接近窗口上限时主动摘要,而非粗暴截断
2. **跨会话连续性**:用外部存储记录用户偏好、历史关键信息
3. **用户预期管理**:明确告知"我能记住什么、记不住什么"
4. **成本意识**:不是窗口越大越好,够用 + 合理的记忆策略更实际

**常见误区**:"模型有记忆"——实际上是没有的,所有"记忆感"都是工程手段模拟出来的。

## 追问延伸

- **追问 1**:"用户抱怨'你刚才不是说好了吗',你怎么解决?"
  → 检查对话历史是否被截断;优化摘要策略保留关键承诺;关键信息写入外部记忆库。
- **追问 2**:"上下文窗口和 RAG 是什么关系?"
  → RAG 是用检索突破窗口限制的手段:不把所有知识塞进窗口,而是按需检索相关片段注入。
- **追问 3**:"多轮对话中 token 成本怎么控制?"
  → 历史摘要而非全量保留;滑动窗口(只保留最近 N 轮);关键信息提取后丢弃原始对话。
