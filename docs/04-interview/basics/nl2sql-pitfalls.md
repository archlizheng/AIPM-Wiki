# 为什么 Text-to-SQL 在 Spider 上很高分,上线企业库却翻车?

**难度**:⭐⭐⭐ 进阶
**出现频率**:中,数据产品/BI 类 AI PM 岗位、看数 Agent 相关面试常见

## 考察点

- 能否区分学术榜单分数和企业生产可用性之间的差距,而不是把 Leaderboard 当唯一指标
- 是否理解 Text-to-SQL 翻车的具体环节:语义层缺失、权限治理、评测指标本身的偏差
- 能否给出面向产品落地的判断框架,而不是只会说"模型不够强"

## 参考答案

**一句话**:Spider 这类学术榜单测的是"干净、单库、公开 schema"下的语法生成能力,企业库翻车的原因几乎都出在"榜单默认不存在"的地方——不统一的指标口径、缺失的权限治理、千级列多方言的真实 schema 复杂度。

### 数字说话:Spider 1.0 vs Spider 2.0

Spider 2.0 论文(2024)专门用同一批模型重新测了一遍,结果是断崖式下跌:

| 基准 | 场景特征 | GPT-4o | o1-preview |
|------|----------|--------|------------|
| Spider 1.0(2018) | 单库、公开 schema,贴近学术假设 | 约 86.6% | — |
| Spider 2.0(2024) | 企业级工作流、千级列、多方言(BigQuery/Snowflake),常需读元数据/文档/项目代码才能写对 query | 约 10.1% | 约 17.1% |

这个断崖不是模型变笨了,是任务定义变了——Spider 2.0 更贴近企业真实场景,证明"学术高分"和"企业可用"衡量的根本不是同一种能力。

### 翻车的三个具体环节

1. **语义层(Semantic Layer)缺失**:企业库字段名常是缩写或历史遗留命名(如 `amt_02`、`cust_flg`),模型不知道它对应业务口径里的哪个指标。缺少一层统一的指标/维度定义,模型只能"猜列名",猜错了 SQL 语法正确但答案是错的。
2. **权限治理跟不上**:自然语言问数天然会跨表、跨库,如果权限过滤没有在 SQL 生成前后强制执行,很容易让用户查到本不该看的数据——这一层学术榜单几乎不测。
3. **评测本身有偏差**:传统 Execution Accuracy(比对执行结果)对句法变体敏感、会忽略同一问题的多种正确写法,也可能被本身有误的 gold SQL 带偏,导致"分数"和"是否真的答对用户意图"脱节。

### 产品视角的应对

- **先补语义层再上模型**:把指标口径、维度定义、常用字段别名整理成一份"业务词典",能解决相当一部分"猜列名"错误,性价比通常高于直接换更强模型。
- **权限校验前置或做结果过滤**,不能依赖模型"自觉不查",这一点和 RAG 场景的多租户权限治理是同一类问题。
- **拆开评测环节**:把 Text-to-SQL 拆成 Schema Selection(选对表)/ Candidate Generation(生成 SQL)/ Query Revision(执行校验与改写)分别测,能定位到底是"没找对表"还是"SQL 语法错"还是"没有自我纠错能力",比只看一个总分更能指导优化方向。
- **排行榜数字只作方向参考**:榜单靠前的系统多是厂商 Multi-Agent 方案,设置上也可能存在 oracle table 等特殊简化,不能直接当作"企业里也能打这个分"的证据。

## 追问延伸

- **追问 1**:"你会怎么设计上线前的验收标准?"
  → 不能只看一个 Execution Accuracy 总分,建议按 Schema Selection / 生成 / 执行校验拆开测,并且用业务方真实历史问题(而不是学术数据集)做验收集。
- **追问 2**:"语义层应该谁来维护?"
  → 通常由数据/分析团队和产品共同拥有,PM 要确保这层被当成正式产品资产维护(有版本、有 Owner),而不是一次性整理完就不更新。
- **追问 3**:"能不能靠小模型专门做 Text-to-SQL 来降低成本?"
  → 有厂商用专门微调的小模型打榜,思路是"专用小模型 + 强规则校验"通常比通用大模型裸问更稳定,但前提是已有干净的语义层和评测集支撑,否则小模型一样会猜错列名。
