# 如何构建大模型效果评测体系?

**难度**:⭐⭐⭐ 进阶
**出现频率**:极高,小米(7 道评测题)、百度、理想、蚂蚁面经均重点考察

## 考察点

- 能否区分离线评测和在线评测,并说明各自价值
- 是否理解"评测不是算法的事,产品要定义什么是好"
- 能否设计分层指标体系,而非只说"看准确率"

## 参考答案

**核心观点**:评测体系的核心问题是"谁来定义好"——产品负责定义标准,算法负责量化和优化。

**三层指标体系**:

| 层级 | 指标类型 | 示例 | 谁主导 |
|------|----------|------|--------|
| 效果层 | 任务完成质量 | 回答准确率、解决率、格式合规率 | 产品定义 + 算法量化 |
| 体验层 | 用户感知 | 响应延迟、回答长度适中、语气得体 | 产品主导 |
| 商业层 | 业务价值 | 人工转接率下降、用户满意度、付费转化 | 产品 + 业务 |

**离线 vs 在线**:

- **离线评测**:用标注好的测试集跑分,迭代快、可复现,适合模型选型和能力对比
- **在线评测**:A/B 测试、用户反馈(点赞/点踩)、人工抽检,反映真实场景效果

**构建步骤**:
1. 明确核心场景和用户目标(解决什么问题算"好")
2. 构建覆盖典型 case 的评测集(含边界 case 和 bad case)
3. 定义可量化的评测维度(不只看一个准确率)
4. 建立迭代闭环:评测 → 发现问题 → 优化 → 再评测

**PM 的关键贡献**:不是写评测代码,而是定义"什么算答对了"——这往往比算法更难,因为业务场景的"好"没有唯一标准。

## 追问延伸

- **追问 1**:"评测集怎么构建?需要多少条?"
  → 覆盖核心场景 + 边界 case + 历史 bad case;数量取决于场景复杂度,质量远比数量重要。
- **追问 2**:"模型准确率从 90% 提升到 95%,业务价值怎么量化?"
  → 转化为业务指标:人工介入率下降多少、用户投诉减少多少、处理时效提升多少。
- **追问 3**:"离线分数高了但线上效果不好,你怎么排查?"
  → 评测集与真实分布不一致(分布偏移)、评测维度遗漏(只看了准确率没看体验)、线上有新场景未覆盖。展开见[离线 Evals 全绿、线上「时灵时不灵」](offline-eval-online-gap.md)。
