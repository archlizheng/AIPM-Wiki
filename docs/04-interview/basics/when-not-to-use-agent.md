# 所有人都在卷 Agent，什么场景不该用？怎么说服老板？

**难度**:⭐⭐⭐ 进阶
**出现频率**:中高，Agent 平台 / ToB 办公 Agent / 二面架构选型常见

> 选题启发自磊叔《关于 AI 产品经理的 100 个问题》Q16 / Q17 / Q41 / Q43 / Q99；正文为本库原创，未摘录该 PDF 答案原文。框架对齐正课 [何时不该上多 Agent](../../02-pm-skills/ai-product-operations/when-not-to-use-multi-agent.md)。

## 考察点

- 能否把「上 Agent」和「上多 Agent」分层说清，而不是一刀切否定或跟风
- 能否用延迟、成本、工具面、可观测性给出**可证伪**的劝退标准，而不是口号
- 能否用一页纸对照方案说服老板：替代路径 + 复盘触发条件，而不是单纯说「技术不行」

## 参考答案

**一句话**：不是「别做 Agent」，而是**默认走最简路径**——单次 LLM / 规则 / Workflow 够用就不上 Agent；单 Agent 够用就不上多 Agent。多 Agent 是用更高的协调税换并行与隔离，没证明税值得付就别立项。

### 一、先分清三层，别和老板吵同一件事

| 层级 | 典型形态 | 何时该停 |
|------|----------|----------|
| 单次 LLM（可加 RAG） | 问答、摘要、抽取 | 一步能验收，就别做成循环 Agent |
| 单 Agent / Workflow | 多步工具循环，或固定编排 + 局部模型判断 | 路径大体可写死 → 优先 Workflow；开放规划才上单 Agent |
| 多 Agent | 多上下文 + 编排/交接 | 没有「上下文污染 / 真并行 / 专精工具面」硬约束 → 默认不批 |

决策顺序可口述：

```text
多步骤 + 要外部动作 + 结果可验证？
  ├─ 否 → 单次 LLM / 规则 / 表单
  ├─ 是，路径可写死 → Workflow
  ├─ 是，路径开放 → 受约束的单 Agent
  └─ 单 Agent 撞硬约束 → 再谈多 Agent
```

公开工程共识（Anthropic 等，细节与数字见正课，访问日以正课为准）：先找最简单方案；Agent 用延迟与成本换效果；多 Agent 相对单 Agent 常见约 **3–10×** token 量级——**用自有灰度账单填表，不要背外部倍数当财务红线**。

### 二、什么场景「不该用 / 先别上」

**不该上 Agent（连单 Agent 都重）**：

- 步骤固定、规则可穷举（改状态、填表、固定审批链）→ 规则引擎 / 传统工作流更稳
- 零容错且错了难回滚（支付金额、合规硬闸）→ 模型只可辅助，执行走确定性系统
- 用户在对话里等结果，任务价值撑不起多跳延迟与费用
- 还没有任务级评测与成本看板，就先上「更炫的编排」

**不该上多 Agent（单 Agent / Workflow 优先）**：

- 子任务强依赖、几乎无法并行，却拆成「规划 / 执行 / 审核」流水线——交接丢上下文、协调税高
- 工具面过宽导致空转，瓶颈在工具描述与选型，不在 Agent 个数
- 简单意图被错误路由进重路径（见 [路由题](agent-routing-and-large-files.md)）——先收默认路径与门槛

**可能值得上多 Agent（仍要评测证明）**：信息面大需真并行、单上下文易被中间结果污染、工具面过宽拆专精后选型准确率上升，且单位任务价值盖得住协调税。

### 三、怎么说服老板（给可签字的取舍，不给技术否定）

一页纸结构（可直接贴进评审）：

1. **用户任务与成功证据**：完成标准是业务证据，不是模型自称完成
2. **候选方案对照表**：规则 / 单次 LLM / Workflow / 单 Agent / 多 Agent → 效果假设、P50/P95、单位费用、可控性、工期
3. **自有基线**：哪怕小流量灰度；缺数据就写「两周内补齐评测，当前不扩大多 Agent 投入」
4. **硬约束检查**：上下文污染 / 真并行 / 专精工具面——三项皆无 → 默认不批多 Agent
5. **劝退结论 + 替代路径**：例如「先 Workflow + 关键步人工确认；单 Agent 评测不够再开子 Agent」
6. **复盘触发条件**：何种成功率 / 成本 / 接管率组合出现时，才允许重新立项——避免被竞品叙事再次绑架

口头三句：

- 「多 Agent 是用更高协调税换并行与隔离；我们还没证明税值得付。」
- 「现在瓶颈在工具面 / 评测 / 权限，不在 Agent 个数。」
- 「先把单路径做到可观测、可熔断，再谈编排复杂度。」

上线后延迟暴增时，别一上来二选一砍功能：先归因「误入重路径 / 工具空转 / 步数无上限 / 假并行 / 外部 API 慢」，经验顺序是**收默认路径与预算 → 瘦工具面 → 合并 Agent → 最后才砍对用户可见的功能**。完整归因表见正课。

## 追问延伸

- **追问 1**:"竞品都上了多 Agent，我们不上是不是落后？"
  → 问他们任务是否真并行、单位任务价值是否覆盖协调税、有没有错路由与可观测性。没有自有对照数据，跟风是叙事不是工程。
- **追问 2**:"多 Agent 一定比单 Agent 强吗？"
  → 不一定。强在隔离与并行；弱在交接摘要丢信息、成本与调试复杂度。边界清晰、需要隔离上下文时才划算。路由选错与超大输入接法见 [Agent 路由与超大文件](agent-routing-and-large-files.md)。
- **追问 3**:"老板只听 ROI，你怎么算？"
  → 用单位任务：`(成功率提升 × 业务价值) − (增量 token/延迟/人工接管成本)`。缺分子就先定评测集与灰度账单，而不是先定架构。
