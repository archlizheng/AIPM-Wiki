# 什么是 token?它如何影响产品的成本和体验?

**难度**:⭐⭐ 入门必备
**出现频率**:高,Brave 交叉面经、仓库规划题

## 考察点

- 能否用通俗语言解释 token 是什么
- 是否理解 token 同时影响成本(按量计费)和体验(上下文长度限制)
- 能否在产品设计中找到优化 token 使用的方法

## 参考答案

**一句话定义**:Token 是大模型处理文本的最小单位,可以理解为"模型眼中的字/词片段"——英文约 4 字符一个 token,中文约 1.5-2 字一个 token。

**Token 的双重影响**:

| 影响维度 | 机制 | 产品含义 |
|----------|------|----------|
| 成本 | API 按 token 数计费(输入 + 输出) | 上下文越长、回答越多,单次成本越高 |
| 体验 | 模型有上下文窗口上限 | 超出上限的内容会被截断,长对话会"失忆" |
| 延迟 | 生成 token 数越多,耗时越长 | 冗长回答影响响应速度 |

**成本优化思路**:
1. **精简 Prompt**:去掉冗余指令,用结构化格式替代自然语言啰嗦
2. **控制输出长度**:限制 max_tokens,要求简洁回答
3. **RAG 精准检索**:只塞相关片段进上下文,而非整篇文档
4. **缓存复用**:相同问题复用已有回答,避免重复调用
5. **模型分级**:简单问题用小模型,复杂问题用大模型

**体验优化思路**:
1. **上下文管理**:长对话做摘要压缩,保留关键信息
2. **流式输出**:边生成边展示,降低首 token 等待感
3. **合理预期**:告知用户上下文限制,引导拆分复杂问题

**PM 要会算的账**:日活 × 人均对话轮次 × 每轮 token 数 × 单价 = 日成本。写 PRD 时应估算 token 消耗,避免功能上线后成本失控。

## 追问延伸

- **追问 1**:"接入大模型后成本涨了 10 倍,你怎么降本?"
  → 分层路由(简单问题用小模型)、缓存高频问答、优化 Prompt 减少无效 token、设置用量上限和熔断机制。
- **追问 2**:"上下文窗口越大越好吗?"
  → 不一定:窗口大意味着单次成本高、推理慢;"够用就好",配合 RAG 和摘要策略比盲目追求大窗口更实际。
- **追问 3**:"怎么估算一个功能的月均模型成本?"
  → 预估 DAU × 使用率 × 人均调用次数 × 平均 token 数 × 单价,留出 2-3 倍 buffer 应对波动。
