# 模型选型该听算法还是 PM？你怎么协作？

**难度**:⭐⭐ 常规
**出现频率**:中高，行为面 / 协作面常见；有算法团队的公司尤爱问

## 考察点

- 是否把选型理解成**取舍会**（效果 / 成本 / 延迟 / 合规），而不是「谁官大谁说了算」
- 能否说清 **PM 与算法的决策分层**：谁定约束、谁出候选、谁拍板、谁保留技术否决
- 是否能描述一场可落地的协作流程，并举出冲突时怎么解，而不是空喊「一起讨论」

## 参考答案

### 一句话核心

**不听职位，听决策层。** PM 对「要什么效果、能接受什么代价」负责；算法对「能不能做到、边界在哪」负责。选型听谁，取决于你在讨论哪一层——约束与取舍听 PM，方案与可行性听算法。

### 展开：别用「听谁」回答，用分层表回答

把「该听谁」拆成四层，比争话语权更像做过事的人：

| 决策层 | 主要内容 | 谁主导 | 谁协作 |
|--------|----------|--------|--------|
| 约束与成功标准 | 效果底线、延迟上限、成本上限、合规一票否决 | **PM** | 算法补可行性；法务/安全确认红线 |
| 候选方案与技术边界 | 哪些模型/层级能在约束内跑通；路由、缓存、自建 | **算法 / 工程** | PM 提供流量与场景假设 |
| 产品取舍拍板 | 多付一点换体验，还是降本换可接受效果 | **PM（对业务结果负责）** | 算法陈述风险与不确定性 |
| 上线后复盘 | 业务指标 + 技术指标是否同向；是否触发换模 | **共同 owner** | 监控与复评节奏事先写进纪要 |

面试官若追问「那万一两边意见相反呢」，把否决权说清楚：

- 算法的**技术否决**只针对「不可行 / 不可控风险」（达不到底线、合规不可用、延迟物理上达不到），不是对「我更喜欢旗舰模型」行使否决。
- PM 的拍板必须落在**已声明的约束**内；约束没写清就去逼算法「上最强」，是 PM 失职，不是算法不配合。

选型四要素与评审顺序见正课 [模型选型决策框架](../../02-pm-skills/cost-and-tech/model-selection-framework.md)；组织侧分工见 [AI 产品团队怎么建](../../00-roadmap/ai-pm-team-org-and-roles.md)。

### 协作怎么开：一场选型会的五步议程

回答「你怎么协作」时，直接报议程，比讲理念更有说服力：

1. **PM 先摊约束（一页纸）**：任务定义、「好」的标准、不可突破的延迟 / 成本 / 合规。
2. **算法给候选池（通常 3–5 个组合）**：离线评测摘要、延迟与单价粗估、已知失效模式——不在会上现场发明「最强模型」。
3. **一起算规模化账单**：比的是月成本与单位任务成本，不是单次调用贵不贵（方法见 [成本测算入门](../../02-pm-skills/cost-and-tech/llm-cost-101.md)）。
4. **PM 在约束内拍板**；算法仅对不可行项行使技术否决。
5. **写下监控与复评节奏**（例如按季度复评模型与价格），避免「选定即永久」。

### 场景举例（面试可口述）

**场景**：客服助手要不要默认上旗舰模型。

- 算法倾向旗舰：离线难例准确率更高。
- PM 摊约束：P95 延迟 ≤ 某阈值、月推理预算有上限、主路径是高频短问答。
- 协作结果：主流量走主力层 / 轻量层 + 路由，难例与高风险工单升旗舰；评测集里单独挂「路由误判」指标。两边都「赢」——算法保住了难例质量，PM 保住了成本与延迟。

**反面对照（扣分答法）**：「听算法，因为他们更懂模型」或「听 PM，因为要对业务负责」——都把分层压成一言堂。

### 避坑指南

| 雷区 | 为什么扣分 | 改法 |
|------|------------|------|
| 「听算法 / 听领导」 | 无框架 | 按决策层拆开 |
| PM 替算法定超参、推理优化 | 角色越位 | 声明「怎么实现」归算法 |
| 算法单独决定「上最强」 | 忽略成本与体验约束 | 先写清四要素优先级 |
| 只谈和谐协作、无冲突解法 | 显得没开过选型会 | 补技术否决边界 + 一页纸约束 |
| 选型会上比 Benchmark 榜单 | 与业务不对齐 | 强调自建评测集 + 业务指标 |

## 追问延伸

- **追问 1**：「算法说必须自建 / 必须私有化，你怎么办？」
  → 先拆「合规硬约束 vs 商务偏好」；真约束走 TCO 与效果底线过会，假约束回到企业 API / 专区等替代路径，不拿工程承诺换折扣。详见选型框架「私有化」一节。
- **追问 2**：「你和算法吵过最狠的一次选型是什么？结果如何？」
  → 用 STAR：争议点落在哪一层（约束未声明 / 候选未评测 / 取舍标准不一致）→ 你补了什么一页纸或评测集 → 最终怎么拍板与复盘。没有经历可用模拟场景，但要讲清分层。
- **追问 3**：「PM 不懂模型细节，凭什么拍板？」
  → 拍板的不是「哪个架构最优」，而是「在可行候选里选哪条业务取舍」；不懂细节更要依赖算法的候选池与风险说明，而不是放弃产品责任。
