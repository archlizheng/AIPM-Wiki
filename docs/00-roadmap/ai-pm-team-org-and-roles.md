# AI 产品团队怎么建：角色、分工与选型话语权

> 本文回答三件事：AI 产品团队常见怎么搭？从 0 到 1 最少要哪些角色？模型选型时 PM 和算法各自说了算什么？
> 文中组织建议均为**常见模式、非唯一正解**——适合作为讨论起点，需按公司阶段、业务形态与合规约束裁剪，不宜照搬某一家大厂的编制表。

组织与岗位形态和「你要做哪一类 AI PM」强相关，建议先读 [AI PM 岗位类型盘点](ai-pm-job-types.md) 与 [AI 产品经理能力模型](ai-pm-capability-model.md)；选型四要素与评审流程见 [模型选型决策框架](../02-pm-skills/cost-and-tech/model-selection-framework.md)。

选题启发自磊叔《关于 AI 产品经理的 100 个问题》Q83 / Q84 / Q9。

## 一、为什么组织问题会卡产品

AI 产品比传统功能多出几条跨职能链路：效果评估、数据与标注、模型/供应商选型、内容安全与合规。这些事如果没人认领、或认领边界不清，常见后果不是「缺人」，而是：

- 评测集没人定标准，上线后只能用业务指标事后吵架
- 选型会上各说各话（体验 / 成本 / 技术可行性），会开完仍无决策
- 飞轮只停在算法侧指标，产品侧埋点与反馈回路缺位

搭团队的目标，不是先画一张完美组织图，而是让「谁定义成功、谁提供候选方案、谁拍板取舍、谁对风险升级」在项目早期就写清楚。

## 二、按功能分还是按场景/模型分？

这是早期团队最常纠结的组织题。下面两种都是**常见模式、非唯一正解**。

| 模式 | 怎么切 | 常见优点 | 常见代价 |
|------|--------|----------|----------|
| 职能制（按功能分） | 产品 / 设计 / 工程 / 算法 / 数据 / 安全各自成组 | 专业深度集中，基础设施与公共能力不易重复建设 | 跨组协调成本高；AI 迭代快时，联调与决策容易成为瓶颈 |
| 场景/模型小组制 | 按核心场景或核心能力线组「端到端小分队」（PM + 算法 + 工程 + 设计等） | 决策半径短，从方案到上线反馈更快 | 易重复造轮子；公共平台、评测基建、安全基线可能各自为政 |

### 怎么选（启发式，非硬规则）

1. **探索期、场景少**：小组制往往更顺——用小半径闭环验证「场景是否成立」，而不是先把职能墙砌齐。
2. **规模化、场景多、要共用底座**：职能制或「平台职能 + 场景小组」混合更常见——公共能力（推理网关、评测平台、内容审核、成本监控）收口，场景组只负责业务闭环。
3. **混合（也很常见）**：核心增长场景用小组制抢速度；模型托管、评测、安全、数据管道用职能制保深度与复用。

公开招聘也能侧面看到「按产品线/能力线切分」的痕迹，而不是单一「算法大组 vs 产品大组」二分。例如 Anthropic 招聘页上的 PM 岗位会按 Compute Platform、Safeguards、Model Behaviors、消费端 Web 等方向拆开（截至 2026-08 访问）；Google DeepMind 的 Gemini 相关岗位也会区分 API/模型发布、Post Training、App 等。这不等于你的公司也要照抄编制，只说明：**组织往往跟着产品对象切，而不是先按「有没有 AI」统一挂一个大部门。**

## 三、从 0 到 1：最小角色配置

「最少要几个人」没有行业标准编制。下表是创业团队与大厂内部创新小队里较常见的**最小闭环**——同样是**常见模式、非唯一正解**。人可以兼职，角色不宜缺席。

| 角色 | 0→1 阶段主要负责什么 | 缺席时常见后果 |
|------|----------------------|----------------|
| AI 产品经理 | 场景与成功标准、效果底线、优先级、跨角色对齐、评估闭环的产品侧定义 | 团队会「做出东西」，但说不清什么叫做成 |
| 算法 / ML 工程师 | 模型与方案可行性、Prompt/RAG/微调等路径、离线评测与效果调优 | 只能堆交互壳，核心能力不可控 |
| 全栈 / 应用工程师 | 产品可交互形态、服务与 API、上线与观测埋点落地 | 方案停在 notebook / demo |
| 设计师（可兼职） | 不确定性交互、失败态与预期管理、信任相关信息架构 | 功能可用但不可信、不可用、不可恢复 |

### 几点边界说明

- **「四个角色」是闭环，不是编制 KPI**。同一人可兼设计+前端，或算法兼部分工程；关键是责任有人认，而不是头衔凑齐。
- **数据标注 / 评测运营**：验证期可用外包或业务兼职；一旦进入持续迭代，通常需要固定 owner（仍可不单独成组）。
- **安全 / 合规 / 法务**：早期可借公司共享职能；面向 C 端内容生成、未成年人、金融医疗等场景时，应尽早拉进评审，而不是上线前突击。
- **人越多不一定越快**：0→1 阶段多余协调层，往往会稀释决策、拉长「改一版 Prompt / 评测集」的反馈周期。

产品长大后，角色通常会再拆：算法侧出现数据工程、推理优化；工程侧出现前端/后端/SRE；产品侧出现增长、商业化、平台 PM 等——对应关系可对照 [岗位类型盘点](ai-pm-job-types.md) 里的应用 / 平台 / 行业分型，而不是用同一套最小班底硬套所有阶段。

## 四、选型话语权：听算法还是听 PM？

模型选型表面上是技术会，底层通常是**体验、成本、延迟、合规**的取舍会。把它理解成「谁官大谁说了算」，几乎总会陷入僵局。

更稳的做法是**决策分层**（与 [选型框架](../02-pm-skills/cost-and-tech/model-selection-framework.md) 一致）：

| 决策层 | 主要内容 | 谁主导 | 谁协作 |
|--------|----------|--------|--------|
| 约束与成功标准 | 效果底线、延迟上限、成本上限、合规一票否决项 | **PM 主导** | 算法补充可行性；法务/安全确认红线 |
| 候选方案与技术边界 | 哪些模型/层级组合能在约束内跑通；路由、缓存、自建可行性 | **算法 / 工程主导** | PM 提供流量与场景假设 |
| 产品取舍拍板 | 在可行候选里选哪条：多付一点换体验，还是降本换可接受效果 | **PM 主导（对业务结果负责）** | 算法陈述风险与不确定性 |
| 上线后复盘 | 业务指标 + 技术指标是否同向；是否触发换模/降级 | 共同 owner | 监控阈值事先写进评审纪要 |

### 一场典型选型会怎么开（可直接当议程）

1. **PM 先摊约束**（写在一页纸上）：任务定义、「好」的标准、不可突破的延迟/成本/合规。
2. **算法给候选池**（通常 3–5 个组合），附：离线评测摘要、延迟与单价粗估、已知失效模式——不在会上现场「发明」一个最强模型。
3. **一起算规模化账单**（方法见成本测算正课），避免只比「单次调用贵不贵」。
4. **PM 在约束内拍板**；算法保留「技术否决权」仅针对**不可行或不可控风险**（例如根本达不到底线、或合规不可用），而不是对体验偏好行使否决。
5. **写下监控与复评节奏**（例如按季度复评模型和价格），避免「选定即永久」。

一句话原则（与选型框架第九节同向）：**PM 对「要什么效果、能接受什么代价」负责；算法对「能不能做到、边界在哪」负责。** PM 不该替算法定超参与推理优化细节；算法也不该在业务约束未声明时单独决定「上最强模型」。

若你关心能力侧「怎样才有资格参与这类讨论」，对照能力模型里的「技术认知」与「商业判断」及格线 / 优秀线即可。
