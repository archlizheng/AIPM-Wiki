# AI 项目从 PoC 到生产：组织采用的阶段门

## 先说结论

PoC 证明“在给定样例上能工作”，生产化要证明“在真实流程、真实权限和真实责任下，能持续交付可复核结果”。组织采用再多一步：目标岗位愿意把任务放进日常工作，管理者能看到结果和风险，支持团队能处理失败。三者不能用同一张演示截图或一次满意度调查替代。

本文聚焦**组织阶段门、采用和培训**，不重复工具 Schema、状态机、轨迹字段和 Agent 运行时细节；这些内容见[Agent 产品生产化](agent-product-design.md)、[Agent 评测与可观测性](agent-evaluation-and-observability.md)和[AI 安全与 Agent 权限](guardrails-and-agent-security.md)。

## 先修与职责边界

先修阅读是[企业 AI 需求发现](../prd-and-design/ai-demand-discovery.md)（立项前证据）、[Agent 评测与可观测性](agent-evaluation-and-observability.md)（质量与轨迹）和内部助手教学契约（角色、租户、状态、确认与幂等）。本篇由 PM/业务 owner 主导阶段门、采用目标和培训安排；工程/IT owner 负责可用性、接入、值班与回滚；安全/法务负责阻断项与政策；业务 champion 负责岗位反馈和 badcase；主管/审批人仍对业务审批负责，不能把责任转给助手。

| 角色 | 在阶段门中的决定或交付 | 不承担的责任 |
|---|---|---|
| PM/业务 owner | 定义结果、分群、阶段门和扩围条件 | 不替业务审批或替用户确认 |
| 工程/IT owner | 版本、监控、接入、故障和回滚演练 | 不把演示通过当生产证据 |
| 安全/法务 | 数据、租户、权限、合规阻断 | 不替业务定义成功结果 |
| Champion/培训负责人 | 任务教学、反馈、badcase 和支持 | 不绕过权限或人工闸门 |
| 主管/审批人 | 对业务申请和审批结果负责 | 不由 Agent 代批 |

## 一、四个阶段，四种问题

| 阶段 | 要证明什么 | 典型产物 | 不能据此宣称 |
|---|---|---|---|
| 立项 | 问题真实且值得投入 | 需求证据卡、基线、优先级 | AI 已有效果 |
| PoC | 样例和小范围数据可行 | 种子集、演算结果、风险清单 | 适合全员使用 |
| 受控试点 | 真实流程中结果稳定、可接管 | 通过门禁、灰度报告、培训记录 | 已证明现金 ROI |
| 生产与扩围 | 采用、支持、成本和风险可持续 | 看板、值班、回滚、复盘 | 所有岗位均适用 |

阶段门不是固定百分比。门槛应根据错误代价、任务频次、可逆性、人工兜底能力和数据分布设定，并记录决定人和日期。

## 二、G0：立项门

立项材料来自[企业 AI 需求发现](../prd-and-design/ai-demand-discovery.md)，至少回答：谁在什么触发下完成什么任务；当前耗时、等待、返工和人工介入如何定义；AI 增量是什么；完成证据是什么；不做什么；谁对最终结果负责。

一票否决项包括：数据和租户范围不清、结果没有业务系统回执、不可逆动作无确认、无法记录关键轨迹、没有失败和人工出口。缺证据时应补证或暂缓，不能用“模型很强”填空。

## 三、G1：PoC 门

PoC 只回答可行性，不替生产背书。建议使用脱敏真实样本加边界样本，分开记录：

- 任务成功：是否得到定义好的结果对象；
- 质量：正确、引用、格式、完整性和高风险子集；
- 链路：必要步骤、工具返回、权限和停止条件；
- 体验：等待、追问、修改、转人工和取消；
- 成本：模型、工具、基础设施和人工协助；
- 风险：越权、泄露、重复写入、错误状态和审计缺口。

PoC 报告应注明样本来源、时间范围、分母、版本、评分规则和未覆盖分布。若结果来自教学演算，必须写“虚构、未运行真实系统”；不能把演算通过率称作上线效果。

## 四、G2：受控试点门

试点要把 AI 放入真实入口，但限制人群、权限、任务类型和预算。最小闭环是：

1. 先选能观察结果的队列，保留上线前基线；
2. 让用户看到草稿、引用、状态和下一步，关键写入需确认；
3. 设定人工接管、暂停、回滚和事故响应责任人；
4. 以任务 ID 关联模型、工具、版本、人工节点和结果证据；
5. 按岗位、任务、租户、版本和数据新鲜度拆分指标；
6. 试点结束时复盘未使用者、失败者和重度用户，而不是只看平均值。

“使用率上升”不等于采用。建议同时看受邀→有需求→发起→有效完成→再次有同类需求→再次使用的漏斗。培训签到只能证明培训发生，不能证明行为改变。

| 看板层 | 最小指标与分母 | 触发动作 | owner |
|---|---|---|---|
| 触达 | 受邀员工、完成培训人数/受邀人数 | 补场次、改入口或补岗位示例 | 培训负责人 |
| 采用 | 发起人数/有需求人数、再次使用人数/有效完成人数 | 访谈未使用者，修任务入口和支持 | PM/champion |
| 任务 | 有效完成意图/去重任务意图、人工协助率 | 查失败任务、补知识或人工出口 | 业务 owner/工程 |
| 结果 | 业务系统回执数/提交数、返工或否决率 | 暂停扩围，核对状态和责任链 | 业务 owner |
| 风险 | 越权、重复建单、错误状态和事故数 | 关闭写操作、回滚版本并复盘 | 安全/工程 |

## 五、G3：生产与扩围门

生产门至少包含五类证据：

| 证据 | 通过问题 |
|---|---|
| 业务 | 结果对象和责任边界是否被业务方接受？ |
| 质量 | 关键任务和高风险子集是否达到自定门槛？ |
| 稳定 | 延迟、错误、重试、限额和依赖故障如何处理？ |
| 经济 | 每个有效完成任务的全成本能否被预算或定价承受？ |
| 组织 | 培训、支持、值班、内容更新和回滚是否有人负责？ |

扩围应按“复制一个已验证工作流”推进，不能把一个团队的成功数字直接外推到全公司。新租户、新岗位、新数据域和新工具均应触发权限与回归检查。若供应商升级模型、Prompt、工具或数据索引，应执行差异评测并保留可回滚版本。

## 六、采用与培训怎么设计

培训不应从 Prompt 技巧开始，而应围绕岗位任务做三层：

1. **知道何时用**：识别支持场景、禁止场景和结果定义；
2. **会检查**：核对来源、字段、状态、权限、风险和不确定性；
3. **能接管**：取消、转人工、纠正、重试和报告事故。

每个团队指定一名业务 champion，负责收集 badcase、解释流程变化和推动反馈；产品/工程负责版本和指标；安全/法务负责政策与高风险闸门；IT 或运营负责账号、培训和支持。Champion 不是替代审批人，也不是替用户承担业务责任。

## 七、教学演算：内部 IT 服务助手

以下数据全部来自统一教学契约，是虚构演算，未运行真实系统。200 名受邀员工中 120 人有符合定义的需求，100 人发起使用；1,000 个去重任务意图中 840 个按任务契约完成，总完成率 84%，其中 80 个经人工协助后完成。1,000 元总成本包含模型与工具 300 元、基础设施 100 元、人工协助 420 元、运营维护 180 元，因此每个有效完成意图约 1.19 元。

同等范围人工处理假设为每个意图 6 分钟、60 元/小时，账面工时成本约 6,000 元；与 1,000 元的差额是教学场景的内部工时账面差，不是现金节省，也不是已验证 ROI。它没有扣除一次性建设、返工全成本、治理、机会成本和业务系统改造费用。正式上线前必须用真实基线重算。

该助手仅覆盖制度问答、设备申请（草稿→员工预览确认→受控提交）与状态查询。设备申请需经历 `draft → awaiting_confirmation → submitting → pending_approval`；提交成功只代表得到业务系统申请 ID，不代表审批通过或设备交付。助手不采购付款、不提权、不代主管审批；同一 `request_key` 超时先查业务对象，禁止重复建单。

## 八、阶段门表格

```text
【阶段】G0 立项 / G1 PoC / G2 受控试点 / G3 生产扩围
【目标任务与完成证据】
【样本、时间范围、分母】
【上线前基线】
【质量、链路、体验、成本、安全指标】
【一票否决项】
【用户范围、租户、权限和预算】
【培训与支持】负责人、champion、值班和内容更新
【人工接管、暂停、回滚】触发条件和操作人
【退出条件】何时补证、缩小范围或停止
【决定】通过 / 有条件通过 / 退回；决定人、日期、版本
```
