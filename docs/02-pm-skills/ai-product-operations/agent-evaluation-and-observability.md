# Agent 评测与可观测性：从最终答案追到完整轨迹

单轮问答可以只看最终输出，Agent 产品不能。一个 Agent 可能最终给出看似合理的答案，却在中间调用了错误工具、读取了不该读的数据、重复执行了动作，或者靠多轮重试把成本和延迟推高。AI PM 需要把“任务有没有完成”拆成**结果、步骤、工具、风险、成本和体验**几层，并让每一次线上执行都能被追踪和复盘。

本文后半部分补充生产侧最常见的几类坑：离线全绿但线上“时灵时不灵”、静默劣化、没有 golden set 怎么补救、多轮对话怎么评、供应商升版怎么拦，以及灰度比例与跨版本体验一致性。

> **选题启发**：磊叔《关于 AI 产品经理的 100 个问题》Q42、Q48、Q56、Q57、Q59、Q60、Q66、Q67。正文为原创方法论，不复述 PDF 中的具体数字与轶事。
>
> **事实**：Anthropic 与 OpenAI 都把“定义成功标准 → 建设可重复 evals → 持续评估 / 轨迹打分”放在迭代闭环的核心；Agent 评测还要区分**结果（outcome）**与**轨迹（transcript / trace）**，并在多试次下报告稳定性。见文末官方资料。
>
> **建议**：先定义任务成功的证据，再选指标和工具；不要先接一套监控平台，最后才发现团队并不知道什么叫“成功”。离线评测过闸不等于线上体验成立——二者要对齐，而不是互相替代。

## 一、先定义评测单位：一项任务，而不是一条回答

每条 Agent 评测用例至少应有以下字段：

| 字段 | 说明 |
|------|------|
| 用户目标 | 用户希望完成的任务，以及允许的输入范围 |
| 初始状态 | 用户权限、可用数据、可用工具、环境和时间点 |
| 允许路径 | 可接受的工具、步骤顺序或替代方案 |
| 必须满足 | 业务结果、内容质量、格式、权限和安全要求 |
| 不得发生 | 越权、泄露、重复副作用、未经确认的高风险动作 |
| 终止条件 | 成功、部分完成、拒绝、暂停、转人工的判定规则 |
| 评分方式 | 代码判定、人工 rubric、模型评分或组合判定 |

对于主观任务，标准答案通常不是唯一文本，而是可执行的 rubric；对于工具型任务，工具返回的业务状态和副作用结果应成为评分证据。评测集的来源、覆盖和版本管理可直接复用[从零建设评测集](../model-evaluation/build-your-eval-set.md)的方法。

## 二、四层指标：结果、步骤、工具、体验

### 1. 任务成功率(Task Success Rate)

```text
任务成功率 = 满足全部硬性条件且达到质量标准的任务数 ÷ 有效任务总数
```

“有效任务”要先定义，例如排除输入缺失、权限本来就不具备或用户主动取消的任务；但排除规则不能用来掩盖系统失败。建议同时报告：完全成功、部分成功、转人工、拒绝、系统失败和用户取消的比例。

任务成功的判定应包含三类证据：

- **业务证据**：工单状态、资源 ID、计算结果、审批状态等可验证结果；
- **质量证据**：内容正确性、引用充分性、格式和语气等 rubric 得分；
- **安全证据**：权限策略通过、没有泄露、风险动作得到确认。

### 2. 步骤成功率(Step Success Rate)

Agent 可能跳过步骤，也可能执行了很多无效步骤，所以建议把两个分母分开：

```text
必要步骤完成率 = 已完成且通过验证的必要步骤数 ÷ 该任务要求的必要步骤数
执行步骤有效率 = 通过验证的执行步骤数 ÷ 实际执行步骤数
```

前者回答“任务有没有漏做关键环节”，后者回答“Agent 已经做出的动作有多少有效”。两者都不能替代任务成功率：步骤全对，最终结果仍可能不满足用户目标；最终结果看起来正确，也可能掩盖了不安全的中间路径。

### 3. 工具成功率(Tool Success Rate)

工具成功不能只看 HTTP 200。至少区分：

- 调用是否通过 Schema 校验；
- 是否通过身份、租户、资源和动作级鉴权；
- 服务是否正常返回；
- 业务动作是否真的生效；
- 返回结果是否足以支持下一步判断。

例如“创建工单”接口返回成功，但工单被创建到错误租户，产品上仍然是失败甚至安全事件。建议为每个工具建立业务级成功事件，并记录错误码而不是只记录“调用异常”。

### 4. 体验与风险指标

Agent 的线上效果还会受到以下因素影响：首 token 延迟、任务总耗时、等待用户确认的时间、转人工率、取消率、重复追问率、用户采纳率、越权拦截率和安全告警率。具体指标树见[AI 产品指标体系](ai-product-metrics.md)。

## 三、轨迹追踪：把一次任务拆成可读的事件链

推荐把一次执行组织成一棵 trace：

```text
task
├─ model_turn: 规划或判断
│  ├─ tool_call: 搜索
│  │  └─ tool_result: 返回文档/错误码
│  └─ policy_check: 是否允许下一步
├─ human_approval: 用户确认
└─ final_result: 完成证据与用户回执
```

OpenTelemetry 将 Trace 定义为一组描述请求在系统中经历路径的 Span；Agent 产品可以借鉴这一标准，把模型调用、工具调用、策略检查和人工节点作为可关联的 Span。OpenAI 面向 Agent 工作流的评测入口也建议：先用 **trace grading** 定位工具选择、handoff、策略违例等问题，再沉淀成可重复的 dataset / eval runs。无论采用什么平台，至少要做到：

| 追踪层 | 必记字段 |
|--------|----------|
| 任务 | `task_id`、`trace_id`、用户/租户、目标、开始/结束时间、最终状态 |
| 模型回合 | 模型和 Prompt 版本、输入输出 token、延迟、是否产生工具调用 |
| 工具调用 | 工具版本、参数摘要、权限决策、开始/结束时间、错误码、重试次数 |
| 观察结果 | 返回数据类型、数据来源、校验结果、是否改变下一步计划 |
| 策略节点 | 命中的规则、拦截/放行原因、是否需要人工确认 |
| 最终结果 | 完成证据、用户可见回执、人工接管原因、成本汇总 |

**日志要分层。**调试用的原始输入输出不应默认对所有人可见，也不应把密钥、完整个人信息和认证凭据写进普通日志。产品活动记录可以只展示用户需要知道的动作；安全审计日志则保留足够的决策证据，并通过权限控制和保留策略保护它们。

## 四、工具错误与线上 Badcase

### 工具错误分类

| 类别 | 识别信号 | PM 要推动的处理 |
|------|----------|-----------------|
| 参数错误 | Schema 校验失败、缺少必填字段 | 优化工具描述、参数校验和模型提示 |
| 鉴权错误 | 无权限、租户不匹配、令牌失效 | 检查权限链，不允许靠重试绕过 |
| 暂时性错误 | 超时、限流、网络错误 | 只对可重试操作设置有限重试和退避 |
| 业务错误 | 对象不存在、状态不允许、库存不足 | 返回明确业务原因，走替代路径或转人工 |
| 数据错误 | 空结果、过期内容、格式异常 | 标记来源和新鲜度，触发数据修复或降级 |
| Agent 决策错误 | 选错工具、参数范围错误、重复调用 | 回放轨迹，补充评测用例和策略约束 |

### Badcase 记录卡

线上 Badcase 不要只贴一段最终回答。建议记录：

```text
问题描述：用户想完成什么，实际发生了什么
复现条件：输入、权限、数据版本、模型/Prompt/工具版本
轨迹摘要：关键计划、工具调用、策略判定、重试和人工节点
影响范围：用户影响、数据影响、是否产生副作用
初步归因：检索 / 模型 / Prompt / 工具 / 数据 / 产品预期 / 安全
修复验证：点验证、全量回归、灰度观察和回滚条件
```

具体的收集、归因、分发和回归方法见[Badcase 分析方法论](../model-evaluation/badcase-analysis.md)。每个已修复的线上 Badcase 都应进入回归集或对抗集，而不是只在工单里关闭。

## 五、离线评测与回归测试

### 评测集分层

建议至少维护四类集合：

- **核心任务集**：覆盖高频、重要且代表真实分布的正常任务；
- **边界任务集**：缺失输入、超长上下文、歧义、多轮和工具返回空结果；
- **安全对抗集**：Prompt Injection、越权尝试、恶意网页/文件和敏感信息请求；
- **回归集**：曾经修复过的线上 Badcase，以及不能再次出现的硬性失败。

回归集是“不能退步”的底线，不应因为分数饱和就删除；核心集和边界集则要随着线上分布和产品范围变化持续更新。Anthropic 区分 **capability evals**（爬山、可接受较低通过率）与 **regression evals**（应接近稳定通过，用来抓回退）；能力集跑通后可“毕业”进回归集持续守门。对 Agent 评测，建议把最终结果和轨迹约束同时评分；对于存在随机性的任务，可在相同版本下重复运行（多 trial），报告 pass@k / 一致性类指标，避免一次运行的偶然性决定上线结论。

### 版本对比表

每次变更至少绑定以下版本：

| 版本项 | 例子 |
|--------|------|
| 任务与评测集 | 用例版本、标注/rubric 版本、数据快照 |
| 模型行为 | 模型版本、系统 Prompt、路由策略、参数 |
| 工具链路 | 工具 Schema、服务版本、权限策略 |
| 评分器 | 代码规则、人工 rubric、LLM Judge 版本 |
| 运行环境 | 检索索引、依赖服务、超时和重试配置 |

这样才能解释“分数变了”到底是模型变了、评测集变了，还是工具和环境变了。上线前不应只看总分，还要看高风险用例是否触发一票否决、哪些维度显著退步，以及成本/延迟是否超过预算。

### 没有 golden set 就上线了：事后怎么补救

很多团队是产品先跑起来，才发现迭代全靠“看着顺眼”。补救顺序建议固定，避免边建设边继续盲飞：

1. **先立闸门，再扩规模。** 立刻从脱敏后的真实日志抽一批高频 / 高损任务，做成可评分的**种子集**（客观题写可校验答案，主观题写 rubric）。种子集要小而准：宁缺毋滥，两名业务专家应对同一条用例能给出一致的通过/不通过结论。
2. **把种子集写进发布流程。** 任何模型、Prompt、工具 Schema 或路由变更，必须先在种子集（外加安全对抗子集）上过闸；没有跑分记录的变更不允许进灰度。OpenAI 的评测实践强调 continuous evaluation：每次变更都跑、从生产日志挖新 nondeterminism 用例——这正好是补救阶段要补上的纪律。
3. **用线上信号持续扩集。** 每周把新 badcase、转人工会话、隐式负反馈会话回流；能力集里已稳定通过的任务毕业进回归集。建设方法与生命周期见[从零建设评测集](../model-evaluation/build-your-eval-set.md)。

补救的成功标准不是“集子变大了”，而是：**下一次供应商升版或 Prompt 改动，团队能在用户投诉前说清“哪类任务退步了”。**

### 多轮对话 / Agent：Evals 怎么设计才不失真

把多轮对话拆成单轮再加权平均，是最常见的失真做法：每一轮分数都不低，整段对话却已经跑偏。Anthropic 对 Agent eval 的定义更贴近产品现实——一次 **task** 对应多次 **trial**，完整 **transcript** 与环境 **outcome** 分开打分。

推荐三层同时评，任一层硬失败则整段任务失败：

| 层 | 评什么 | 常见判定 |
|----|--------|----------|
| 单轮可用 | 当轮是否相关、忠实、可执行 | 代码校验 / rubric |
| 对话一致性 | 前后是否矛盾、指代与约束是否被保持 | 轨迹约束、状态机检查 |
| 任务完成度 | 用户原始目标是否达成、副作用是否正确 | 业务状态 / 完成证据 |

额外约束：

- **评测单元是整段任务**，不是单条 message；用户模拟器或脚本用户可以驱动多轮，但最终仍以 outcome 为准。
- **轨迹与结果都要看**：Agent 可能口头说“已预订”，但库里没有订单——outcome 否决。
- **多试次**：同一任务跑多次，报告成功率分布，而不是单次绿灯。面向用户的稳定性更关心“几乎每次都成功”，而不是“多试几次总能撞中一次”。
- **环境隔离**：每次 trial 从干净状态起步，避免共享缓存/残留文件造成假阳性或假阴性。
- **样本来自真实多轮路径**：团队编的“理想剧本”往往覆盖不到用户插话、改口、带错别字和中途换目标。

OpenAI 的 Agent evals 路径也建议：调试期用 trace grading 找失败模式，稳定后迁到可重复 dataset；这与“先回放真实轨迹、再固化用例”一致。

### 供应商推了新版本：回归能不能拦住

供应商侧模型升级对调用方常是“同一 endpoint、不同行为”。接口与文档未变，不等于产品行为未变。回归闸门至少覆盖：

| 闸门 | 作用 |
|------|------|
| 固定回归集 | 高频场景、关键路径、已知边界、历史 badcase；升版前后同 harness 对比 |
| 分场景切片 | 总分不变也可能某个高频场景全线风格/事实漂移；按场景桶看跌幅 |
| 影子回放 | 用近期真实流量（脱敏）在新版本上重跑，与旧版本结果做差异排序，人工抽检高差异样本 |
| 护栏指标 | 安全、拒答、工具错误、成本、延迟分位——效果分涨但护栏爆了仍不能放行 |
| 钉死版本 | 生产绑定可回滚的模型版本 ID；“默认 latest”等于把发布权交给供应商 |

Anthropic 指出：有 evals 的团队能在新模型发布后较快判断强弱并调 Prompt；没有 evals 则只能靠猜测与补锅。PM 要推动的不是“测更多”，而是**升版事件自动触发回归 + 异常自动告警**，并把“能否一键切回旧版本”写成上线前置条件。

## 六、线下绿、线上灰：Gap 怎么填

用户反馈“时灵时不灵”，离线报表却一片绿，通常不是“用户太挑剔”，而是**离线世界与线上世界脱节**。

### 常见根因

| 根因 | 表现 | 排查动作 |
|------|------|----------|
| 评测分布 ≠ 线上分布 | 测试集是规范、干净的；用户用方言、错别字、多意图揉在一起 | 按线上频率分桶重采样；长尾单独建切片 |
| 评测维度 ≠ 用户价值 | Evals 涨在流畅度/格式，用户要的是一次办成、可复制、可信任 | 把采纳、完成、转人工等行为指标与分维度 eval 对齐 |
| 链路瓶颈不在模型 | 模型输出变好，但检索、权限、兜底、UI 入口仍卡住 | 按链路分段看“模型层改善是否触达用户可见结果” |
| 方差被当成稳定质量 | 单次跑分全绿，线上同一任务时好时坏 | 多 trial；线上按用户/会话聚合，见[AI 产品的 A/B 测试](../model-evaluation/ab-testing-for-ai-products.md) |
| 过拟合评测集 | 团队反复对着同一批 case 调到满分 | 保留 held-out；新日志持续进集；能力集与回归集分开 |

### 离线涨了、业务不动：断点怎么查

这是 Gap 的“反向版本”：技术侧宣称提升，业务侧无感。排查优先级：

1. **指标翻译是否对齐**：离线主指标是否映射到预注册的线上 OEC / 护栏？不对齐就先改评测定义，而不是加流量。
2. **散点对照**：若干次版本变更的离线分 vs 线上行为/业务指标；长期不相关，说明评测在优化错误目标。
3. **触达检查**：灰度用户是否真的打到新版本？缓存、路由、客户端旧包是否稀释了效果？
4. **体验摩擦**：延迟、确认弹窗、格式变化是否抵消了质量收益？

推荐默认链路（与 A/B 文一致）：

```text
离线评测集 + 安全闸门 → 小流量/影子观察质量与稳定性 → 正式 A/B（用户随机）→ 结论与离线分维度对照
```

离线负责“输出是否按规格变好”，线上负责“用户与业务是否因此变好”。详细实验设计见[AI 产品的 A/B 测试](../model-evaluation/ab-testing-for-ai-products.md)。

### 用线上行为把 Gap 补上

离线 Evals 回答发版前“系统还行不行”；线上监控回答发版后“用户感受到了什么”。除了报错率，优先看**拿到回答后的下一步**：复制/采纳、继续追问并完成任务、立即重生成、关闭、转人工。把负向会话抽样脱敏后回流评测集，Gap 才会随迭代缩小。

## 七、静默劣化：用户投诉前怎么发现

静默劣化（silent degradation）指：系统日志无报错、延迟正常，但效果在变差——用户慢慢流失、投诉慢慢上升。根因常是供应商透明升版、检索索引漂移、工具下游语义变化，或 Prompt/路由在未跑回归的情况下被改动。

**技术健康 ≠ 效果健康。** 发现手段要叠三层：

1. **行为哨兵**：重新生成率、转人工率、任务完成率、采纳/复制、会话中途放弃等相对基线的漂移告警（按任务类型与租户切片，避免总平均吞掉局部崩盘）。
2. **质量哨兵**：定期用固定回归集 + 线上抽样回放跑分；Google Cloud 将生产期用新数据周期性评估、发现性能下降再行动的过程称为 continuous evaluation——Agent 产品应把“周更/变更触发”写成机制，而不是靠人记得去测。
3. **变更哨兵**：模型版本 ID、Prompt hash、工具 Schema、索引版本任一变化，自动触发回归；生产禁止无版本钉死的 `latest`。

处置预案写在告警里：定位退步场景桶 → 评估是否回滚模型/Prompt/路由 → 补充回归用例 → 复盘为什么闸门没拦住。等投诉爆发再查，伤害已经沉没。

## 八、灰度、回滚与体验一致性

推荐把发布拆成四步：

1. **离线闸门**：核心任务和安全回归达到上线线；硬性安全失败直接阻断。
2. **影子或小流量验证**：在不产生副作用的前提下观察真实输入分布、工具错误、轨迹长度和成本。
3. **分层灰度**：先覆盖低风险用户、低风险工具或可回滚场景，按用户、租户、模型版本分组观察。
4. **扩大与复盘**：稳定后扩大流量，并把新 Badcase 回流评测集。

### 灰度比例：原则比“标准百分比”重要

不存在普适的流量切分表。比例由**风险、可回滚性、指标方差与样本量**共同决定；把外部文章里的阶梯百分比抄成制度，本身就是发布设计失败。可执行原则：

- **从小到大，每步有观察期**：观察的是用户行为与护栏，不只是错误率和延迟；观察窗口长度取决于产品使用频率与功效需求（高频与低频产品所需日历时间不同）。
- **先低风险切片**：新用户或可逆场景 → 再老用户/高价值租户；低风险工具 → 再有副作用的工具。
- **按用户/租户粘性分流**：同一用户在观察期内应稳定落在同一版本，避免会话中途来回跳（见下一小节）。
- **回滚前置**：扩大流量前确认能按版本一键切回；回滚条件（效果、安全、成本、延迟、基础设施）写在上线单里，而不是出事后再争论。
- **与正式 A/B 分工**：灰度先回答“能不能安全放大”；要宣称相对旧版的业务因果，仍需满足[A/B 实验设计](../model-evaluation/ab-testing-for-ai-products.md)的预注册与功效要求。

### 同一用户跨版本：体验一致性怎么保证

用户昨天在 A 版、今天在 B 版时，困惑往往来自**格式、风格、能力边界**同时漂移。传统软件保 UI 即可；AI 产品还要保“回答长什么样、敢不敢做什么”。建议三层约束：

| 层 | 目标 | 手段 |
|----|------|------|
| 格式合同 | 结构稳定（引用、列表、必填字段、拒答话术） | System Prompt / 输出 Schema；跨模型同一套校验 |
| 风格对齐 | 语气与详略不过度跳变 | few-shot 锚定旧版合格样例；配对抽样人工或 Judge 对比 |
| 能力不回退 | 核心场景不低于旧版 | 回归集 + 场景桶对比；高风险能力未过闸则对该能力继续走旧版或降级 |

发布策略上优先 **sticky assignment**（按用户/会话粘住版本），并在产品内对能力变更做可见说明（尤其是拒答边界变严或工具权限收缩时）。一致性不是要求两版逐字相同，而是：**用户可预期的合同不变，意外只出现在已沟通的能力升级上。**

回滚开关至少要能切换模型/Prompt/路由版本、关闭某个工具、降低 Agent 自主范围、切回固定 Workflow 或直接转人工。

## 九、成本与延迟：每条轨迹都要算账

一次 Agent 任务的成本可以拆成：

```text
任务成本 = 模型输入/输出成本
         + 工具与基础设施成本
         + 检索/存储/浏览器执行成本
         + 人工确认或接管成本
```

延迟则至少拆成排队、模型首 token、模型生成、工具网络往返、工具执行和人工等待。平均值会掩盖长尾，建议看 P50/P95/P99 或与业务约定的其他分位数，并按任务类型、模型层级、工具和是否重试分组。

需要重点观察两种“看似成功”的异常：

- 任务成功率上升，但每项任务调用轮数和成本快速上升；
- 平均延迟不变，但长任务和人工确认的长尾已经影响用户完成率。

## 十、Agent 评测看板自查清单

- [ ] 每个任务都有可验证的成功标准和失败分类。
- [ ] 任务成功率、必要步骤完成率、执行步骤有效率和工具业务成功率分开统计。
- [ ] 线上执行能通过 `task_id/trace_id` 关联模型、工具、策略和人工节点。
- [ ] 评测集覆盖正常、边界、安全对抗和线上回归用例；无集上线时有种子集补救计划并已写入发布闸门。
- [ ] 多轮/Agent 用例以整段任务为单元，同时评一致性与 outcome；关键任务有多 trial。
- [ ] 评测报告记录模型、Prompt、工具、数据和评分器版本；生产钉死可回滚版本 ID。
- [ ] 供应商升版 / Prompt 变更会自动触发回归与差异回放告警。
- [ ] 行为哨兵与质量哨兵可发现静默劣化，不等待投诉。
- [ ] 离线提升与线上 OEC/护栏有对照解释；冲突时有分布与链路排查路径。
- [ ] 灰度前已写好扩大条件、粘性分流、回滚条件和责任人；核心场景有跨版本格式/能力一致性检查。
- [ ] 成本、延迟、重试、转人工和长尾按任务类型分层监控。
- [ ] Badcase 修复后完成点验证、全量回归和灰度观察，并回流评测集。
