# Agent 产品生产化：从会执行到可负责地完成任务

> **选题启发**：磊叔《关于 AI 产品经理的 100 个问题》Q14、Q18、Q19（非确定性流程兜底、「少能力多可靠」、人介入决策点；仅选题结构，正文为原创）。

Agent 产品不是“给大模型接几个工具”就结束了。生产化的核心，是把模型的自主决策放进一份明确的产品契约：它要完成什么任务、可以调用什么、什么时候必须停下来问人、失败后怎么退回、花费到哪里必须刹车，以及什么证据足以证明任务真的完成。

> **事实**：Anthropic 将固定路径编排的系统称为 Workflow，将由模型动态决定步骤和工具使用的系统称为 Agent；OpenAI 的 Agent 指南也把模型、工具、指令与防护机制视为一个需要整体设计的系统。Agent 因为路径不完全固定而更灵活，也因此更难预测。见文末官方资料。
>
> **建议**：AI PM 不要先问“要不要做 Agent”，而要先问“这项任务是否多步骤、是否需要外部动作、每一步能否验证、出错代价是否可接受”。

## 一、先定义任务，不先定义 Agent

一个可生产化的 Agent，首先应该有一张**任务卡(Task Contract)**。任务卡不是技术方案，而是产品、算法、工程、安全和运营共同认可的边界。

| 字段 | 要回答的问题 | 可验收的写法 |
|------|--------------|--------------|
| 用户目标 | 用户到底想完成什么，而不是想让模型说什么？ | “把本周待处理工单按优先级分组，并生成待确认清单” |
| 触发条件 | 什么输入会启动任务？什么输入直接拒绝？ | 规定输入来源、格式、数据范围和不支持场景 |
| 任务范围 | Agent 能做哪些子任务，不能碰哪些系统或数据？ | 明确允许的工具、资源、租户和操作类型 |
| 完成标准 | 什么证据说明任务完成？ | 结果字段齐全、关键工具返回成功、业务规则校验通过 |
| 人工介入 | 哪些节点必须由人确认或接管？ | 金额、删除、外发、权限变更等副作用动作先确认 |
| 失败出口 | 失败后是重试、降级、暂停还是转人工？ | 每类错误对应唯一的下一步和用户提示 |
| 预算边界 | 一项任务最多消耗多少调用、时间和费用？ | 到达任一上限就停止自主循环并说明原因 |

**完成标准不等于模型说“完成了”。**模型输出的自然语言只能是一个候选结果；真正的完成状态应由工具结果、业务校验、人工确认或用户验收共同决定。比如“已发邮件”至少需要邮件服务返回可追踪的发送结果，而不是 Agent 生成一段“邮件已发送”的文字。

## 二、任务拆解：选择 Agent、Workflow 还是混合方案

先把任务画成路径，再决定哪里让模型自主规划：

```text
用户目标
  ↓
输入校验 → 固定步骤？ ── 是 ──→ Workflow/规则流程
  │                         │
  否                        └─ 关键节点仍可调用模型
  ↓
允许的计划范围 → 工具调用 → 结果校验 → 继续/重试/人工确认/结束
```

| 场景特征 | 推荐形态 | PM 的重点 |
|----------|----------|-----------|
| 步骤固定、规则清晰、错误代价高 | Workflow 或规则流程 | 把分支、权限和回滚写死，模型只负责局部理解 |
| 步骤不固定、需要搜索和判断、结果可检查 | 受约束的 Agent | 限制工具目录、最大循环、完成证据和失败出口 |
| 前半段需要规划，后半段必须确定性执行 | 混合方案 | 让模型提出计划，让代码校验并执行关键动作 |

### 工具调用要当作产品接口设计

工具描述会影响模型是否选中它、传入什么参数和何时停止。每个工具至少要有以下契约：

| 设计项 | 需要写清的内容 |
|--------|----------------|
| 名称与用途 | 用用户能理解的动词命名，明确“能做什么”和“不能做什么” |
| 输入 Schema | 类型、必填项、枚举值、长度限制、格式校验和默认值 |
| 权限范围 | 当前用户、当前租户、可读资源、可写资源和不可访问资源 |
| 副作用 | 只读、可逆写入、不可逆写入；是否会产生费用或对外发送 |
| 幂等性 | 重复调用会不会重复扣款、重复建单或重复发送 |
| 超时与错误 | 超时、鉴权失败、业务拒绝、空结果分别返回什么错误码 |
| 返回证据 | 返回状态、资源 ID、时间戳、来源和可供下一步判断的字段 |

OpenAI 的 Function Calling 文档描述了模型生成结构化工具调用、由应用执行并把结果回传给模型的基本循环；MCP 解决的是 Agent 与外部工具/资源如何连接的问题。两者都不等于业务权限系统，真正的鉴权和参数校验必须在工具服务端再次执行，不能只相信模型的判断。

## 三、状态与记忆：让任务可暂停、可恢复、可解释

不要只把 Agent 当成一段对话。生产产品需要保存**任务状态**，并区分“这次任务的临时上下文”和“跨任务长期保留的记忆”。

### 推荐的最小状态机

```text
created → planning → running_tool → observing
              ↑           │             │
              │           ├─ 可重试 ────┘
              │           ├─ 需确认 → waiting_approval
              │           └─ 达到上限 → blocked
              └────────────┴─ 继续规划

waiting_approval → approved → running_tool
                 └ denied/cancelled → cancelled
observing → succeeded / failed / handed_off
```

状态名要能回答三件事：用户现在是否需要操作、系统是否还会继续消耗资源、运营是否可以恢复任务。暂停状态不能悄悄变成后台继续执行；用户取消后也不能因为队列重试而重新触发副作用动作。

### 短期状态与长期记忆

| 类型 | 适合保存 | PM 要求 |
|------|----------|---------|
| 短期状态 | 当前计划、中间结果、工具返回、待确认动作 | 绑定任务 ID，支持恢复、取消和过期 |
| 长期记忆 | 用户明确授权保存的偏好、稳定配置、历史结论 | 说明用途、来源、有效期、修改和删除方式 |
| 不应保存 | 密钥、完整支付信息、无必要的敏感原文、无法验证的模型猜测 | 默认不保存；需要时只传最小必要字段 |

**建议**：每条记忆都记录来源和时间，不把模型生成的推断自动当成用户事实。让用户能查看、纠正和删除长期记忆；对跨租户、跨用户共享的知识，优先走有权限的知识库/RAG，而不是混进个人记忆。

## 四、人工接管与权限：自主性必须有边界

人工接管不是 Agent 失败后的临时补丁，而是高风险任务的正常路径。哪些步骤必须设人闸门，见[第八节](#八人介入决策点哪些步骤必须停下来问人)；本节先按副作用做风险分级与权限链：

| 风险级别 | 例子 | 默认策略 |
|----------|------|----------|
| 低 | 只读搜索、草稿生成、内部摘要 | 可自动执行，但记录来源和结果 |
| 中 | 创建草稿工单、修改可撤销配置、批量整理文件 | 先预览变更，允许用户编辑或撤销 |
| 高 | 付款、删除、对外发布、发送敏感信息、修改权限 | 展示目标/范围/后果，用户明确确认；必要时重新认证 |

权限链至少要经过：**当前用户身份 → Agent 身份 → 工具权限 → 资源范围 → 动作级权限 → 风险确认**。模型可以提出动作，但不能自行扩大权限。工具服务端要根据当前用户和租户重新鉴权，并校验资源归属、参数范围和目标地址。

确认弹窗不能只写“是否继续”。应至少展示：将要做什么、对哪个对象做、使用哪些数据、可能造成什么后果、是否可撤销，以及拒绝或修改入口。确认应绑定当前任务和当前版本，过期后不能被旧任务重放。

## 五、失败重试、降级与成本上限

Agent 的失败不是一种错误。建议把错误分为四类，并为每类预先定义动作：

| 错误类型 | 典型表现 | 默认处理 |
|----------|----------|----------|
| 暂时性错误 | 超时、网络抖动、服务限流 | 只对幂等步骤有限重试，带退避和总时限 |
| 参数/Schema 错误 | 缺少字段、格式不合法、工具拒绝参数 | 不盲目重试，修正参数或回到计划节点 |
| 业务错误 | 资源不存在、库存不足、用户无权限 | 告知原因，改走替代路径或转人工 |
| 未知/高风险错误 | 返回异常、结果与预期冲突、疑似越权 | 立即暂停，保留现场，要求人工判断 |

**重试的三个硬条件**：知道错误可能是暂时的；重复执行不会叠加副作用；重试次数和总耗时都受上限控制。对非幂等工具，优先通过幂等键、执行状态查询或人工确认来避免重复动作。

任务预算可以拆成：

```text
任务预算 = 模型调用预算 + 工具调用预算 + 时间预算 + 人工复核预算
```

模型调用预算不仅看 token，还要考虑规划轮数、工具结果被反复塞回上下文的放大效应。达到任一上限就进入 `blocked` 或 `handed_off`，向用户解释“已完成什么、卡在哪里、下一步需要谁处理”，而不是继续静默烧资源。

## 六、非确定性流程：别用确定性流程图硬套

传统功能 PRD 习惯画一条「点 A → 必达 B」的主路径，再挂异常分支。Agent 的主路径本身就是概率性的：同输入可能走出不同工具序列，某一步「看起来合理」却未必可验证。若仍按确定性流程图验收——默认每一步都会成功、没有中间出口——demo 很漂亮，上线后第一次偏航就会把用户摔在空状态里。

> **事实**：Anthropic 在 *Building effective agents* 中明确区分 Workflow（代码编排的固定路径）与 Agent（模型在循环中动态选工具）；并建议先找最简单方案，只在确有必要时增加自主性。路径越开放，延迟、成本与失败形态越难先验穷举。见文末资料。
>
> **建议**：先问「哪几段必须确定性、哪几段允许模型规划」，再画图；图上每个非确定节点都要预先挂**唯一下一步**，而不是「模型自行想办法」。

### 流程图里每个 AI 节点至少写清四件事

| 要写的 | 可验收写法 | 不要写成 |
|--------|------------|----------|
| 成功判据 | 工具回执字段 / 业务规则 / 人工确认里哪几条必须满足 | 「模型说完成了就算」 |
| 不确定出口 | 低置信、证据冲突、超出能力边界时走拒答 / 澄清 / 转人工 | 「尽量答」 |
| 失败出口 | 重试条件、降级形态、暂停态（对齐第五节错误分类） | 「失败就再试一次」 |
| 副作用刹车 | 写操作前是否必须确认；取消后不得重放 | 只画 happy path |

「模型只有七成把握」时，产品要接住的不是一句免责声明，而是**主流程上的分支**：澄清追问、缩小任务范围、只产出可编辑草稿、或把现场交给人。交互层控件与话术见 [兜底、反馈与预期管理](../prd-and-design/fallback-and-feedback-design.md)；PRD 里把失败分支写进用户故事，见 [AI 产品 PRD 怎么写](../prd-and-design/ai-prd-guide.md) 的兜底与能力边界章节。

### 可落地的混合画法

```text
确定性段（校验 / 鉴权 / 计费 / 写库）── 代码或 Workflow 扛
        │
非确定性段（理解意图 / 选工具 / 起草计划）── 受约束 Agent
        │
汇合闸门（完成证据 + 风险确认）── 不通过则停，不让模型「再绕一圈硬闯」
```

把「规划」和「执行关键副作用」拆开，比画一张超大自由 Agent 图更容易上线：模型可以提议，闸门决定是否真的改世界状态。

## 七、「少能力多可靠」：先抬地板，再谈天花板

Agent 演示容易比拼「还能多干一件事」；生产验收更该问：**在承诺范围内，最差一批任务还能不能稳妥结束**。能力多、工具多、自主规划步数多，通常伴随延迟、费用与失败面同时放大——Anthropic 也提醒：Agent 常以更高延迟与成本换取任务表现，应先确认这笔交换值不值得。

**「少能力多可靠」**在本库的含义是：主动收窄默认能力面与工具面，把工程与产品精力从「再加点技能」挪到「承诺内的成功率下限、失败可解释、副作用可刹住」。它不是鼓励做弱产品，而是拒绝用不可靠的宽能力换演示分数。

| 维度 | 追能力天花板时常见做法 | 追可靠性地板时的产品选择 |
|------|------------------------|--------------------------|
| 范围 | 默认开放多工具、多意图 | 白名单场景 + 明确不支持清单（对齐 PRD 能力边界） |
| 路径 | 端到端自主规划 | 固定段用 Workflow；仅必要处分叉给模型 |
| 指标 | 平均任务成功率、单次 demo 惊艳度 | **分位数 / 高风险子集**成功率、人工介入率、不可逆误操作率、预算触顶率 |
| 失败 | 靠模型「再想想」 | 预置出口：降级、草稿化、转人工、blocked |
| 扩张 | 先上线再补边界 | 新工具 / 新副作用默认关闭，过评测与灰度再开 |

衡量时建议至少同时看三块（阈值由业务定，下表是结构不是普适红线）：

1. **完成质量**：在任务卡范围内，成功 / 部分成功 / 失败的分布；尤其看最差分位与高风险子集，而不是只报均值。
2. **过程可控**：越权尝试是否被工具层拦住、确认是否被跳过、取消后是否仍产生副作用。
3. **资源与交接**：是否在预算内结束；转人工时是否带上「已完成 / 卡点 / 证据」，而不是丢给坐席一个黑箱会话。

> **建议**：扩张能力前先问——新能力会把哪条可靠性地板拉低？若暂时补不上出口与评测，就先不要进默认路径。信任侧如何避免「能力宣传跑在真实水位前面」，见 [Agentic UX 与信任校准](../prd-and-design/agentic-ux-and-trust-calibration.md)；授权与停机条件如何写进文档，见 [AI 产品 PRD](../prd-and-design/ai-prd-guide.md) 的 Agent 行为边界一节。

## 八、人介入决策点：哪些步骤必须停下来问人

第四节讲风险分级与确认弹窗「长什么样」；交互层何时该信、如何校准，见 [Agentic UX 与信任校准](../prd-and-design/agentic-ux-and-trust-calibration.md)。本节只回答生产化问题：**任务图上哪些节点必须是人闸门（HITL），哪些可以自动过**。

> **事实**：Anthropic 在安全可信 Agent 框架中强调——自主有价值，但高后果决策前人应保留控制；其工程实践也指出逐步弹权限容易造成确认疲劳（用户大量机械点「允许」），监督要落在真正高风险处，而不是每一步都打断。见文末资料。
>
> **建议**：人介入是默认设计选项，不是失败后的补丁；真正要设计的是**介入点清单**，并写进任务卡与 PRD 行为边界。

### 决策题：这个节点要不要等人？

按下面四问打分；任一问为「高」就倾向设闸门，而不是靠模型自觉：

| 决策题 | 偏自动 | 偏人介入 |
|--------|--------|----------|
| 副作用可逆吗？ | 只读、可丢弃草稿、可一键撤销 | 外发、付款、删除、改权限、难回滚配置 |
| 错了代价谁扛？ | 用户可轻松改掉；无合规/资金敞口 | 资金、隐私、安全、法律责任、品牌公关 |
| 证据是否可自动核验？ | 工具回执 + 业务规则能判真假 | 需主观判断、跨系统对账、或证据互相冲突 |
| 用户是否具备当场判断力？ | 确认卡片信息足够、用户懂后果 | 需专家审核、或确认已沦为「下一步」按钮 |

### 三类介入点（写进任务卡即可验收）

| 类型 | 典型位置 | 产品要求 |
|------|----------|----------|
| **事前闸门** | 首次授权连接器、进入高风险工具、批量写操作前 | 展示对象 / 范围 / 后果 / 可否撤销；绑定当前任务版本，防重放 |
| **事中闸门** | 计划偏离原目标、置信不足、策略冲突、疑似提示注入 | 进入 `waiting_approval`；禁止静默改写目标后继续 |
| **事后闸门** | 不可逆动作已发生后的复核、抽检、客诉升级 | 保留完成证据与审计字段；支持补偿流程而不是只道歉 |

**反模式**：

- **全程 HITL**：每一步都点确认 → 确认疲劳，高风险确认也被点掉（可靠性假象）。
- **零 HITL 演示路径**：demo 关掉所有确认 → 线上事故后才补闸门，信任一次性打穿。
- **只写在 Prompt 里**：「高风险要问人」但工具层仍可直接调用 → 硬边界必须落在鉴权与状态机，与 [AI PRD 的 Agent 行为边界](../prd-and-design/ai-prd-guide.md) 一致。

渐进放开的顺序建议与信任校准相同：先「建议 → 人确认后执行」，白名单场景再自动执行，高后果节点长期保留人闸门。每升一级，都要用第七节的可靠性地板指标证明「自动段」站得住。

## 九、审计日志与完成标准

日志要同时服务于三类人：用户需要知道发生了什么；运营需要定位 Badcase；安全和合规需要追责与复盘。建议记录以下事件字段：

- `task_id`、`trace_id`、用户/租户标识、创建和结束时间、当前状态；
- Agent、模型、Prompt/Policy、工具版本；
- 每个计划步骤、工具名、参数摘要、权限判定、确认人和确认时间；
- 工具返回状态、错误码、重试次数、输入/输出 token、延迟和费用；
- 最终完成证据、人工接管原因、用户取消原因和回滚结果。

日志不等于把所有原文都存下来。敏感字段应脱敏或哈希，访问应分级，保留周期应与业务和合规要求对齐。调试日志、用户可见活动记录和安全审计日志可以分层存储，但三者应能通过任务 ID 关联。

一项任务对用户的完成回执，至少应包含：

```text
完成状态：成功 / 部分完成 / 等待确认 / 失败 / 已转人工
已完成：动作、对象、结果证据
未完成：原因、影响范围、是否会继续执行
下一步：用户需要确认、补充信息或联系谁
```

## 十、上线前自查清单

- [ ] 任务卡写清了目标、范围、完成证据和不支持场景。
- [ ] 流程图上每个非确定节点都有成功判据、不确定出口、失败出口和副作用刹车。
- [ ] 默认能力面与工具面已收窄；扩张前有可靠性地板指标（含高风险子集，不只看均值）。
- [ ] 每个工具都有输入校验、权限范围、副作用、幂等性和错误码。
- [ ] Agent 有明确状态机，用户取消后不会继续执行副作用动作。
- [ ] 短期状态、长期记忆和敏感数据的保存边界已区分。
- [ ] 人介入决策点已按可逆性 / 代价 / 可核验性列出；高风险动作确认有信息量，且未做成逐步机械弹窗。
- [ ] 重试只覆盖可识别的暂时性错误，且有次数、时间和费用上限。
- [ ] 任务、模型、Prompt、工具、权限、确认和结果证据可以通过日志关联。
- [ ] 任务级成功标准已经进入评测集，并能在灰度期间和线上指标对应起来。
