# 模型选型决策框架:效果、成本、延迟、合规四要素

> **信息状态**：动态快照｜**最后核验**：2026-08-06

> 价格截至 2026-07,以官方定价页为准。本文引用的模型单价参考[《AI 产品成本测算入门》](llm-cost-101.md)中的价格对比表;分层路由与降本手段见[《降本手段盘点》](cost-optimization.md)。

"该用哪个模型"是 AI PM 最常被问到、也最容易拍脑袋回答的问题。很多团队默认"选最强的模型"或"选最便宜的模型",两种做法都容易踩坑——前者浪费预算,后者伤害体验。本文给出一套可以落地评审的四要素框架:**效果、成本、延迟、合规**,以及配套的选型流程和团队分工建议。

文末三节补充企业交付里常卡死的选型外延决策:私有化是真约束还是谈判话术、何时拒绝「每客户一模型分支」、开源能力追上后哪些流量该从 API 迁本地。选题启发自磊叔《关于 AI 产品经理的 100 个问题》Q77 / Q81 / Q97;正文为原创决策框架,**不摘录该 PDF 答案**。

## 一、四要素总览

| 要素 | 核心问题 | 典型冲突 |
|------|----------|----------|
| 效果(Quality) | 模型能不能把这个任务做对、做好? | 效果越好的模型通常越贵、越慢 |
| 成本(Cost) | 按这个方案跑,规模化后账单能不能承受? | 便宜的模型可能需要更复杂的 Prompt/更多轮重试,隐性成本更高 |
| 延迟(Latency) | 用户能不能接受这个响应速度? | 低延迟往往要牺牲模型规模或牺牲效果 |
| 合规(Compliance) | 数据出不出境?内容安不安全?能不能审计? | 最合规的方案(自建/国产/私有化)往往效果或成本不占优 |

选型的本质,不是找到"四项全优"的模型(几乎不存在),而是**明确任务对四要素的优先级排序**,再做取舍。下面逐一展开。

## 二、效果:怎么评估"好不好"

### 评估方法

| 方法 | 适用阶段 | 说明 |
|------|----------|------|
| 公开 Benchmark(如 MMLU、GPQA、行业垂类榜单) | 候选池初筛 | 快,但和你的实际任务可能不对齐,只能做参考不能做决策依据 |
| 自建评估集 + 人工评分 | 选型中期 | 用真实业务场景的 100-300 条样本,让标注/业务人员打分,是最可信的方法 |
| 模型互评(LLM-as-judge) | 大规模评估 | 用强模型给候选模型的输出打分,能规模化但要警惕评委模型本身的偏好偏差 |
| 影子测试/线上 A/B | 上线前最后一步 | 真实流量下对比核心业务指标(转化率、满意度、复购等),而不只是"回答质量分" |

### PM 该问的问题清单

- 这个任务的"好"是怎么定义的?是事实准确、逻辑严密,还是语气得体、格式规范?不同任务对效果的定义完全不同。
- 我们有没有一份能代表真实用户输入分布的测试集?(避免只用"简单干净"的样例测试,上线后被长尾 case 打脸)
- 效果的评估是一次性的,还是要建立持续监控(防止模型升级、Prompt 改动导致效果悄悄下滑)?
- 多大的效果差距才值得多付钱?(比如"贵 3 倍但准确率只高 2 个百分点",大概率不值得)

## 三、成本:延续上一篇的估算方法

成本要素的落地方法已经在[《AI 产品成本测算入门》](llm-cost-101.md)详细展开,这里只列选型时要追问的问题清单:

- 这个任务的输入 token 量级是多少?是否有长文档/长历史对话,导致输入成本远高于输出成本?
- 是否可以用小模型完成大部分请求,只把疑难请求路由给大模型?(分层策略见下一节)
- 这个场景是否是异步/非实时的?能不能用 Batch API 拿到官方 50% 左右的折扣?
- 调用量的增长曲线是怎样的?今天算的账,3 个月后渗透率翻倍还成立吗?

## 四、延迟:用户能接受多慢

| 指标 | 含义 | 产品影响 |
|------|------|----------|
| 首 token 延迟(TTFT) | 用户发出请求到看到第一个字返回的时间 | 直接决定"感觉快不快",流式输出可以大幅改善这个体感 |
| 总生成时间 | 完整回答生成完的总耗时 | 输出 token 越多耗时越长,长回答场景要考虑限制输出长度 |
| 并发/排队延迟 | 高峰期请求排队等待的时间 | 容易被忽略,压测时只测单请求延迟,忽略了并发下的真实体验 |

### PM 该问的问题清单

- 这个场景是同步等待(用户盯着屏幕等),还是异步通知(比如生成报告后推送)?同步场景对延迟敏感得多。
- 能不能用流式输出改善体感?(哪怕总耗时一样,"边生成边看到"比"转圈等待"体验好很多)
- 高峰期的并发量级是多少?选型时是否测过高并发下的延迟劣化,而不只是单请求延迟?
- 是否可以用"快速模型先给初步结果,慢速模型异步优化"的分级体验来兼顾速度和效果?

## 五、合规:容易被低估的一环

合规不是"选完模型再补的手续",而是应该在选型早期就参与筛选候选池的硬约束。

### PM 该问的问题清单

- 数据能不能出境?哪些字段是敏感信息(身份证、病历、金融账户等),是否有强制的数据本地化/国产化要求?
- 模型供应商是否承诺不用客户数据训练?合同条款是否明确?
- 是否需要满足特定行业监管(金融、医疗、教育)对 AI 生成内容的审计、留痕、可解释性要求?
- 内容安全:是否有内置的内容审核能力,还是需要自建一层审核?
- 版权风险:生成内容是否可能涉及版权纠纷(尤其是图片、代码类场景)?

**建议**:把合规当作"一票否决项"先过滤候选池,再在剩下的候选中比较效果、成本、延迟——顺序反了容易做无用功(选型选到一半才发现某模型不能用于你所在的行业/地区)。

## 六、大小模型分层策略

实践中很少有产品只用一个模型跑所有请求,更常见的做法是分层:

| 层级 | 典型模型定位 | 承接的请求 | 占比参考 |
|------|--------------|------------|----------|
| 轻量层 | Haiku 级 / mini・nano 级 / Flash-Lite 级 | 意图识别、简单分类、格式化提取 | 60-70% |
| 主力层 | Sonnet 级 / 主力级 / Flash 级 | 常规问答、大部分业务场景 | 20-30% |
| 旗舰层 | Opus 级 / 旗舰级 / Pro 级 | 复杂推理、长文档理解、高风险决策 | 5-10% |

分层的关键不是"哪个模型好",而是"用一个足够便宜/足够快的分类器,把请求准确路由到合适的层级"。路由误判是这套策略最大的风险——把复杂问题误判成简单问题、发给轻量模型,会直接反映在用户体验上。具体的路由实现和节省幅度测算,见[《降本手段盘点》](cost-optimization.md#四小模型路由分级服务)。

## 七、自建 vs API:什么规模才值得考虑私有化部署

这是几乎每个团队都会讨论、但常常没有结论的问题。给出一个粗略的决策框架:

| 决策维度 | 倾向 API 直连 | 倾向自建/私有化部署 |
|----------|----------------|----------------------|
| 调用规模 | 日调用量在百万级 token 以内,或业务尚在验证期 | 日调用量达到十亿级 token 以上且长期稳定,GPU 成本摊薄后低于 API 账单 |
| 团队能力 | 没有专职的模型部署/推理优化团队 | 有算法工程团队能做推理优化(量化、批处理、vLLM 等) |
| 合规要求 | 数据可以出境,或供应商已满足合规要求 | 数据绝对不能出企业内网/必须国产化替代 |
| 迭代速度要求 | 需要跟着最新最强模型快速迭代 | 任务边界清晰、模型能力已经"够用",不需要追新 |
| 场景定制化程度 | 通用能力即可满足 | 需要针对垂类场景深度微调,通用 API 效果始终不达标 |

**一个直观的判断方法**:先用[成本测算入门](llm-cost-101.md)的估算模板算出"如果一直用 API,月成本是多少";再找算法/基础设施同事估一个"自建需要多少张 GPU + 多少运维人力";两者做 12-18 个月的总拥有成本(TCO)对比,而不是只比"单价"。很多团队自建后发现,GPU 利用率不足、运维投入被低估,实际成本并不比 API 便宜——所以自建决策一定要拉上算法/基础设施团队一起测算,PM 不该单方面拍板。

对外销售场景里,客户口中的「私有化」往往比上表更含糊——可能是监管硬约束,也可能只是压价话术。甄别方法见下文「十、私有化:真需求还是谈判筹码」。开源追上闭源之后,内部产品侧的「API → 本地」迁移节奏见「十二」。

## 八、选型评审的落地流程

一套可以直接搬进团队评审会的流程:

```
1. 需求定义
   明确任务类型、效果底线、延迟要求、合规硬约束(一票否决项先过滤)

2. 候选池筛选
   基于公开 Benchmark + 供应商资质,筛出 3-5 个候选模型/层级组合

3. 评估集设计
   用真实业务分布抽样 100-300 条,覆盖典型 case 和已知的长尾 case

4. 离线评测
   跑候选模型,人工/LLM-judge 双重打分,同时记录延迟和 token 消耗

5. 成本测算
   用llm-cost-101.md 的模板,按候选模型分别测算规模化后的月成本

6. 影子测试/小流量 A/B
   选出 Top 1-2 候选,在真实流量上小比例验证核心业务指标

7. 上线与监控
   设定效果/成本/延迟的监控阈值,定期(建议每季度)复评——模型和价格都在持续变化
```

## 九、和算法工程师的分工边界

选型不是 PM 一个人的工作,明确分工能减少来回拉扯:

| 事项 | PM 该做的 | 该交给算法工程师的 |
|------|-----------|---------------------|
| 定义"好"的标准 | 主导:业务目标、用户体验标准、效果底线 | 参与:补充技术可行性意见 |
| 评估集设计 | 主导:样本来源、覆盖场景、优先级 | 协作:统计方法、评测工具搭建 |
| 模型/参数调优 | 不该管:Prompt 底层细节、模型超参数、推理优化 | 主导 |
| 成本估算 | 主导:业务侧参数假设(调用量、渗透率) | 协作:单价、推理优化后的实际成本 |
| 自建可行性 | 参与:业务规模判断、ROI 测算 | 主导:技术选型、部署方案、运维评估 |
| 上线监控指标 | 主导:业务指标(满意度、转化) | 协作:技术指标(延迟、错误率、漂移检测) |

**一句话原则**:PM 该对"要什么效果、能接受什么代价"有清晰判断,不该替算法工程师决定"怎么实现"。把决策权放在正确的人身上,选型才能又快又准。

## 十、私有化:真需求还是谈判筹码

> **补充于 2026-08**：与第七节互补——那里算己方 TCO,这里做**客户侧需求甄别**。合同条款须法务确认;不确定处标「需法务」。

客户说「能不能私有化 / 专有云 / 专属实例」,这句话里至少混着三档形态。混谈会把工程按最重方案开工、商务按最轻方案报价。

### 先对齐「私有化」指哪一档

| 形态 | 大致含义 | 对你方工程的冲击 |
|------|----------|------------------|
| 公有 API + 合同约束 | 数据默认不用于训练、留存/审计可控(见文末厂商企业隐私与数据控制页) | 低:合同与平台配置为主 |
| 专有云 / VPC 私网接入 | 流量走客户或云租户私网,模型仍由供应商托管 | 中:网络、权限、专区联调 |
| 客户机房 / 内网自托管权重 | 模型与推理栈落在客户边界内 | 高:交付、升级、联调、值班全变重 |

口头「私有化」经常只要第一、二档;第三档才是「权重进内网」。先写进纪要再评估投入。

### 真约束 vs 谈判筹码

| 信号 | 更像真约束 | 更像谈判筹码 |
|------|------------|--------------|
| 监管 / 合同 | 有明文驻留、等保、行业专规,或采购清单强制内网部署 | 口头「集团都要求」,拿不出条款编号 |
| 数据敏感度 | 能指出禁止出境/禁止进第三方推理的字段分级 | 演示可脱敏,生产数据路径未定义 |
| 用量与经济账 | 稳态调用用[成本测算模板](llm-cost-101.md)算完后,API 长期高于自建 TCO(含 GPU+推理人力) | 量级说不清,却要求「按私有化能力报价再砍 API」 |
| 预算与人力 | 有 GPU/运维编制与 capex 口径 | 「私有化但预算按公有 API」 |
| 时间线 | 允许数月部署与验收 | 「下周签约就要专有部署」且无过渡方案 |
| 替代方案态度 | 接受 VPC/专区/企业 API「不训练+驻留」作等价 | 咬定必须自托管权重,无视效果与版本滞后 |

### 售前 checklist(五问)

1. 二选一时:接受「专有云/VPC + 零训练承诺」还是必须「权重进机房」?答不出 → 先别开第三档评估。
2. 哪几类数据绝对不能出域?有没有现成分级文档?(训练数据红线见[数据合规](../data-annotation/data-compliance.md))
3. 预估日/月 token 与峰值?没有数 → 先 API PoC 量分布再谈自建。
4. 上线后模型升级谁审批、多久一次?「永远锁版本」须计入维护成本。
5. 预算是否含客户侧 GPU/专线/安全审计?

**回应策略**:真约束 → 走第七节 TCO + 第五节合规一票否决,分阶段交付(先 VPC,再按需内网)。筹码型 → 用三档对照表讲清差异与报价结构,把谈判拉回效果/延迟/成本,勿用工程承诺换商务折扣。选型会把「合规硬约束 vs 商务偏好」写成两栏。

## 十一、每客户一模型分支:何时该说「不」

> **补充于 2026-08**：此处「分支」指按客户拆开的**模型产物**(独立微调权重、长期分叉的 Serving/主干 Prompt 链),不是普通功能开关。

大客户常提「用我们的数据单独训一版」。短期像贴身服务,长期是分支爆炸:评测集×N、回归×N、事故无法统一热修、数据隔离一旦失效即合规事件。

| 更该坚持共用主干 | 更可接受独立分支 |
|------------------|------------------|
| 差异主要在话术、字段、工作流 | 数据分布、标签体系、合规域截然不同 |
| 可用 Prompt / RAG / 工具配置解决 | 共用模型在离线评测上系统性达不到及格线 |
| 客户要的是「专属感」而非可测效果差 | 合同明确专属权重与独立运维预算 |
| 团队没有按分支做回归与值班的人力 | 有明确 sunset:合并回主干的条件与日期 |

### 说「不」的时机与替代路径

同时满足越多,越应拒绝独立权重分支:需求仅该客户且无法抽象成租户配置;维护成本随分支数线性涨而非随 DAU;配置层(Prompt/检索/工具/路由)已能覆盖;客户不愿为专属回归与审计付费。

按侵入性从低到高给替代方案,而不是只拒绝:

1. **租户配置**:系统 Prompt、语气、禁用工具、输出 schema——配置中心下发。
2. **知识与权限隔离**:每客户独立索引/ACL,模型共用。
3. **轻量适配**:若必须上适配器,约定可合并回主线的周期与验收集。
4. **专属 Serving 副本**(同一权重、隔离部署):满足驻留与性能隔离,仍共用模型产物。
5. **真·独立微调分支**:仅当评测证明配置层不可解,且写入退出/合并条款。

默认「一个主干 + 租户配置」;开分支时强制写清:谁出评测集、谁付回归成本、何时合并或下线。路由与缓存失败模式见[降本手段盘点](cost-optimization.md);单位任务成本见[成本测算入门](llm-cost-101.md)。对外可见替代路径还可含专属工作流、专属人工复核队列。

## 十二、开源追上后:哪些模块从 API 迁本地

> **补充于 2026-08**：开源/开权模型在部分任务上逼近闭源旗舰、单位推理成本下降时,问题不是 All-in 本地,而是**按模块迁移**。「成本降 N 倍」不作行业红线;单价以[成本测算入门](llm-cost-101.md)与官方页为准。

### 迁移前四门闩

1. **效果**:自有评估集对比,不以公开榜单代替业务分(第二节)。
2. **TCO**:本地计入 GPU(含闲置)、推理工程、值班、升级回归;API 侧先吃满缓存/Batch/路由(见[降本手段](cost-optimization.md))。
3. **工程就绪**:稳定 Serving、观测、回滚,以及一键 fallback 到 API 的网关。
4. **合规**:本地化解决数据边界,不自动免除内容安全与审计(第五节)。

### 四维打分 → 三类落位

| 维度 | 更倾向迁本地 | 更倾向留 API |
|------|--------------|--------------|
| 延迟敏感 | 强交互、p99 紧、怕公共队列抖动 | 异步/可 Batch |
| 数据敏感 | 内网知识、未公开业务数据、强驻留 | 已脱敏或公开域 |
| 调用量与形状 | 量大且平稳,GPU 吃得饱 | 量小或尖峰,固定成本划不来 |
| 效果天花板 | 中等难度、结构化、内部工具 | 仍需旗舰推理/长上下文/尖端多模态 |

| 落位 | 典型画像 | 动作 |
|------|----------|------|
| **优先迁本地** | 高调用 + 中等效果 + 数据或延迟敏感(内部知识问答、意图分类、批量结构化抽取) | 影子流量对齐 → 小流量切流 → API 熔断托底 |
| **必须留 API** | 低量/尖峰 + 效果要求极高(复杂多步推理、高风险决策、创意难例) | 旗舰托底;路由把简单请求剥走 |
| **混合路由** | 难度分布不均 | 本地吃主干,API 吃难例与溢出;与第六节同一套监控 |

**建议切流顺序**(先易后难):离线/批处理/内部工具 → 高频可自动验真的在线任务 → 可切分的 RAG 问答 → 最后才动开放域创作与高后果决策辅助。

每档迁移前固定四问:效果过及格线?P95 可接受?闲置 GPU 进 TCO 了吗?能否一键回切 API?效率提升可能刺激用量(Jevons)见[降本手段](cost-optimization.md)。是否「追上」必须以**业务评测集 + 当日官方定价/硬件成本**为准;保留旗舰 API 托底直至影子流量与小流量 A/B 过护栏。

客户要的「私有化」(第十节)≠ 你方主干迁本地(本节)。若客户强制内网而产品仍强依赖闭源 API,方案须写清:**可私有化的开源层 + 合规允许时的外联旗舰层**,避免口头承诺「全部同等效果本地化」。
