# 企业 AI 需求发现：先找到值得立项的任务

## 这篇文章解决什么问题

企业 AI 项目最容易从一句“大家都想要一个 Agent”开始，最后留下一个能演示、没人持续使用的原型。需求发现阶段的任务不是先挑模型，也不是把访谈意见整理成愿望清单，而是证明一项具体工作满足三个条件：有人反复承担它，现有流程存在可度量的损耗，AI 介入后能在权限和责任边界内产生可验收的改进。

本文止于**立项决策**。进入受控 PoC、生产化和组织采用后，转到[PoC 到生产与组织采用](../ai-product-operations/poc-to-production-adoption.md)；工具、状态、权限和轨迹规格转到[Agent 产品生产化](../ai-product-operations/agent-product-design.md)。

## 先修与职责边界

先修阅读是[AI 产品 PRD 怎么写](ai-prd-guide.md)（目标、范围与验收）、[模型选型决策框架](../cost-and-tech/model-selection-framework.md)（候选方案比较）和内部助手教学契约（角色、租户、状态与禁止动作）。本篇由 PM 主导需求证据、任务卡和立项建议；业务负责人确认流程与结果责任；IT/系统 owner 提供日志、接口和基线；安全/法务审核数据、权限与高风险闸门；算法/工程只在 AI 增量假设成立后评估实现，不替 PM 证明需求成立。

## 一、先把“需求”写成任务

不要从“想用大模型做什么”开始。先记录一个可观察的任务单元：

| 字段 | 要回答的问题 | 证据例子 |
|---|---|---|
| 触发 | 什么事件让任务开始？ | 新工单、合同到达、设备申请、月末对账 |
| 执行者 | 谁现在完成它？ | 岗位、团队、外包方；不要写“用户” |
| 输入 | 任务依赖哪些文件、字段和系统？ | 工单、制度版本、CRM 字段、审批状态 |
| 动作 | 人现在按什么顺序做？ | 查找、判断、填写、调用系统、请人确认 |
| 产出 | 什么对象算完成？ | 草稿、业务系统 ID、已更新记录、已发送通知 |
| 代价 | 时间、返工、等待和错误如何出现？ | 中位工时、P90 等待、返工率、升级率 |
| 责任 | 谁对最终结果负责？ | 员工、主管、IT 经办、法务或财务 |

“回答问题”通常不是任务终点。比如设备助手的任务是“读取适用制度→检查必填字段→生成申请草稿→员工确认→提交业务系统→返回申请 ID”；主管审批和设备交付属于后续业务状态，不能在需求阶段合并成“AI 完成采购”。

## 二、证据层级：事实、判断与愿望分开

访谈中常见的“每天都很痛苦”“如果自动化就能省很多人力”只能作为待验证假设。建议给每个需求建立证据卡：

| 证据级别 | 内容 | 可支持的结论 |
|---|---|---|
| A | 脱敏任务日志、业务系统记录、抽样观察 | 任务频次、耗时、失败和等待的基线 |
| B | 多名执行者的同类访谈、流程文档、培训材料 | 流程差异、例外和责任边界 |
| C | 单个主管意见、供应商演示、个人感觉 | 线索或假设，不能直接写成规模和 ROI |

每条证据都写日期、范围、分母、数据所有者和是否可复核。厂商案例、内部演算和概念验证结果要明确标为“自述”“虚构演算”或“试点”，不能升级成正式生产效果。

## 三、从流程损耗找到 AI 介入点

把现有流程画成“任务—状态—责任人—系统”的表，再标出四类损耗：

1. **检索损耗**：资料散落、版本不清、重复查找。适合问答、检索和文档抽取，但必须有来源与版本。
2. **判断损耗**：规则复杂、字段缺失、例外难分。适合建议和分类；高风险判断要保留人工确认。
3. **执行损耗**：跨系统复制、填写、路由和状态查询。适合 Agent 或确定性 Workflow，但写操作需服务端鉴权和幂等键。
4. **交接损耗**：等待主管、人工复核、补充材料和返工。适合状态可见、提醒和草稿生成，不能把“已提交”写成“已审批”。

需求发现不等于把所有损耗都交给模型。若规则稳定、错误代价高、接口明确，先做普通 Workflow；若任务需要理解非结构化材料，但最终动作确定，可采用“模型抽取 + 规则校验 + 人确认”；只有在目标、工具、停止条件和异常出口仍需动态判断时，才进入 Agent 候选。

## 四、立项评分卡

用 0–3 分评分，分数是团队比较用的工具，不是行业标准。

| 维度 | 0 分 | 3 分 | 需要的证据 |
|---|---|---|---|
| 频次与规模 | 偶发 | 高频且分布稳定 | 日/周任务量、用户数 |
| 基线损耗 | 不清楚 | 有任务级耗时、返工或等待基线 | 日志、观察、抽样 |
| 结果可验收 | “更智能” | 有明确完成对象和业务状态 | 字段、ID、状态定义 |
| 数据与权限 | 无法取得 | 来源、租户和角色清楚 | 数据清单、权限矩阵 |
| AI 增量 | 规则即可 | 理解/生成/规划能减少损耗 | 人工对照任务 |
| 风险可控 | 不可逆且无复核 | 可预览、可撤销或人审 | 风险分级、升级出口 |
| 采用条件 | 需改变大量习惯 | 可嵌入现有入口并可培训 | 入口、责任人、推广计划 |

建议把总分之外的“一票否决”单列：无法验证数据权限、没有业务系统回执、涉及付款/删除/提权却没有人工确认、无法记录轨迹，均不能仅凭高分立项。立项材料至少包含：问题陈述、目标用户与执行者、当前流程图、基线假设、候选方案比较、风险与责任、PoC 通过条件和不做清单。

## 五、示例：内部 IT 服务助手

以下为教学演算场景，未运行真实系统，也不是任何公司的数据。员工 E01 属于 tenant-A，主管 M01 和 IT 经办 IT01 同属 tenant-A；E02 属于 tenant-B，用于跨租户越权测试。

候选任务应拆为：

- A：根据生效制度版本回答问题并给出引用；
- B：生成设备申请草稿，员工预览并确认后提交，返回业务系统申请 ID；
- C：只读查询当前申请状态。

不纳入本项目：采购付款、账号提权、代员工提交、代主管审批、把已提交写成已交付。需求卡要写清 `draft → awaiting_confirmation → submitting → pending_approval` 等状态，以及同一意图的 `request_key`，避免网络重试产生重复申请。

教学口径中的 1,000 个去重任务意图、840 个契约完成和 300 元模型与工具成本均为虚构演算，不能证明稳定性能、现金节省或真实 ROI。内部工时差只能说明“账面工时成本差”，还未扣除建设、返工、治理和机会成本。

## 六、立项前材料模板

```text
【需求名称】
【触发事件与任务终点】
【执行者/受影响角色/责任人】
【当前流程】按状态写出人、系统、输入、动作、产出
【证据】来源、日期、范围、分母、可复核方式
【基线】频次、耗时、等待、返工、错误、人工介入
【AI 增量假设】理解/生成/检索/规划分别解决什么损耗
【候选方案】规则 Workflow / AI 功能 / Agent / 暂不做
【一票否决风险】数据、权限、不可逆动作、合规、责任
【PoC 通过条件】任务级结果、质量、成本、延迟、人工接管
【不做清单】明确禁止承诺的结果
【立项决定】立项 / 补证 / 暂缓；决定人和日期
```
