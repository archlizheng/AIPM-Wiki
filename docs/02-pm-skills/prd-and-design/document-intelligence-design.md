# 文档智能产品怎么设计

**层级**：进阶正课　**先修**：[上下文工程](../../01-ai-basics/prompt-engineering/context-engineering.md)、[AI 产品 PRD](ai-prd-guide.md)

文档智能不是把文件丢给模型再显示一段摘要。PM 要先定义文件从哪里来、哪一版有效、答案要引用到什么粒度，以及生成的草稿由谁确认。只要任务涉及申请、审批或对外发送，最终完成就必须落到业务系统回执和责任人身上。

## 一、先把文档任务分成四类

| 任务 | 用户要的结果 | 主要风险 | 首个验收问题 |
|---|---|---|---|
| 找答案 | 带制度版本和引用的回答 | 旧文档、来源错配 | 每个结论能否回到有效条款 |
| 提取字段 | 表格或结构化字段 | 漏字段、单位错、版面错 | 字段是否有原文位置和置信依据 |
| 生成草稿 | 可编辑申请、邮件或简报 | 越权写入、语气和事实错误 | 草稿是否能被人修改并留下版本 |
| 执行任务 | 调接口提交并返回业务 ID | 重复提交、权限绕过 | 是否先确认，再用 request_key 幂等提交 |

不要用 OCR（光学字符识别）准确率代替任务成功率。文字读对了，来源版本错了，答案仍然不能用。模型提取了字段，接口拒绝了，业务任务也没有完成。

### OCR、版面、表格和字段抽取不是同一指标

| 能力 | 解决的问题 | 典型输出 | 不能替代什么 |
|---|---|---|---|
| OCR | 图片/扫描件中的字符是否被识别 | 文字、字符框和页码 | 版面顺序、字段含义和制度适用性 |
| 版面理解 | 标题、段落、页眉页脚、阅读顺序如何组织 | 区块树、坐标和阅读顺序 | 表格单元格关系与业务校验 |
| 表格理解 | 行列、合并单元格、表头和跨页关系是否保留 | 行列结构、单元格坐标 | 字段是否满足业务规则 |
| 字段抽取 | 把原文映射成带类型和单位的业务字段 | JSON/结构化记录 | 原文证据、权限和提交回执 |

同一份文件可能 OCR 正确、版面错位、表格串行，或字段值看似合理却缺少证据。评测应分层记录错误，不能只报一个“文档准确率”。

### 可复用的字段规格与证据回链

| 字段 | 类型/单位 | 必填条件 | 原文证据要求 | 校验与缺失动作 |
|---|---|---|---|---|
| `device_model` | 字符串 | 申请任务必填 | 文档 ID、页码/条款/表格行、原文片段 | 不能从图片模糊字形猜型号，缺失则补问 |
| `delivery_location` | 地址/地点 | 提交前必填 | 用户本轮确认或授权地址源 | 变更后旧确认失效，重新确认 |
| `department` | 组织 ID | 从身份服务读取 | 身份服务回执与租户 | 不让用户任填，读取失败转 IT |
| `purpose` | 枚举+说明 | 申请任务必填 | 用户原话与规范化值 | 枚举不明时展示候选并追问 |
| `policy_version` | 版本号 | 制度问答/申请均必填 | D01 等有效文档及生效日 | 冲突时按适用规则处理，无法判定才转人工 |

证据回链示例直接使用[教学资料 D01](../../../assets/internal-service-assistant/teaching-materials.md#d01-现行设备标准)：抽取 `max_monitor_inches = 27`，证据记录为 `{document_id: D01, version: v2, clause: 第2条, effective_from: 2026-09-01}`，对应原文为“显示器默认规格上限为27英寸”。Markdown 材料用条款定位，不编造 PDF 页码或不存在的表格行。该字段只说明制度上限，不能代替用户选择的设备规格。

完整推演：E01 希望申请 27 英寸显示器，系统从 D01 提取上限并与用户规格比较，再从身份服务读取部门、向用户补问用途和地点，生成带 D01 v2 引用的草稿。若扫描测试副本把“27”识别成“21”，即便 JSON 类型正确也应判字段错误；模糊证据标为 `needs_review`，交人工复核后再形成可提交草稿。D02 是过期规则，D06 是低权威冲突源，均不能静默替换 D01/D05。

错误分类验收至少分为：字符错误（OCR 与原文不一致）、版面错误（阅读顺序/区块错）、表格错误（行列或合并单元格错）、字段错误（类型/单位/归一化错）、证据错误（无法回链或引用了失效版本）、业务错误（权限、缺字段、重复提交）。每类都要有样例、通过条件和失败出口；例如字段值正确但证据页码错误，仍应判证据层失败并进入人工复核。

## 二、来源矩阵要先于 Prompt

每份文件至少记录归属租户、标题、版本、生效日、失效日、来源人和可引用页码。制度有冲突时，优先看适用范围与生效规则。单纯按更新时间排序会把未来版本或别的部门规则误用到当前任务。

教学场景中，E01 属于 tenant-A。D01 是现行设备标准，D02 是过期标准，D03 是角色与数据域，D06 是旧 FAQ 冲突。用户问设备标准时，回答需要引用 D01 的适用条款，并说明 D02 已过期。无法判断归属或生效状态时，助手应暂停承诺，转 IT 负责人。

## 三、把用户流程写成可验收状态

```text
用户问题 → 取适用文档 → 抽取证据 → 生成答案或草稿
                    ↓
              缺资料 / 冲突 / 越权
                    ↓
               补充、暂停或转人工
```

任务 B 的状态是 `draft → awaiting_confirmation → submitting → pending_approval`。助手只能形成设备申请草稿，经员工预览确认后提交并返回业务申请 ID。主管 M01 在业务系统完成审批，`approved` 不等于设备已经交付，`fulfilled` 仍由 IT01 人工登记。管理员 ADM01 能配置系统，不默认代员工提交或代主管审批。

确认时要展示字段、适用规则、数据范围、即将发生的动作和可撤销性。员工修改关键字段后，旧确认立即失效。网络超时先用 request_key 查询原业务对象，同 key 同 payload 只建立一个申请。提交后说“已撤回”必须有业务系统回执，聊天里的停止按钮不能改变已发出的写动作。

## 四、交付物应该保留证据

| 交付物 | 最少内容 | 人的动作 |
|---|---|---|
| 问答 | 结论、引用、文档版本、适用范围 | 判断是否适用 |
| 抽取表 | 字段、原文位置、缺失标记、置信依据 | 修正字段或补文件 |
| 申请草稿 | 设备、用途、部门、申请人、制度引用 | 预览、修改、确认提交 |
| 已提交结果 | 业务申请 ID、当前状态、下一责任人 | 在业务系统跟进审批 |

“已生成”只代表文件或草稿产生。“已提交”必须有业务系统 ID。“已批准”和“已交付”必须分别读取业务状态，不能靠模型的自然语言推断。

## 五、失败态和降级

文件损坏时提示重新上传，不继续猜测。资料缺字段时列出缺什么和为何需要。来源冲突时展示冲突双方和适用条件。权限不足时说明当前身份不能执行，转给有权限的人。解析失败可降级为人工查看或只读摘要，但不能跳过确认直接写入系统。

建议先做小评测集，覆盖正常问题、过期文档、冲突 FAQ、缺字段、跨租户和重复提交。每条同时评分证据正确性、字段完整性、权限正确性、业务回执和用户是否知道下一步。

## 六、练习

请为任务 B 写一张 PRD 规格卡。至少填入输入文档、输出字段、引用要求、确认字段、禁止动作、状态变化、超时查询方式和失败出口。再用 D01、D02、D06 各写一条用例。合格标准是读者能判断助手何时回答、何时补问、何时暂停，也能分清提交、审批和交付。
