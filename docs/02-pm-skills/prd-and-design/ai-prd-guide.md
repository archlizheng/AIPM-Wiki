# AI 产品 PRD 怎么写:与传统 PRD 的核心差异

## 一句话核心差异

传统 PRD 回答的问题是"做什么、什么时候上线、交互长什么样";AI 产品的 PRD 除了这些,还必须回答一个传统 PRD 从不需要回答的问题——**"效果好到什么程度才算做完"**。这是因为传统功能是确定性的(按钮点了就跳转,规则命中就执行),而 AI 功能是概率性的(同一个问题,模型今天答对,明天可能答错)。这个本质差异,决定了 AI PRD 必须新增几个传统 PRD 里没有的章节。

关于 AI PM 和传统 PM 差异的整体认知,可先看 [AI 产品经理和传统产品经理最大的区别是什么?](../../04-interview/behavioral/ai-pm-vs-traditional-pm.md);本文聚焦到**文档层面**,回答"这些差异具体要落到 PRD 的哪些章节、怎么写"。

## 传统 PRD vs AI PRD:多出来的章节

| 传统 PRD 章节 | AI PRD 是否需要 | AI PRD 额外新增 |
|--------------|-----------------|-----------------|
| 需求背景与目标 | 需要,不变 | — |
| 用户故事 / 交互流程 | 需要,但要加"AI 判断失败时怎么办"的分支 | 兜底交互流程 |
| 功能规格(字段、状态、边界条件) | 需要,但边界条件从"参数校验"变成"能力边界" | 能力边界与不承诺清单 |
| 验收标准 | 传统 PRD 是"功能跑通即验收";AI PRD 不能这样验收 | **效果定义章节**(核心新增) |
| 上线计划 | 需要 | 数据需求与回流设计、成本预算章节 |
| 埋点与数据指标 | 需要,但要新增模型层指标 | 评测集与及格线 |
| — | — | **Prompt Spec + Eval Spec**(把效果定义落成可执行规格) |
| — | Agent / 工具型功能额外需要 | **Agent 行为边界**(可调用什么、何时必须停) |

可以看到,AI PRD 不是把传统 PRD 推倒重来,而是在原有骨架上,把"验收标准"从一句话("功能正常可用")展开成效果定义、能力边界、数据回流、成本等章节;对生成式 / Agent 功能,还要把效果定义进一步落成 **Prompt Spec + Eval Spec**,并把有副作用的自主行为写成可验收的边界。下面先拆解基础新增章节,再写规格落地与文档协作。

## 一、效果定义章节:怎么写

这是 AI PRD 与传统 PRD 最大的分野。传统功能的验收是二元的(能用/不能用),AI 功能的验收是一个**分布**——你要先定义"够好"是什么样子,再证明模型/系统达到了这个水位。

一个完整的效果定义章节,至少要包含三块:

### 1. 目标指标(要分层,不能只写一个"准确率")

| 指标层级 | 举例 | 谁来看 |
|---------|------|--------|
| 模型层指标 | 准确率、召回率、BLEU/ROUGE、幻觉率 | 算法团队日常调优 |
| 产品层指标 | 任务完成率、人工介入率、用户采纳率(是否直接使用 AI 输出而不修改) | PM 判断功能是否达标 |
| 业务层指标 | 留存、转化、人效节省、投诉率 | 老板判断这个功能值不值得做 |

三层指标要写清楚**因果链条**假设,例如:"模型准确率从 85% 提到 92% → 人工复核率从 40% 下降到 15% → 客服人效提升 20%"。这条链条本身就是需要在效果定义章节里明确写出、后续验证的假设,而不是想当然。

### 2. 评测集(测试集从哪来、怎么维护)

- **来源**:历史真实数据(优先)、人工构造的边界 case、竞品/业界公开 benchmark(仅作参考,不能替代业务数据)
- **规模与代表性**:至少覆盖高频场景 + 长尾困难场景 + 已知的历史 bad case;避免"测试集全是简单题"导致的虚假高分
- **标注标准**:谁来定"这个回答算对";主观任务(如文案生成)要写清打分维度和评分细则,而不是"看着还行"
- **更新机制**:评测集不是一次性交付物,业务变化、新 bad case 出现后要迭代;写清楚"谁负责评测集的持续维护"

评测集的具体建设方法论,见 [从零建设评测集](../model-evaluation/build-your-eval-set.md);本节只要求 PRD 写清来源、覆盖与维护责任,字段级 Eval Spec 见[第五节](#五把效果定义落成-prompt-spec--eval-spec)。

### 3. 及格线(Pass Bar):上线前必须明确的数字

及格线要写成可验证的具体数字,而不是"效果要好"这种无法验收的话。例如:

- 核心场景准确率 ≥ 90%,且 P0 高风险场景(如涉及金额、合规)准确率 ≥ 99%
- 幻觉率(编造事实的比例)≤ 2%
- 人工介入率(转人工/拒答比例)首月 ≤ 30%,并有季度下降计划
- P95 响应延迟 ≤ 3 秒

**及格线要区分"上线线"和"目标线"**:上线线是不达标就不能上线的红线,目标线是长期优化方向。两条线混为一谈,是很多 AI 项目"效果不够也硬上"的根源——这也是 [AI 产品如何判断 PMF、如何冷启动、兜底策略怎么设计?](../../04-interview/product-design/ai-product-pmf-coldstart-fallback.md) 里提到的典型踩坑场景。

## 二、能力边界与不承诺清单

传统 PRD 的"功能边界"写的是参数范围(如"最多上传 10 张图");AI PRD 的"能力边界"写的是**这个功能不擅长、甚至不该用来做什么**。这一节最容易被忽略,却是防止用户预期跑偏、防止业务方"既要又要"的关键武器。

建议按下面的结构写:

| 分类 | 示例 |
|------|------|
| 明确支持的场景 | "支持中文电商退换货政策问答" |
| 明确不支持的场景 | "不支持法律纠纷判定,涉及此类问题一律转人工" |
| 已知的失败模式 | "对多轮嵌套条件(如'如果A且不是B,除非C')准确率会显著下降" |
| 不承诺的效果 | "不保证每次回答完全一致(温度参数导致的随机性)" |
| 风险场景的强制阻断 | "涉及金额修改、账户注销,AI 只能建议,不能自动执行" |

这一节本质上是在做"提前透露局限性",避免上线后被用户投诉"说好的智能客服怎么这都不会"。这个思路可以直接类比 Anthropic、OpenAI 发布模型时的 **System Card**(系统卡)——下文详细展开。

> **和后文的分工**:本节回答的是"这功能擅长 / 不擅长什么"(能力与预期);若功能会**调用工具、改外部状态**,还要另写 [Agent 行为边界](#六agent-行为边界怎么写进-prd)——那是"允许自主做什么、做到哪必须停",不要和能力边界混成一张空表。

## 三、数据需求与回流设计

AI 功能上线不是终点,而是"数据飞轮"的起点。这一节要写清楚三件事:

1. **冷启动数据从哪来**:历史日志、人工标注、专家写的种子数据、第三方数据采购——分别写明来源、数量级、质量把控方式。
2. **线上数据怎么回流**:用户的每一次点赞/点踩/编辑/转人工,都是潜在的训练/评测信号,要在 PRD 里明确"这些行为数据流向哪个系统、多久处理一次、谁负责看 bad case"。
3. **数据合规红线**:哪些用户数据可以用于模型迭代,是否需要脱敏,是否需要用户授权——这条不写清楚,后期极易埋雷。

具体的数据标注规范和冷启动方法论,见 [data-annotation/](../data-annotation/README.md) 板块。

## 四、成本预算章节

传统 SaaS 功能上线后,多一个用户的边际成本趋近于零;AI 功能不同,**每一次用户请求都在真金白银地花钱**(token 消耗)。这一节至少要写清楚:

| 成本项 | 说明 |
|--------|------|
| 单次调用成本 | 按预估的输入/输出 token 量 × 模型单价估算 |
| 并发/规模化成本 | DAU × 人均调用次数 × 单次成本,给出月度总成本估算 |
| 成本上限与告警 | 超过预算阈值时是否自动降级到更便宜的模型或规则兜底 |
| 降本路线图 | 缓存高频问题、小模型分流简单任务、按需微调替代长 Prompt 等 |

成本测算的详细方法,可参考 [cost-and-tech/](../cost-and-tech/README.md) 板块,以及面试题 [某功能接入大模型后成本涨了 10 倍,如何降本?](../../04-interview/case-analysis/reduce-llm-cost-10x.md) 中的成本拆解框架。

## 五、把效果定义落成 Prompt Spec + Eval Spec

前面的[效果定义](#一效果定义章节怎么写)回答的是"好到什么程度才算做完"(指标、评测集来源、及格线)。落到工程协作时,还差一层:**这些要求如何变成研发每天能跑、能回归的规格?** 行业里常把这两份配套规格叫做 **Prompt Spec** 与 **Eval Spec**——它们不是替代背景、用户故事、数据与成本等章节,而是把"概率性验收"从形容词改成可执行合同。

> **事实**:Anthropic 平台文档把"先定义成功标准、再建评测"作为模型迭代闭环的起点;其工程文章指出,早期把产品要求写成评测任务,能检验需求是否足够具体,远比事后从线上系统反推成功标准便宜,并建议把评测当作与单元测试同级的常规产品工件。见文末参考资料。
>
> **建议**:可以说"验收靠 Eval",但不必宣布"PRD 已死";缺的是把效果定义拆成 Prompt Spec + Eval Spec,背景、流程、数据与成本章节仍然要有。

### 1. 两份规格各自回答什么

| 规格 | 回答的问题 | 典型内容(写什么) | 不在这里写什么 |
|------|------------|------------------|----------------|
| **Prompt Spec** | 模型在目标场景下应如何表现? | 角色/语气、任务目标、输入约束、必须遵守的输出格式、拒答与转人工策略、正反例(好输出 / 坏输出)、变量与上下文从哪注入 | 最终线上字符串的每一个逗号;模型选型比价;基建部署细节 |
| **Eval Spec** | 怎么证明表现达标? | 评测维度与 rubric、用例构成(典型/边界/对抗)、评分方式(规则 / 人工 / LLM-as-Judge)、**上线线 vs 目标线**、回归触发条件(改 Prompt / 换模型 / 改工具必跑) | 评测平台选型长文;指标因果链的完整业务叙事(那是效果定义章节的事) |

两者必须成对出现:**没有 Eval Spec 的 Prompt Spec 只是愿望清单;没有 Prompt Spec 约束的 Eval Spec 容易测到"碰巧好看"的偶然输出**。评测集怎么建、rubric 怎么写,方法论见 [从零建设评测集](../model-evaluation/build-your-eval-set.md);Prompt 如何版本化、改一词如何强制回归,见 [系统提示词设计与 Prompt 工程化](../../01-ai-basics/prompt-engineering/system-prompt-and-prompt-ops.md)。本节只约定 PRD 里要交付什么字段。

### 2. 和「效果定义」怎么衔接(避免写两遍)

| 效果定义里已有的 | Prompt / Eval Spec 里要补成可执行的 |
|------------------|-------------------------------------|
| 模型层 / 产品层 / 业务层指标与因果假设 | Eval Spec 指定**每条指标对应哪类用例、怎么打分、谁签字** |
| 评测集来源与更新机制 | Eval Spec 给出**首发集规模、持有集(held-out)、回流入口** |
| 上线线 / 目标线数字 | Eval Spec 写成**可自动或半自动判定的门禁**(含一票否决项) |
| — | Prompt Spec 把"能力边界 / 兜底话术"落成**系统层必须遵守的约束与示例** |

写的时候用链接引用上一节的指标表,不要在 Prompt Spec 里再抄一遍"留存提升 XX%"这类业务叙事。

### 3. 最小可交付字段清单

**Prompt Spec(最小集)**

- 场景与用户目标(一句话)
- 系统层身份、语气、能力边界(指向[能力边界清单](#二能力边界与不承诺清单))
- 输入:允许的字段 / 上下文来源;禁止或需脱敏的内容
- 输出:格式、必含字段、长度或结构约束;失败时的固定话术
- 正反例各若干条(足以校准"好/坏",不必上百)
- 变更规则:谁可改、改后必跑哪份 Eval、灰度与回滚入口

**Eval Spec(最小集)**

- 用例分层:典型 / 边界 / 高风险(比例按业务风险调,方法见评测集正课)
- 每条用例的判定方式与及格定义
- 与产品层指标的映射(例如"采纳率"对应哪些隐式信号,离线测什么代理指标)
- 门禁:上线红线、一票否决(安全/合规)、目标线
- 回归策略:何种变更触发全量 / 冒烟;失败时阻断合并还是仅告警

Agent 类任务还要在 Eval Spec 里区分**最终结果**与**轨迹**(是否越权调用工具、是否跳过确认)——评测设计细节见 [Agent 评测与可观测性](../ai-product-operations/agent-evaluation-and-observability.md),PRD 侧至少要写明"轨迹类失败是否一票否决"。

## 六、Agent 行为边界怎么写进 PRD

[能力边界](#二能力边界与不承诺清单)管的是"答什么 / 不答什么";**Agent 行为边界**管的是"可以动什么、动到哪必须停"。有工具调用、会改工单/邮件/配置/资金时,缺这一节等于把授权范围交给模型临场发挥。

生产化侧的任务卡、工具契约、状态机、风险分级,正课已写在 [Agent 产品生产化](../ai-product-operations/agent-product-design.md);交互侧的确认、进度、可撤销见 [Agentic UX 与信任校准](agentic-ux-and-trust-calibration.md)。PRD 不需要重复整份状态机,但必须把**团队共同认可的授权合同**写进可验收条目。

### 1. PRD 里建议固定的六块

| 块 | 写成可验收的样子 |
|----|------------------|
| 任务目标与完成证据 | 完成不等于模型说"好了";写清工具返回、业务校验或人确认中的哪几条必须满足 |
| 允许的工具 / 资源范围 | 白名单:工具名、读写级别、租户与数据范围;黑名单单独列出 |
| 风险分级与默认策略 | 只读可自动;可逆写入要可预览/可撤销;付款、删除、外发、改权限等默认**先确认** |
| 必须停下来的节点 | 金额阈值、批量上限、置信度不足、策略冲突、预算用尽——每条对应唯一下一步 |
| 失败与降级出口 | 重试 / 降级规则 / 转人工 / 暂停;禁止"静默继续烧额度" |
| 预算上限 | 模型调用轮数、工具次数、时延、费用——触顶即 `blocked` 或交接 |

### 2. 写法对照(抽象 vs 可验收)

| 弱写法 | 可验收写法 |
|--------|------------|
| "高风险操作要小心" | "单笔 ≥ ¥X 或批量 ≥ N 条的写操作:展示对象/范围/后果后,当前用户确认才执行" |
| "可以调用内部 API" | "仅 `ticket.read` / `ticket.draft_reply`;禁止 `ticket.close`、`refund.create`" |
| "失败就重试" | "仅对幂等只读超时重试 ≤ 2 次;非幂等写操作不自动重试,进入人工确认" |
| "注意成本" | "单任务模型调用 ≤ 8 轮或费用 ≤ ¥Y,先到先停,并向用户说明已完成与未完成项" |

### 3. 和 Prompt Spec / Eval Spec 的咬合

- **Prompt Spec**:用自然语言重申"不得绕过确认、不得扩大工具范围",但**真正的硬边界在工具服务端鉴权与产品状态机**,不能只写在 Prompt 里。
- **Eval Spec**:准备"诱导越权 / 跳过确认 / 预算耗尽"类用例;轨迹违规可设为一票否决。
- **能力边界清单**:继续写清对用户承诺的场景范围;行为边界写清对系统动作的授权——两张表并存。

## 七、PRD 里该不该写 Prompt?

结论先说:**该写"行为合同",不必把线上最终 Prompt 全文钉死在 PRD 里;写了也不等于研发不用做设计。**

| 做法 | 适用 | 风险 |
|------|------|------|
| PRD 只写业务目标,Prompt 全扔给研发 | 探索期、一人全栈原型 | 验收口径漂移,"感觉能用"就上线 |
| PRD 粘贴一整段最终 System Prompt | 合规要求留痕、强监管话术 | 文档与代码双份真相;改一个词要改 PRD,迭代变慢 |
| **推荐**:PRD / Prompt Spec 写约束、格式、正反例与变更门禁;可附**示例 Prompt**标明非最终实现 | 大多数正式项目 | 需约定所有权:谁改 Prompt、谁维护 Eval |

### 分工建议

| 角色 | 对 Prompt 相关交付的责任 |
|------|--------------------------|
| PM | 定义场景、边界、正反例、Eval 门禁、灰度与回滚条件;审"行为是否符合产品合同" |
| 研发 / 算法 | 上下文拼装、工具 Schema、检索与记忆策略、Prompt 版本落地、性能与成本实现 |
| 设计 / UX | 不确定态、确认态、进度与失败话术(尤其 Agent);不只是"气泡长什么样" |

因此:**PRD 里写了 Prompt Spec,不取消交互设计,也不取消工程上的 Context / 工具设计**——它只是把"系统在目标场景下应如何表现"写成可评测的说明书。版本管理、灰度、回归流程仍按 [Prompt 工程化](../../01-ai-basics/prompt-engineering/system-prompt-and-prompt-ops.md) 执行;PRD 负责点名这些门禁存在,而不是替代工具链。

## 八、AI 需求文档该写到多细?

粒度的目标不是"越细越好",而是:**开发按文档做出来的行为分布,能被同一份 Eval Spec 判定为通过或失败**。写粗了,团队用直觉填洞;写细到实现细节,PM 变成影子工程师,且跟不上每周的 Prompt 迭代。

### 1. 粒度标尺

| 层级 | 写到什么程度 | 谁主要维护 |
|------|--------------|------------|
| L1 意图 | 用户目标、为何用 AI、成功的业务样子 | PM |
| L2 行为合同 | 能力边界、Agent 授权、输入输出约束、正反例 | PM + 算法 |
| L3 可执行规格 | Prompt Spec 字段 + Eval Spec 门禁 + 回流与成本红线 | PM 牵头,工程可执行 |
| L4 实现细节 | 具体 Prompt 字符串、检索参数、服务拆分 | 工程 / 算法(PRD 用链接指向仓库/配置,不内嵌双份) |

正式排期的 AI 功能,PRD 至少稳在 **L2–L3**;L4 放进版本库,用链接引用。

### 2. 写粗了会乱做时,补这四样(而不是补成长篇小说)

1. **补正反例**:比再写三段形容词更有效——各 5–10 条真实或构造 case,标明期望动作(答 / 拒 / 转人工 / 先确认)。
2. **补一票否决**:安全、合规、越权、不可逆误操作——写进 Eval Spec 门禁。
3. **补完成证据**:尤其 Agent,"完成"依赖工具回执还是人审,写死。
4. **补变更门禁**:谁能改 Prompt / 工具权限;改完必须跑哪份回归。

若上述四样齐全而实现仍漂移,问题多半在**所有权与门禁未执行**,而不是文档字数不够。

### 3. 和模板的关系

下文模板把 Prompt Spec、Eval Spec、Agent 行为边界收成独立小节,便于评审勾选;小功能可把 Prompt Spec 嵌在效果定义下,但**Eval 门禁与高风险行为边界不要省略**。

## 类比:向 Model Card / System Card 学"效果怎么披露"

Anthropic 和 OpenAI 为部分模型和系统公开 **System Card**（系统卡）。它与 **Model Card**（模型卡）的范围不完全相同，不能把两者理解为简单的新旧名称。以 2026 年 Anthropic 发布的 Claude Sonnet 5 System Card、Claude Opus 4.6/4.8 System Card,以及 OpenAI 的 GPT-5 系列 System Card 为例,它们的公开结构通常包含:能力评测结果(在哪些 benchmark 和"生产场景真实困难案例"上的表现)、安全评估(红队测试、滥用风险测试)、已知局限性、以及负责任部署决策(在什么条件下才允许开放什么能力)。

这套披露逻辑,和 AI PRD 里"效果定义 + 能力边界"两节想解决的问题几乎一模一样:**不是等用户发现模型不会什么,而是主动、具体地讲清楚模型能做什么、不能做什么、在什么水位上是可信的**。区别在于系统卡面向的是外部世界和监管,AI PRD 面向的是内部团队和验收流程,但"用具体数字和具体场景说话,而不是用形容词"这条原则是相通的。写效果定义章节卡壳时,不妨反问自己:如果要把这个功能的效果写成一份对外的"系统卡",你有没有底气写出具体的评测结果和边界说明?写不出来,往往说明效果定义还不够扎实。

## AI PRD 章节模板(可直接套用)

```markdown
# [功能名称] PRD

## 1. 背景与目标
- 要解决的业务问题
- 为什么用 AI 而不是规则/人工(参考:这个问题是否适合用 AI 解决)

## 2. 用户故事与交互流程
- 正常路径(AI 回答符合预期)
- 异常路径(AI 不确定/答错/超出能力边界时的兜底流程)

## 3. 效果定义(AI PRD 核心新增)
- 3.1 目标指标(模型层 / 产品层 / 业务层,及三者的因果假设)
- 3.2 评测集(来源、规模、标注标准、更新机制)
- 3.3 及格线(上线红线 vs 长期目标线,给出具体数字)

## 3a. Prompt Spec(行为合同,可与 3 合并)
- 角色 / 语气 / 输入约束 / 输出格式
- 拒答、转人工、失败话术
- 正反例;变更所有权与回归门禁
- (示例 Prompt 可附录,标明非最终实现)

## 3b. Eval Spec(可执行验收)
- 用例分层与评分方式 / rubric
- 上线线、目标线、一票否决
- 与产品层指标的映射;何种变更触发回归
- Agent:是否评轨迹、越权是否否决

## 4. 能力边界与不承诺清单
- 明确支持的场景
- 明确不支持的场景
- 已知失败模式
- 不承诺的效果
- 高风险场景的强制阻断规则

## 4a. Agent 行为边界(有工具 / 副作用时必填)
- 完成证据;工具白名单与权限
- 风险分级与确认节点
- 失败出口与任务预算上限

## 5. 数据需求与回流设计
- 冷启动数据来源
- 线上数据回流机制(埋点、bad case 收集、标注分发)
- 数据合规红线

## 6. 成本预算
- 单次调用成本估算
- 规模化后的月度成本
- 成本告警阈值与降级策略

## 7. 兜底与风险
- 置信度分级与降级链路(详见交互设计文档)
- 人工介入触发条件

## 8. 上线计划与灰度策略
- 灰度范围、观察周期、回滚条件
- Prompt / 模型 / 工具权限变更的灰度与回滚

## 9. 后续迭代计划
- 数据飞轮:下一轮优化的数据来源和验证方式
- Eval 集扩充与"评测饱和"处理
```

## 九、把多模态和办公 Agent 写进同一份 PRD

当输入包含文档、语音或屏幕，PRD 需要新增三张表。第一张表说明每个来源是否由用户选择、管理员启用或系统默认读取。第二张表说明输出是回答、草稿还是已经写入业务系统。第三张表说明打断、确认、取消和重试分别影响哪一个状态。

| 需求 | PRD 要写什么 | 不能用什么替代 |
|---|---|---|
| 文档理解 | 版本、生效日、引用位置、缺失字段 | OCR 综合分 |
| 实时语音 | 监听、停顿、打断、转写和首个可听片段 | 支持语音 |
| Computer Use | 适用工具、账号身份、截图回执、沙箱和接管 | 模型可以操作电脑 |
| 办公交付 | 文件类型、可编辑性、来源、发送前审核 | 自动生成报告 |

OpenAI GPT-Live 的官方材料把全双工媒体路径和后台搜索、推理、工具调用分开。Google Workspace 在 2026-09-09 公告中展示了从 Chat、Drive、Docs、Gmail 生成 Slides、Sheets、Brief、邮件和 Deck 的路径。它们说明 AI PRD 的验收对象已经包含持续会话、跨应用来源和可编辑交付物，但不代表每个账号都已获得相同能力。

## 十、提交前的状态和证据检查

写完功能后逐项回答四个问题。谁发起了动作，谁拥有业务权限，系统返回了什么证据，用户下一步还要做什么。任务 B 的“已提交”只能由业务申请 ID 证明，不能由语音播报或页面动画证明。用户停止播报也不能撤回已发请求。

把这些答案放入 Eval Spec。至少加入缺资料、过期文档、冲突来源、跨租户读取、重复提交、审批变化和接口超时。没有真实数据时使用虚构材料，并明确这只是教学演算。
