# 兜底、反馈与预期管理:AI 产品的交互设计三件套

## 为什么这三件事要放在一起说

AI 产品的交互设计,本质上是在回答同一个问题的三个不同侧面:

1. **兜底**:模型这次答不好,产品怎么接住,不让用户体验直接摔到地上?
2. **反馈**:用户觉得答得不好(或好),这个信号怎么被产品捕捉,喂回给下一次迭代?
3. **预期管理**:从一开始就让用户对"AI 可能出错"有心理准备,减少"答不好"造成的信任损耗。

三者是一个闭环:预期管理降低了兜底触发时的用户挫败感;兜底触发本身就是一种反馈信号;反馈机制收集到的 bad case,又反过来优化兜底策略的判断阈值。本文按这三条线展开,并结合 ChatGPT、Claude、Gemini 在 2026 年的真实产品设计逐一验证。

关于 PRD 文档层面如何写清楚效果指标、能力边界,见 [AI 产品 PRD 怎么写:与传统 PRD 的核心差异](ai-prd-guide.md);冷启动阶段兜底策略的分层框架(L1 生成层到 L4 系统层),已在 [AI 产品如何判断 PMF、如何冷启动、兜底策略怎么设计?](../../04-interview/product-design/ai-product-pmf-coldstart-fallback.md) 中给出,本文不重复展开分层表格,而是聚焦**交互设计层面**要落的具体控件和话术。

## 一、兜底设计:模型答不好时,产品怎么接住

### 1. 置信度分级要先于交互设计存在

兜底设计的前提是产品/模型能给出某种"这次答案有多可信"的信号,常见来源:

| 信号来源 | 说明 |
|---------|------|
| 模型自身的置信度/概率分布 | 如生成 token 的 log-probability,或让模型自评"我有多确定" |
| 检索质量信号 | RAG 场景下,检索到的资料相关度是否足够高(见 [什么是 RAG](../../01-ai-basics/llm/what-is-rag.md)) |
| 规则/业务信号 | 是否命中已知的高风险关键词(金额、合规、医疗) |
| 历史准确率 | 该问题类型在评测集上的历史准确率,作为先验 |

这些信号本身不是终点,而是决定"接下来该走哪条交互路径"的开关。

### 2. 拒答话术:怎么说"不知道"才不难看

直接说"我不知道"会显得产品很弱;完全不说又会制造幻觉风险。好的拒答设计通常包含三层:承认边界 + 给出替代路径 + 保留追问空间。例如:

- 差:"抱歉,我无法回答这个问题。"(用户下一步不知道该干嘛)
- 好:"这个问题涉及具体的账户操作,我暂时无法确认,已经为你转接人工专员,预计 2 分钟内响应;如果你想先自己查,可以看看《账户安全说明》。"

这也是 [AI 产品如何判断 PMF、如何冷启动、兜底策略怎么设计?](../../04-interview/product-design/ai-product-pmf-coldstart-fallback.md) 中提到的"透明标注'为您转专员',在擅长的子场景打'秒回'"的具体落地方式。

### 3. 降级链路:从"AI 独立解决"到"系统兜底"的完整路径

一个成熟的对话产品,交互上通常有以下几级降级路径,层层兜底:

```
AI 直接回答(高置信度)
   ↓ 置信度不足
AI 追问澄清("你是想问 A 还是 B?")
   ↓ 仍不确定
AI 明确说明局限 + 提供相关资料链接
   ↓ 涉及高风险操作
强制转人工 / 需要用户二次确认
   ↓ 系统级故障(模型超时、宕机)
规则模板兜底 + 排队提示,保证"至少不空白"
```

每一级降级都需要在交互上有明确的视觉/文案区分,让用户清楚"现在是 AI 在答,还是转到别的机制了",这本身也是预期管理的一部分。

## 二、对话类交互范式:流式输出、打断、重新生成、引用溯源

这一部分的设计范式,主流对话产品在 2026 年已经趋于收敛,可以直接参考成熟做法。

### 1. 流式输出与打断(Stop Generating)

ChatGPT、Claude、Gemini 都采用"边生成边显示"的流式输出,而不是等模型全部生成完再一次性展示——这是降低用户等待焦虑的基本设计。配套的是"停止生成"(Stop Generating)按钮:模型输出过程中,用户可以随时打断,拿到已生成的部分内容,而不需要等待完整回答或整个作废重来。OpenAI 官方帮助文档明确把"点击 Stop generating,再点击 Regenerate 重试"作为标准操作路径。

### 2. 重新生成(Regenerate)与编辑消息(Edit)

- **重新生成**:用户对已有回答不满意时,可以要求模型基于同一个问题重新作答一次,而不需要重新打字。Claude.ai 官方帮助文档描述的操作路径是:打开对话 → 点击 Retry → 选择"不做改动直接重试"→ 得到新回答。
- **编辑消息**:用户可以修改自己之前发的问题,模型基于修改后的版本重新回答,原分支仍然保留可以切回——这本质上是一种轻量级的"对话分支"能力,让用户可以在同一个话题下尝试不同的提问方式,而不用开一个新对话。

这两个控件解决的是同一个产品问题:**AI 输出不满意时,重来的成本要足够低**,否则用户会直接放弃、流失。

### 3. 引用溯源(Citation):把"黑箱"变成"可核验"

引用溯源是缓解幻觉、建立信任性价比最高的设计手段之一(参考 [AI 产品的黑箱问题如何影响用户信任?](../../04-interview/basics/ai-blackbox-trust.md)),三家产品的具体做法有细节差异,值得对比着看:

| 产品 | 机制 | 具体表现 |
|------|------|----------|
| ChatGPT(Search) | 联网搜索触发后,回答中插入内联引用 | 鼠标悬停引用角标可预览来源,点击跳转原文;若未显示内联引用,可点击回答下方 "Sources" 面板查看引用列表 |
| Claude(Citations API / 原生 web_search) | 面向开发者的 Citations 功能,让模型在引用文档时返回带字符级偏移的结构化引用对象 | 保证引用内容确实来自给定文档,而非模型编造;原生联网搜索时,每条网页结果默认自带引用类型 |
| Gemini("双重核查",Double-check response) | 回答生成后,用户可点击"双重核查"用 Google 搜索交叉验证 | 用绿色高亮标出"搜索结果与回答内容相符"的陈述,橙色高亮标出"搜索结果与回答不符或未找到相关信息"的陈述,帮助用户快速判断哪些内容需要重新核实 |

三种机制的产品哲学略有不同:ChatGPT 和 Claude 更偏"生成时就带引用",Gemini 的双重核查更偏"生成后再做一次独立核验"——后者的好处是核查过程和生成过程解耦,即使模型编造了内容,只要核查环节足够独立,依然有机会被检测出来。做对话产品的引用设计时,这是一个值得参考的思路:**不要把"引用展示"和"引用是否真实"这两件事混为一谈**,后者需要工程上的保证机制,而不只是 UI 上加个角标。

## 三、反馈机制:点赞点踩之外还有什么

### 1. 主流产品怎么做显式反馈

点赞/点踩是最基础的显式反馈控件。ChatGPT 的做法是:点赞通常直接记录一个正向信号;点踩会弹出面板,要求用户具体标注问题类型(如"内容不准确""没有遵循指令"),并可选填文字说明——负反馈的"归因颗粒度"远高于正反馈。Claude.ai 类似:回答下方提供 thumbs up / thumbs down;点踩会把该轮对话分享给 Anthropic 用于改进(Team / Enterprise 可由管理员开关;用户也可在设置中管理是否愿意提供反馈)。OpenAI 官方亦把「回答下方点踩 / 使用 Report」作为替代已下线网页反馈表单的主渠道。

> **分工**:显式反馈覆盖率低、如何当指标用、如何与隐式信号配对——见 [AI 产品指标体系 · 第八节](../ai-product-operations/ai-product-metrics.md#八用户为何不点反馈低覆盖不是用户满意了)。本节只谈交互侧:按钮为何点不下去、控件怎么设计才更低摩擦。

### 2. 反馈按钮为何「点不下去」(交互视角)

答案错了,按钮明明在,用户仍不点——多数时候不是「其实满意了」,而是**交互成本高于当下任务收益**:

| 交互断点 | 用户侧感受 | 设计含义 |
|---------|------------|----------|
| 时机错位 | 正在赶任务/扫读答案,没空停下来「评价」 | 评价动作插在主路径中间,会被跳过 |
| 归因负担 | 要点踩还得想「错在哪一类」、写说明 | 必填文字/长问卷把一次点击变成一次写作 |
| 收益不可见 | 点了下次还是一样,感觉没人看 | 缺少即时确认与中长期「被用上了」的感知 |
| 控件淹没 | 👍👎 藏在滚动后、或被复制/重生成抢注意力 | 不满意时用户先点 Regenerate,反馈入口从未进入视线 |
| 隐私顾虑 | 「点了会不会把整段对话交出去训练?」 | 用途说明缺失或文案吓人,理性用户更不点 |
| 强打断 | 弹窗挡路、关不掉就继续弹 | 反馈率被刷高,信号被污染(反模式见[飞轮 KPI 化](../data-annotation/cold-start-and-data-flywheel.md#飞轮反模式)) |

一句话:**显式反馈是「高置信、低覆盖」的金标准抽样**,交互目标不是把点击率刷到很高,而是让**真的不满意、且愿意花 1 秒**的人,能几乎无脑完成一次信号投递。

### 3. 让按钮「点得下去」的交互设计清单

按「先降成本、再补收益感知」排优先级(不抄具体产品像素,只定原则):

1. **一键主路径**:👍 / 👎 默认零文案;点踩后再展开可选原因标签(芯片),文字说明永远可选。不要把「写一段话」当成进入反馈的门槛。
2. **和「不满意动作」放一起**:重生成、编辑消息、复制——用户已经在表达「不够好」时,把点踩放在同一工具条,比单独角落的幽灵按钮更容易被看见。
3. **事后轻触发,而非阅读中打断**:流式输出未结束不弹评价;可在用户完成复制/关闭会话/连续 Regenerate 后给一次**可忽略**的轻提示,禁止模态连环弹窗。
4. **即时确认**:点完立刻有「已收到,用于改进此类回答」类微文案;若会上传对话片段,用一行说明用途 + 链到设置/隐私页,降低「黑箱交出」感。
5. **质量反馈 ≠ 合规举报**:Report / 违规入口与 👎 分开(ChatGPT 即如此)——混用会让用户不敢随手点踩,也会把安全工单和效果 bad case 搅在一起。
6. **闭环可感知(轻量)**:同类问题修好后,可对曾贡献过反馈的用户给一次非打断提示(如「你反馈过的 X 类问题已优化」);这是信任与留存设计,展开见 [AI 功能留存与成功指标](../ai-product-operations/ai-feature-retention-and-success-metrics.md)。不要为刷「反馈被采纳率」而频繁打扰。
7. **A/B 只验摩擦,不验「日均反馈条数」**:对比的是点踩完成率、原因标签完整率、以及点踩后是否仍转人工——不要把弹窗强度当成成功标准。

### 4. 隐式行为:覆盖率补网,交互上不必「求用户评价」

点赞点踩触发率低时,监测面主要靠隐式行为——它们发生在主任务路径上,不额外打断:

| 隐式信号 | 交互含义(不是指标公式) |
|---------|------------------------|
| 编辑 / 大改后仍用 | 「不够好,但还有救」;入口应靠近输出区 |
| 反复重生成 | 前几次未满足;可在第 N 次后轻提示点踩(可忽略) |
| 复制 / 采纳 | 最直接的「有用」;勿在复制瞬间弹评价挡路 |
| 会话中断 / 转人工 | 体验断点;转人工前可收一条可选原因 |
| 换说法追问同一事 | 首答未真正解决 |
| Report(独立于点踩) | 合规/滥用,走审核队列,不要和效果点踩混入口 |

交互上把显式做得极轻;运营上把隐式读成改进方向——口径与编辑三维读法见指标体系[第八–九节](../ai-product-operations/ai-product-metrics.md#八用户为何不点反馈低覆盖不是用户满意了);飞轮回流见[冷启动与数据飞轮](../data-annotation/cold-start-and-data-flywheel.md)。对新的 Prompt / 模型 / 兜底阈值,用小流量 A/B 看采纳率、转人工率、留存等业务结果,而不是仅凭「感觉反馈变多了」就全量。

## 四、预期管理:让用户对"AI 会犯错"有心理准备

预期管理是三件套里最容易被忽视、却是成本最低的设计手段——它不需要改模型,只需要改文案和视觉。

### 1. AI 身份标识

用户需要清楚知道自己在和 AI 交互,而不是真人。这不仅是产品设计问题,也正在变成合规要求:欧盟《人工智能法案》(EU AI Act)已要求 AI 系统在特定场景下履行透明度和披露义务。Google 从 2026 年起在 Gemini 生成的图像中默认嵌入 SynthID 隐形水印,并上线了 SynthID Detector,允许任何人上传图片检测其是否为 AI 生成——这是"AI 标识"从"聊天界面上的一行小字"升级为"内容层面可检测水印"的信号,值得 AI 产品在设计内容溯源机制时参考。

### 2. 免责声明:管用,但不能只靠它

ChatGPT 在输入框下方长期展示"ChatGPT can make mistakes. Check important info."(ChatGPT 可能会犯错,请核查重要信息)。需要客观说明的是:已有研究显示,这类静态免责声明对用户实际核查行为的影响有限,不能指望一行小字就让用户对每条回答都保持警惕。**免责声明的正确定位是"最后一道防线",而不是主力兜底手段**——真正管用的还是前面提到的置信度分级、拒答话术和引用溯源;免责声明解决的是"万一前面几道防线都没拦住"的责任告知问题。

### 3. 能力提示:在用户提问之前,就管理好期待

比事后免责声明更有效的,是在交互设计中前置地提示能力边界:

- 首次使用引导中说明"擅长做什么、不擅长做什么"(对应 PRD 里的能力边界清单,见 [AI 产品 PRD 怎么写](ai-prd-guide.md))
- 对高风险问题在回答前主动提示"这类问题建议咨询专业人士"
- 用"建议"而非"结论"的语气呈现涉及主观判断的内容(如医疗、法律、投资类回答)
- 像 Gemini 的双重核查一样,把"这条内容我们自己核实过""这条内容需要你自己再确认"的区分,做成用户可见、可交互的产品功能,而不是藏在帮助文档里

## 小结

兜底、反馈、预期管理这三件套,本质上都是在替"模型输出的不确定性"做产品层面的翻译工作:兜底负责"这次没做好怎么办",反馈负责"怎么让下次做得更好",预期管理负责"让用户对'可能没做好'本身有心理准备"。反馈这一环在交互上常被做成「角落里的幽灵按钮」——答案错了用户也不点,不是满意,是成本高于收益;把显式反馈做得一键可完成,并把隐式行为接进飞轮,才谈得上闭环。三者任何一环缺失,都会导致同一个结果——用户对 AI 功能的信任被消耗殆尽,即便模型本身的技术指标一直在进步。
