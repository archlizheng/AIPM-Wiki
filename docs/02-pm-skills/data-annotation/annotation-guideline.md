# 标注规范怎么写:PM 写规范,标注质量就是产品质量

## 为什么这是 PM 的活儿,不是标注供应商的活儿

很多团队把"写标注规范"当成外包公司的执行细节,PM 只给一句话需求:"帮我标一下对话有没有解决用户问题"。结果拿回来的数据里,同一类对话被三个标注员标成三种结果——因为"解决问题"这四个字,每个人的理解都不一样。

标注规范的本质,是把 PM 脑子里对"好"与"坏"的判断标准,转译成标注员**不需要请示产品经理就能独立、一致地做出判断**的操作手册。规范写得好不好,直接决定了:

- 训练数据/评测集的**噪声水平**——噪声大,模型学到的是错误信号
- 标注团队(尤其外包)的**返工成本**——规范模糊,来回沟通比标注本身还费时间
- 评估结果的**可信度**——如果人工标注本身不一致,拿它当模型效果的"金标准"就是空中楼阁

一份合格的标注规范,应该让一个完全不了解产品背景的新人,读完之后能独立标注,且和资深标注员的判断高度一致。

## 标注规范的五个组成部分

| 部分 | 回答的问题 | 常见坑 |
|------|-----------|--------|
| 任务定义 | 标注员在做什么?输入是什么,输出是什么? | 只写"判断对话质量",没说清输入范围(单轮/整个会话)、输出格式 |
| 标签体系 | 有哪些标签?每个标签的准确定义是什么? | 标签之间语义重叠,比如"部分解决"和"未解决但有帮助"边界不清 |
| 正反例 | 每个标签下,典型的例子长什么样? | 只给 1-2 个例子,覆盖不了真实数据的多样性 |
| 边界裁决 | 遇到模糊情况,该怎么判? | 完全没有,标注员各自"凭感觉" |
| FAQ | 标注过程中反复出现的疑问怎么处理? | 规范定稿后从不更新,新出现的边界情况无人补充 |

下面逐一拆开讲。

**任务定义**要明确四件事:输入单元(是一整段对话,还是一条消息?)、输出格式(单选/多选/评分/自由文本?)、标注视角(站在用户的角度判断,还是站在客观结果的角度?)、以及标注对象排除范围(哪些数据不需要标,比如测试账号产生的对话)。

**标签体系**要做到"互斥且穷尽"(MECE):任意一条数据,应该有且仅有一个标签能装下它。如果发现标注员经常在两个标签之间纠结,说明标签定义本身有重叠,需要回头修改标签体系,而不是让标注员"自己把握"。

**正反例**是规范里性价比最高的部分。文字定义再精确,也不如 5-10 个真实数据示例直观。正例要覆盖"典型情况"和"容易被误判的边界情况",反例要专门挑那些"看起来像,但其实不是"的案例。

**边界裁决**是规范的核心价值所在。真实数据永远比规范复杂,一定会出现规范没预料到的情况。这部分要给出**裁决优先级**(比如"用户情绪 vs 问题是否解决,以后者为准")和**兜底原则**(比如"无法判断时统一标为'待复核',而不是标注员自己猜")。

**FAQ** 不是写完就归档的文档,而是随着标注推进持续更新的活文档。每周把标注员提出的疑难case 汇总、拍板、写入 FAQ,是质量管理的常规动作。

## 完整迷你示例:"客服对话是否解决问题"三分类

以下是一份可以直接套用的最小可行标注规范,任务是判断一通 AI 客服对话最终是否解决了用户问题。

```markdown
# 标注任务:客服对话解决状态判定(三分类)

## 1. 任务定义
- 输入:一整段用户与 AI 客服的对话(从用户第一条消息到对话结束)
- 输出:从下列三个标签中选择一个
- 视角:以用户在对话结束时的实际状态判断,而非客服态度好坏

## 2. 标签体系
| 标签 | 定义 |
|------|------|
| 已解决 | 用户的问题在对话内得到了明确、可执行的答案或处理结果,用户没有再追问同一问题 |
| 部分解决 | 用户拿到了有用信息或部分处理,但核心诉求仍未达成(如问题被受理但未处理完) |
| 未解决 | 用户没有得到有效回应,或对话中途因客服无法处理而转人工/中断 |

## 3. 正反例
### 已解决
- 例1:用户问"订单为什么还没发货",客服查询后回复"物流延误,已联系仓库,预计明天发出",用户回复"好的谢谢"→ 标"已解决"(问题有明确处理结果)
- 例2:用户问退货流程,客服给出完整步骤,用户未再追问 → 标"已解决"

### 部分解决
- 例3:用户要求退款,客服受理退款申请并告知"3-5个工作日到账",但退款尚未实际到账 → 标"部分解决"(诉求被受理,但结果未完成,不算"已解决")

### 未解决
- 例4:用户连续三次追问同一问题,客服重复相同话术未能解答 → 标"未解决"
- 例5:客服回复"该问题需要转人工处理",对话在转接前结束 → 标"未解决"

## 4. 边界裁决规则
- 优先级:是否解决用户的**核心诉求** > 客服语气是否友好 > 响应速度
- 用户在结束时说"谢谢"、"好的"等礼貌用语,不代表问题已解决,需结合上下文判断
- 若对话被用户主动中断(如未回复退出),按对话中止前的最后处理状态判定,而非默认标"未解决"
- 无法判断或存在歧义的样本,统一标记为"待复核",禁止标注员自行猜测后提交

## 5. FAQ(持续更新)
- Q:用户问了多个问题,一个解决一个没解决,怎么标?
  A:以对话中**优先级最高/最先提出**的问题为准,若产品定义了多问题拆分规则则优先拆分为多条记录分别标注
- Q:客服给错了答案,但用户没有察觉并表示满意,算解决吗?
  A:不算。本任务标注的是"客观是否解决",不是"用户主观满意度",错误答案一律标"未解决"或"部分解决"
```

这份示例可以直接作为模板,替换成你自己产品的标签体系。

## 标注团队协作:内部团队 vs 外包团队

标注规范写完之后,谁来标是另一个关键决策。内部团队和外包团队各有适用场景。

| 维度 | 内部团队 | 外包团队 |
|------|----------|----------|
| 领域理解 | 强,天然懂产品和业务背景 | 弱,依赖规范和培训,理解偏差风险高 |
| 标注成本 | 高(按人力成本计) | 低(规模化后单条成本显著下降) |
| 规模弹性 | 弱,扩容慢 | 强,可快速扩缩量 |
| 保密与合规 | 风险低,数据不出内部 | 需要签署保密协议,评估数据出境/留存风险 |
| 培训与管理成本 | 一次性投入,长期复用 | 每次换供应商/换批次都要重新培训 |
| 适合场景 | 冷启动早期、高敏感数据、需要频繁修订规范的探索阶段 | 规范已稳定、标注量大、任务相对标准化的规模化阶段 |
| 典型风险 | 人力有限,标注量跟不上业务增长 | 一致性差、责任心参差、规范理解走样 |

实践中常见的组合策略是:**内部团队先把规范打磨到稳定状态(标注一致性达标),再把标准化的部分外包扩量,内部团队专注处理外包标注不了的疑难case 和质检**。涉及用户隐私或高敏感数据时,还要评估外包供应商的数据合规资质(参见[数据合规红线](data-compliance.md))。

## 质检机制:怎么知道标注质量靠不靠谱

规范写得再好,也需要机制去验证标注员是不是真的按规范执行。三个核心手段:

**1. 交叉标注(多人标注同一批数据)**

抽取一定比例的数据(通常 5%-20%),让 2 名及以上标注员独立标注,不互相参考。这是衡量规范和标注一致性的基础数据来源。

**2. 一致性指标**

用统计指标衡量交叉标注的一致程度,而不是凭感觉判断"标得还不错":

| 指标 | 适用场景 | 简单说明 |
|------|----------|----------|
| 一致率(Percent Agreement) | 快速直观查看 | 两人标注结果相同的样本占比,但没有排除"蒙对"的可能 |
| Cohen's Kappa | 两名标注员 | 在一致率基础上扣除随机蒙对的概率,更能反映真实一致性 |
| Fleiss' Kappa | 三名及以上标注员 | Cohen's Kappa 的多人版本 |

行业经验值:Kappa 低于 0.6 通常说明规范存在歧义或标注员理解有偏差,需要先修订规范,而不是简单地加派人手重标。

**3. 抽检仲裁**

对交叉标注中出现分歧的样本,由资深标注员或 PM 本人做最终裁决(仲裁)。仲裁结果要反过来更新到规范的"边界裁决"和"FAQ"部分——质检不是终点,而是规范持续迭代的输入源。建议节奏:**每周抽检一次分歧样本,每两周更新一版规范**,直到一致性指标稳定在目标线以上。

## 常见误区

- **误区一:规范一次写完就不改了**。真实数据的复杂度会不断暴露规范的漏洞,规范应该像产品文档一样版本化管理。
- **误区二:只关注标签定义,不关注裁决优先级**。当多个判断维度冲突时(比如态度好但没解决问题),没有优先级规则,标注员只能各凭主观。
- **误区三:把质检当成一次性验收,而不是持续机制**。标注员会疲劳、会遗忘规范细节,一致性需要持续监控,不是标完就完事。
