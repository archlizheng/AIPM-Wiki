# 实践四：成本、采用与上线验收

> **层级：实践。** 先修：[评测与发布判断](internal-service-evaluation.md)、[AI产品指标体系](../ai-product-operations/ai-product-metrics.md)、[PoC到正式采用](../ai-product-operations/poc-to-production-adoption.md)。全部数字为[统一教学账本](../../../assets/internal-service-assistant/teaching-materials.md)中的假设，不代表实际试点、财务收益或用户增长。

## 一、先给“有效完成”一个分母

教学月内200名受邀员工，120名发生相关需求，100名实际使用；共发起1000个去重任务意图。重试是意图里的步骤，不另算任务。使用、去重、人工协助和W窗口均按[统一事件定义](../../../assets/internal-service-assistant/teaching-materials.md#统一事件与观察窗口)。任务类型与完成条件继承[PRD](internal-service-prd.md)：问答需要适用依据，提交需要业务ID，查询需要经授权的状态与读取时间。

| 任务 | 发起意图 | 按本任务契约完成 | 完成率 |
|---|---:|---:|---:|
| 制度问答 | 600 | 500 | 83.33% |
| 申请提交 | 300 | 250 | 83.33% |
| 状态查询 | 100 | 90 | 90% |
| 合计 | 1000 | 840 | 84% |

840个完成中，760纯自动、80在人工协助后完成；未完成160。共有140个意图触发一次人工协助，其中80完成、60仍未完成。因此纯自动完成率76%，人工介入率14%。不能将“840完成”全部宣传为自动化，也不能把转人工直接当失败或全部当成功。

申请提交的250个完成仅指已经建单。截点累计100个批准，其中40个登记交付；剩余状态仍需跟踪。批准与交付是嵌套状态，不能相加成140个“完成”。不同申请等待时间不同，100/250不应被解释成成熟队列最终通过率。

## 二、算清每个有效任务的成本

这里使用人民币统一演算，模型与工具300元是教学账单总额，不引用任何供应商API单价。实际项目应从真实版本、渠道和计量记录取数。

| 成本项 | 教学计算 | 金额 |
|---|---|---:|
| 模型与工具 | 所有意图的累计费用；含失败/重试增量60元 | 300元 |
| 基础设施 | 检索、存储、环境等教学分摊 | 100元 |
| 人工协助 | 140个意图各一次协助×3分钟÷60×60元/小时 | 420元 |
| 运营维护 | 制度维护、抽检与支持的教学分摊 | 180元 |
| 总运行成本 | 300＋100＋420＋180 | 1000元 |

每发起意图成本＝1000/1000＝1元；每有效完成意图成本＝1000/840≈1.19元。两者分别回答“服务一次需求付出多少”和“获得一个合格结果付出多少”，必须同时呈现。60元已经计入300元，不能再次相加。

内部助手的工时成本不是外部客户收入。即使供应商按credits或actions计费，你仍应按业务任务核算；一次意图可能消耗多个收费动作。

## 三、基线与敏感性：便宜不等于值得扩围

假设相同1000个意图用人工处理，每个6分钟、每小时60元，则人工基线6000元。6000−1000＝5000元只是教学账面工时成本差，隐含完成质量可比的假设。不能称“月省5000元现金”：员工薪酬未必变化，一次性开发、数据清理和额外返工还未计入。

| 变化（其他条件保持教学假设） | 新总成本 | 每有效完成意图成本 | 判断 |
|---|---:|---:|---|
| 原场景 | 1000元 | 1000/840≈1.19元 | 基准 |
| 模型与工具费翻倍 | 1300元 | 1300/840≈1.55元 | 成本上涨，仍需核对效果是否改善 |
| 每次人工协助从3分钟变6分钟 | 1420元 | 1420/840≈1.69元 | 人工接管设计可能比降token更重要 |
| 完成意图从840降为700，成本暂不变 | 1000元 | 1000/700≈1.43元 | 低总账单不能掩盖质量下降 |

上表是假设单变量变化，不是预测因果；实际中完成率、人工介入和模型成本可能一起变化。先按任务类型找瓶颈，再讨论换模型或调整自主程度。

## 四、采用队列：有需求的人是否愿意再用

受邀员工使用率100/200＝50%；有相关需求员工中的使用率100/120＝83.33%。同样100名使用者，分母不同回答不同问题。1000项任务不能推出1000名活跃用户。

本例只计算次周观察，并在第4周复盘，不提供连续4周留存。第1周首次使用40人，第2周24人再次有同类需求，18人再次使用：

- 普通次周留存：18/40＝45%。
- 有同类需求条件下的复用：18/24＝75%。

这说明要补查“是否发生新需求”，但不能因此忽略未复用的6人。对这6人分诊：入口找不到、旧制度答错、提交步骤繁琐、审批结果不透明，还是偏好人工。也不能把没有新需求的16人全部解释成满意。

## 五、把受控试点写成一份决策单

前一课B版仍有两项教学失败，尚未实际运行。以下是可交给真实项目团队的试点设计示例，不代表本仓库已启动试点。

| 项目 | 本练习的试点设计 |
|---|---|
| 进入前提 | 补独立留出集；权限/幂等/取消硬性失败为0；当前制度可取；业务系统与支持负责人就绪 |
| 起始范围 | 单租户单部门，先只读问答与草稿；修复或关闭受影响知识路径后才考虑提交 |
| 人员 | PM负责范围与判断；工程负责工具、日志和恢复；IT维护制度；主管审批；运营支持培训与反馈 |
| 对照 | 同类任务保留原入口，记录质量、人工操作时间与完成状态；自选使用结果不能直接当因果增益 |
| 观察 | 按任务和成熟队列看完成、转人工、返工、费用、延迟；每周复盘只是教学节奏，真实周期按使用频率调整 |
| 立即收缩 | 越权、重复有效申请、失效确认写入、无法追查回执，关闭写工具并人工核查影响 |
| 允许扩大 | 目标场景稳定达到业务预先约定标准；没有硬性失败；支持量和成本可承受；未解决问题不被平均分掩盖 |
| 退出 | 非AI方案同样有效、真实采用不足、制度长期无人维护或成本不支持业务价值 |

不规定通用“上线成功率必须95%”或标准流量百分比。门槛取决于任务风险、可逆性、真实基线、样本量和观察窗口；少量试点未出事故也不能证明事故概率为0。

## 六、验收报告与作品集怎么呈现

交付报告按以下顺序：问题和范围→PRD关键取舍→权限与状态→评测证据→运行成本→采用观察→继续/收缩决策。每个数值标出教学假设、实际采样或已核验外部资料的类别。

本系列可写：“基于虚构内部IT场景，完成12份材料、需求与权限规格、30条评测设计及成本教学演算。”不能写“已上线企业助手，准确率93.33%，服务200员工，节省5000元”。真正运行后才补实际日期、版本、样本和本人职责，教学结果仍应保留标识。

读者最后提交四份实践作业和一页决策记录，由另一名读者检查能否独立解释：哪一步算完成、谁能批准、重试为什么不建两单、成本分母是什么、哪些结果还没被证明。回答不清楚的部分回到对应正课修订。
