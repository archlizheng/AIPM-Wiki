# 实践一：企业内部服务助手的需求发现

> **层级：实践。** 先修：[AI 需求发现](../prd-and-design/ai-demand-discovery.md)。目标：完成一张能被业务负责人否决或接受的立项卡。全文为虚构教学推演，不是实际用户访谈或已上线项目。

## 一、先把“做个 IT Agent”改成可观察的问题

假设你收到需求：“员工总是问设备怎么申请，我们做一个全自动 IT Agent。”这句话还没有说明员工卡在哪里。若问题只是入口难找，固定链接可能比模型更便宜；若真正卡在主管审批，聊天助手也不能代替主管。

本系列最终覆盖三个任务：回答适用制度、生成并提交员工确认过的申请、查询申请状态。本篇先做立项判断；先验证问答和草稿，通过后续权限与评测验收才考虑开放提交。采购、付款、账号提权、自动审批不属于本期。最终产物为 Markdown 需求与验收材料，不提供可运行应用。

打开[统一教学资料包](../../../assets/internal-service-assistant/teaching-materials.md)，保留其中12份制度资料、四类角色以及故意设置的过期和冲突信息。所有课使用同一套材料ID与数值。

## 二、用访谈和工作观察区分原因

下面是作者编写的练习记录。它们演示访谈分析方法，不能称作真实“3位用户访谈”。

| 教学角色 | 虚构记录 | 尚不能直接得出的结论 | 下一步该观察什么 |
|---|---|---|---|
| 员工 E01 | “搜到两份设备标准，不知道按哪份填；提交后又问 IT 有没有批。” | 员工需要任意任务全自动代办 | 能否找到适用制度；是否混淆提交、批准和交付 |
| 主管 M01 | “申请用途太笼统，我常退回补信息。” | 模型应自动编写用途、自动审批 | 退回原因分布；哪些字段能通过澄清补齐 |
| IT01 | “我花时间解释流程、纠正旧 FAQ，并查工单状态。” | 所有工时都能转成现金节省 | 哪些问答可标准化；处理时间中等待与人工操作的比例 |
| ADM01 | “员工跨部门调岗后，旧权限可能失效。” | 拥有管理员权限就可以代员工操作 | 身份数据更新时间与服务端鉴权责任 |

访谈可使用以下问题：最近一次申请是什么；从哪个入口开始；在哪一步停下；实际打开哪些材料；失败后找谁；什么证据让你相信提交成功。少问“想不想要 AI”，多让对方复述一次真实任务。

工作观察表至少包含任务ID、角色、触发原因、原始入口、操作步骤、等待时间、人工处理时间、失败或返工原因、最终业务状态。敏感内容只记录必要摘要；组织政策尚未允许采集时，先使用脱敏或教学材料。

## 三、画出当前流程并建立非 AI 基线

```text
员工搜索制度 → 判断版本 → 找表单 → 填写 → 提交
                                      ↓
                              主管审批 → IT人工交付
                                      ↑
                             员工向IT询问当前状态
```

助手可以缩短查找、澄清和状态查询，但不应把审批等待也算作已经消除的人工工时。要把“操作时长”“流程历时”“最终完成率”分开统计。

按[统一事件与观察窗口](../../../assets/internal-service-assistant/teaching-materials.md#统一事件与观察窗口)记录需求，同一目标的澄清、修改、重试与接管不增加意图数。教学月度场景为1000个去重意图：600问答、300提交、100查询。为了演算，假设人工每个意图处理6分钟；这只是[共同账本](../../../assets/internal-service-assistant/teaching-materials.md)的基线假设。真实调研应按任务类型和成功／失败分别抽样计时，不能直接沿用6分钟。

先设三个可比较方案：

| 方案 | 改变什么 | 先验证什么 | 何时选它 |
|---|---|---|---|
| A：固定入口＋结构化表单 | 统一制度链接、必填校验、状态入口 | 员工是否仅因找不到入口而受阻 | 路径固定、任务分歧少 |
| B：检索问答＋表单链接 | 对问题查适用制度，再交回现有表单 | 版本与权限过滤是否可靠 | 理解问题有价值，代操作价值不明 |
| C：问答＋受控申请提交 | 澄清字段、预览确认、提交并查回执 | 是否减少填报返工，能否阻断越权与重复单 | B通过且新增执行收益足以覆盖风险 |

本练习采用 B→C 的验证顺序。不是断言 Agent 总比表单好，而是让写操作的投入有单独证据。

## 四、机会评分只用于安排验证顺序

先检查权限、权威制度、流程责任人这三项前置条件；缺一项，任务暂不进入执行型方案。之后才对频率、返工损失、任务清晰度和可撤回性打1—3分，分数代表团队判断，不是市场事实。

| 候选任务 | 频率 | 返工损失 | 清晰度 | 可撤回性 | 教学决策 |
|---|---:|---:|---:|---:|---|
| 制度问答 | 3 | 2 | 2 | 3 | 第一批，用冲突材料验证权威判断 |
| 申请草稿 | 2 | 3 | 3 | 3 | 第一批，只给可编辑草稿 |
| 确认后提交 | 2 | 3 | 3 | 2 | 第二批，必须有回执和幂等服务 |
| 自动审批 | 2 | 3 | 1 | 1 | 排除，违反角色边界，不能靠高分覆盖 |

不要把分数简单相加后宣布“自动审批最值得做”。硬约束决定能否进入，分数只安排已经可做的候选任务。

## 五、最小验证设计与停止条件

第一步，用 D01、D02、D05、D06 让两名扮演员工和IT的评审者各自完成同一任务，记录是否找到正确制度；这是角色扮演检查，不等于用户验证。第二步，用静态草稿和确认卡观察能否发现用途、地点或规格错误。第三步，用纸面业务回执推演超时和重复提交，在没有真实系统前暴露契约缺口。

真实试点开始前，再用独立采集的真实需求验证方案A/B/C的相对收益。此时数据授权、服务端权限和业务责任人必须已就绪。

停止条件预先写入立项卡：统一表单已解决主要问题；没有权威制度维护人；执行接口无法防止重复或越权；目标改善来自缩短审批等待但项目无权改变审批流程。命中后缩范围或停止，不以“模型能力已经很强”为理由继续追加功能。

## 六、填好的立项卡

| 字段 | 教学项目选择 |
|---|---|
| 问题 | 适用制度难识别、草稿信息缺失、提交后状态不透明 |
| 用户与入口 | tenant-A员工，从现有IT服务入口使用 |
| 本期任务 | 适用制度问答、申请草稿；通过下一阶段验收后才开提交 |
| 成功定义 | 问答有适用依据；草稿字段准确；提交有业务ID和待审批状态 |
| 基线与比较 | 固定入口＋表单，与问答／草稿辅助分别比较 |
| 证据缺口 | 当前仅教学假设，缺真实需求分布、人工基线、采用验证 |
| 风险责任 | PM定边界；工程定接口与日志；IT维护制度；主管人工审批 |
| 决策 | 允许继续规格与评测设计，不能宣称已经证明PMF或生产收益 |

## 练习与自查

将场景中的“设备申请”替换为你熟悉的内部服务，只改任务和资料，不先换模型。交付立项卡、原流程和非AI方案；检查每项优势是否有可采集证据。若只有聊天演示和满意度想象，立项依据尚未完成。
