# 主观任务怎么评:人工评估与 LLM-as-a-Judge

## 主观任务为什么难评

"这道数学题答案对不对"很容易评——比对标准答案即可。但"这条客服回复够不够得体"呢?"这篇总结写得好不好"呢?这类任务往往没有唯一正确答案,评判标准隐藏在一堆模糊的形容词里(专业、有帮助、有共情心),不同人打分可能相差很大。这正是绝大多数生成式 AI 产品要面对的现实:摘要、创作、对话、推荐理由——几乎所有"生成类"能力的评估,本质上都是主观任务。

在 [《从零建设评测集》](build-your-eval-set.md)中我们提到,评分方法按可靠性和成本排序依次是代码评分、LLM 评分、人工评分。本篇专门展开后两种——当任务没有唯一答案时,人工评估和 LLM-as-a-Judge(模型当裁判)分别怎么做,以及如何把两者结合成一套可持续运转的评估体系;后半补上 Judge **不可信的三类问题**,以及老板要"准确率 90→99"时的预期管理(与价值量化面试题互链)。

> **选题启发**：磊叔《关于 AI 产品经理的 100 个问题》Q26、Q58。正文为原创方法论，不复述 PDF 中的具体数字与轶事。
>
> **事实**：Anthropic / OpenAI / Google 均要求 LLM 评分先与人工对齐、用具体 rubric，并持续抽检；位置/自我偏好/冗长等偏差有业界与官方文档反复提及。见文末参考资料。
>
> **建议**：把 Judge 当大规模初筛，人工当校准器；高分不等于可信，先问"评的是不是用户要的维度"。

## 人工评估:黄金标准,但要讲方法

人工评估通常被认为是质量的"黄金标准",但"找人来看一看"不等于"人工评估做得好"。要让人工评估真正可信,至少要做好三件事:

### 1. Rubric 设计

给标注员一句"判断回答好不好"是没用的,必须把标准拆解成可执行的检查项。一个可参考的 rubric 结构:

```text
【总结质量人工评估 rubric】

维度 1:事实准确性(0/1) —— 是否存在与原文矛盾或编造的信息?
维度 2:信息完整性(1-5) —— 是否覆盖了原文的关键信息点?
维度 3:简洁性(1-5) —— 是否存在冗余、重复表达?
维度 4:可读性(1-5) —— 句子是否通顺、逻辑是否连贯?

任一维度为最低分,总分自动判定为不合格,需要标注理由。
```

Anthropic 官方在讨论"定义成功标准"时特别强调,即便是"语气""伦理""安全"这类看似难以量化的主题,也应该转化为具体、可衡量的描述——比如把"输出要安全"改写成"1 万次试跑中,被内容过滤器标记为有毒内容的比例低于 0.1%"。同样的逻辑也适用于人工评估的 rubric 设计:标准越具体,标注结果越可信。

### 2. 标注一致性

多个标注员对同一条内容打分,结果差异大,说明 rubric 本身有问题,而不是标注员水平问题。常见做法:

- 抽取一批"金标"用例,让多名标注员盲评,计算一致性(常用 Cohen's Kappa 或简单一致率);一致性低于阈值就回头修 rubric,而不是继续标注。
- 定期抽样"背靠背复核":两名标注员对同一批用例独立打分,对分歧项开会讨论、更新 rubric 说明。
- 保留标注理由(不只是分数),便于事后追溯"为什么这条被判不合格"。

### 3. 成本与效率

人工评估慢且贵,几乎不可能对每一次模型/Prompt 迭代都跑一遍全量人工评估。因此实践中的定位是:**人工评估用于"校准"和"抽检",不用于"日常回归"**——日常回归交给自动化的 LLM 评分,人工定期抽样验证 LLM 评分是否仍然可信。

## LLM 当裁判:原理与官方最佳实践

LLM-as-a-Judge 的核心思路很直接:与其让人一条条看,不如写一个评分 Prompt,让另一个大模型来读题目、读回答、按 rubric 打分。它的价值在于**速度快、成本低、可以对每一次迭代都全量跑**,代价是需要先验证它和人类判断是否一致。

结合 Anthropic、OpenAI、Google 三家官方文档的表述,LLM 评分的最佳实践可以归纳为以下几条:

| 实践 | 说明 |
|------|------|
| 清晰、具体的 rubric | "回答第一句必须提到公司名,否则自动判为不合格"这种具体规则,好过"回答要专业得体" |
| 先推理、后结论 | 让模型先在 `<thinking>` 标签里给出评分理由,再输出 `<result>` 结论,最后只保留结论——这能显著提升复杂判断任务的准确性 |
| 结构化、可枚举的输出 | 让模型只输出"correct/incorrect"或 1-5 的整数,而非开放式文字评价,便于批量统计 |
| 分维度、分裁判 | 一个任务的多个评分维度,应该分别用独立的 LLM 评分调用来打分,而不是让一次调用同时判断所有维度 |
| 给模型"退路" | 遇到信息不足的情况,允许模型输出"无法判断",避免为了给出确定结论而强行武断 |
| 与人工对齐后再放量 | 先用一批人工已标注的"金标"用例验证 LLM 评分和人工评分的一致率,确认可信后再大规模使用 |
| 评分模型与被评模型分离 | 一般建议用不同的模型(或至少独立的调用)来评分,避免评分过程受生成过程的思路"污染" |

一个可参考的最小实现:

```text
你是一名评分员。请依据以下 rubric 对回答评分。

<rubric>
1. 是否准确引用了工单中的订单号?
2. 语气是否耐心、专业?
3. 是否给出了可执行的下一步?
</rubric>

<answer>{待评回答}</answer>

请先在 <thinking> 标签中写出你的评分推理,
然后在 <result> 标签中只输出 "correct" 或 "incorrect"。
```

Google 官方在其评估工具 Stax 的最佳实践中也强调:LLM 评分器(autorater)的质量完全取决于 Prompt 和 rubric 的质量,团队应该先人工评一小批样本、和 autorater 的判断反复对比校准,直到评分结果与人工基本一致,才把 autorater 用于规模化评估。行业观察数据也显示,经过良好校准的 LLM 评分器与人类评审的一致率可以达到约 85%,已经接近甚至超过"两个人类评审员之间"的一致率——这说明 LLM 评分不是"将就的替代方案",而是可以做到与人工同等可信,前提是校准工作做到位。

## 已知偏差及缓解

LLM 当裁判不是没有代价,几类偏差已经被反复验证存在,PM 在设计评分流程时必须提前防范:

| 偏差类型 | 表现 | 缓解方法 |
|----------|------|----------|
| 位置偏差(Position Bias) | 做两两对比(A vs B)时,模型有明显的倾向偏爱排在前面(或某个固定位置)的答案,与内容质量无关 | 把两个答案的顺序互换后各评一次,只有两次结果一致才判定为真实胜出;或引入多个裁判组成"评审团"分摊单一裁判的偏差 |
| 自我偏好偏差(Self-Preference Bias) | 模型评估"自己生成的答案"或"同系列模型生成的答案"时,倾向打更高分 | 评分模型与生成模型尽量使用不同厂商/不同系列;定期用人工抽检交叉验证 |
| 长度偏好(Length/Verbosity Bias) | 模型倾向认为"更长的回答"更好,即便信息密度更低 | 在 rubric 中显式要求"简洁性"作为独立评分维度;必要时控制候选回答长度在同一区间内再比较 |

这些偏差的存在,恰恰说明了"人工对齐"不是一次性动作,而应该是持续的常态检查——每次更换评分模型、更新评分 Prompt,都应该重新用金标数据校准一次。

## Judge 打了高分你却不敢信：三类不可信问题

Evals 报表上 Judge 给出很高的分,不等于可以据此发版。除了上表"怎么偏",更要警惕它在哪几类**问题类型**上会系统性给出误导信号——这时分数不是噪声,而是结构性撒谎。

| 不可信类型 | 为什么不可信 | PM 怎么处理 |
|------------|--------------|-------------|
| **主观偏好类** | "哪个文案更好 / 更有品牌感"依赖真实用户口味;Judge 自带偏好(偏长、偏自信、偏"像助手说话"),常与目标用户不一致 | 用真实用户/业务专家做金标校准;能用行为指标(采纳、复用、转化)的,不要只用 Judge 分做终裁 |
| **自我评估类** | 用同族或同一模型评自己的输出,分数系统性偏高(自我偏好) | 评分模型与被评模型解耦;关键闸门保留人工抽检;不要把"自嗨分"写进上线标准 |
| **维度模糊类** | rubric 只有"质量好 / 用户友好"等形容词,无可观察检查项 | 先把维度拆成可执行规则与反例;模糊维度未校准前,禁止作为唯一放行信号 |

正确用法不变:**Judge = 大规模初筛;人工 = 校准与抽检。** 先在金标集上算与人工的一致率,不够就改 rubric / 加 few-shot,达标后再放量;放量后仍保留定期抽检,监控偏差漂移。官方实践(Anthropic 先推理后结论、Google Stax 强调 autorater 与人工对齐)都指向同一纪律——没有对齐记录的高分,不能当验收依据。

与上节三类**偏差机制**(位置 / 自我偏好 / 长度)的关系:偏差讲"裁判怎么歪",本表讲"哪类任务上歪得最致命"。设计评分时两边一起过一遍。

## 人机结合的推荐流程

把人工评估和 LLM 评分结合起来,而不是二选一,是目前业界的主流做法。一个可落地的流程:

```
① 人工构建/标注一批「金标」评测用例(含标准答案或参考 rubric)
   ↓
② 设计 LLM 评分 Prompt,在金标用例上试跑
   ↓
③ 对比 LLM 评分 vs 人工评分的一致率
   ↓
   一致率不达标 → 回到②修改 rubric/评分 Prompt
   一致率达标 → 进入④
   ↓
④ 用 LLM 评分做日常/全量自动化评估(每次迭代都跑)
   ↓
⑤ 定期(如每周/每次大版本)人工抽样复核 LLM 评分结果,
   监控是否出现偏差漂移
   ↓
⑥ 发现漂移 → 回到②重新校准
```

这个闭环的关键在于:**人工不退出评估体系,而是从"评估每一条"退到"评估评估者"**——用有限的人工成本,持续校准一个可以无限扩展的自动化评分系统。

## 老板要准确率 90→99：怎么管理预期

"把准确率从 90% 提到 99%"听起来只是几个百分点,对 PM 却是典型的预期管理题——中间每一段的难度、成本和路径往往不是线性的。

**先拆指标,再谈承诺。** "准确率 90%"要先澄清:精确率还是召回?按请求还是按用户?整体还是某关键子场景?剩余错误集中在哪类 case?拆开之后,决策者看到的是分布,而不是一个笼统的整数。价值怎么换算成钱/人天,见面试题 [模型准确率提升的业务价值如何量化?](../../04-interview/case-analysis/quantify-model-accuracy-value.md)。

**再按区间谈路径与代价(原则,非固定工期表):**

| 区间 | 常见杠杆 | 预期沟通要点 |
|------|----------|--------------|
| 离底线较远 → 中高水位 | Prompt、检索/规则、参数、明显 badcase 修复 | 工程优化常能看到进展;用离线分 + 灰度业务指标双轨验收 |
| 接近人工可用水平 → 更高目标 | 换更强模型、专项数据飞轮、细分场景策略、人工复核兜底 | 边际成本陡增;最后几个百分点常卡在长尾与能力天花板,不是"再调两周 Prompt" |
| 业务要的"有效 99%" | 模型 + 规则闸门 + HITL / 高风险转人工 | 未必等于"模型裸分 99%";组合方案往往更便宜、可审计 |

沟通模板可以是一页纸:

1. **现状分布**:当前错误落在哪些切片、各自错误成本
2. **目标拆解**:99% 指整体还是核心切片?哪些允许规则/人工兜底
3. **代价对照**:每一档提升对应的研发、标注、算力与周期量级(用区间,不编精确数字)
4. **验收方式**:离线 golden / Judge 校准线 + 线上 OEC;Judge 高分 alone 不算达标

很多时候要 99% 是因为没看见代价。PM 的职责不是无条件接数字,而是把**真实代价与替代路径**翻译给决策者——他可能改成"核心场景有效准确率 + 长尾转人工",而不是全量模型裸奔 99%。Anthropic 对成功标准的要求也是 **Achievable**:目标应基于基准与先验,而不是不可达的口号。

## PM 落地清单

- [ ] 明确这个任务是客观题还是主观题,避免用"精确匹配"硬评主观任务,也避免用模糊的 LLM 评分去评本该有唯一答案的客观任务
- [ ] 主观任务的评分标准写成可执行的 rubric,而不是形容词堆砌
- [ ] 人工评估先做"一致性检验",一致率不达标先改 rubric 再标注
- [ ] LLM 评分 Prompt 要求"先推理后结论",并只保留结构化结论
- [ ] 多维度任务拆成多次独立评分调用,不要一个 Prompt 判所有维度
- [ ] 上线前用金标数据验证 LLM 评分与人工的一致率,达标后再放量
- [ ] 两两对比场景默认做位置互换,防止位置偏差污染结果
- [ ] 评分模型与生成模型尽量解耦,防止自我偏好偏差
- [ ] 建立"人工抽检 LLM 评分"的常态化复核节奏,而不是一次校准了事
- [ ] 主观偏好 / 自我评估 / 维度模糊三类任务,不把未校准的 Judge 分当唯一放行信号
- [ ] 面对"准确率拉到 99%"类目标,先拆口径与错误分布,再摆代价与兜底路径(链价值量化题)
