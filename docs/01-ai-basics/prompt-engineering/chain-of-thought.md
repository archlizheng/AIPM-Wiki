# 思维链(CoT):让模型先想再答

直接问模型「答案是什么」,它往往会「脱口而出」——对简单事实还行,一遇到多步计算、规则嵌套、因果分析,就容易在中间悄悄跳步、算错或自相矛盾。思维链(Chain of Thought, CoT)要做的事很简单:**让模型在给出最终答案之前,先把中间推理步骤写出来**。

对 AI PM 来说,CoT 不只是「Prompt 小技巧」。它决定了产品在复杂任务上的正确率上限、用户能不能看懂「模型为什么这么说」、以及你愿不愿意为这段「思考过程」多付 token 和延迟。懂 CoT,才能在 PRD 里写清「什么场景必须逐步推理、什么场景必须直接答」。

## 一句话定义

**CoT 是一种 Prompt 技术:引导模型在最终答案前,显式输出中间推理步骤。** 它不改模型权重,也不另起一套系统——通常只要改 Prompt(或提供带推理过程的示例)即可生效。

## 直接提问 vs CoT

| 方式 | 提问方式 | 模型行为 | 典型风险 |
|------|----------|----------|----------|
| 直接提问 | 「小明有 3 个苹果,又买了 5 个,吃了 2 个,还剩几个?」 | 可能直接给出「6」 | 答对答错都不透明;复杂题更容易「跳步出错」 |
| CoT 提问 | 「请一步步思考:小明有 3 个苹果……」 | 先写「3+5=8, 8-2=6」,再给出「6」 | 输出更长、更慢、更贵;简单题可能多此一举 |

直觉上:直接提问像让人「口算报数」;CoT 像让人「把草稿本摊开」。草稿本本身不保证算对,但错了你能看见错在哪一步。

## 核心优势

1. **复杂推理更稳**:多步数学、逻辑判断、条件分支、业务规则嵌套等场景,把推理「拆开写」通常比一步蹦答案更靠谱。
2. **可解释性**:用户或审核同学能看到「为什么得出这个结论」,而不只是一个黑盒结果——对推荐理由、合规判断、客服决策说明尤其有用。
3. **零训练成本增强**:不需要微调、不需要另训模型,改 Prompt 或加 few-shot 示例即可试;是成本最低的一类推理增强手段。
4. **错误可定位**:哪一步前提错了、哪一步运算错了、哪一步漏了约束,往往一目了然——便于做 badcase 归因和 Prompt 迭代。

需要强调:CoT **不是魔法**。它提高的是「让模型按步骤思考」的概率与可检查性,并不保证每一步都正确;也解决不了「知识本身缺失」的问题——缺事实时更该配合检索,见下文与 [RAG](../llm/what-is-rag.md) 的组合。

## 适用 / 不适用(产品视角)

**更适合启用 CoT 的场景**:

- 多步计算或逻辑推导(报价规则、库存可用量、优惠叠算)
- 需要「给理由」的决策输出(为什么推荐 A 而非 B、为什么判为高风险)
- 复杂业务规则/合规审查(多条件同时成立才通过)
- 需要人工抽检、质检、审计的链路(可读推理过程是验收资产)

**通常不该默认开 CoT 的场景**:

- 简单事实查询、短指令执行(浪费 token,用户也更烦冗)
- 强创意生成(诗歌、文案 brainstorm)——过细的「推理步骤」可能把发散压死
- 对延迟极敏感的交互(首字延迟、实时语音、高频点击路径)
- 已经打开**推理模型 / 扩展思考**能力的产品档位:这类模型往往在内部自行规划步骤,再显式要求「一步步列出」可能啰嗦甚至干扰;对轻量、非推理档位,显式 CoT 仍然很有用。相关边界见 [Prompt 基本功](prompt-basics.md) 中「推理模型时代」一节。

## 产品落地:怎么用、何时用、怎么控成本

### 1. 在 Prompt 里启用

最常见、也最低成本的做法是加一句明确指令,例如:

- 「请一步步分析,再给出结论。」
- 「先列出关键前提与中间计算,最后用一句话给出答案。」
- 「如果信息不足,先说明缺什么,再给出在已知条件下的推理。」

也可以把「推理过程」和「最终答案」分区要求(Markdown 标题、XML 标签均可),方便前端折叠展示「思考过程」,默认只露出结论——这既保留可解释性,又不把聊天界面刷成墙。

### 2. 何时用 few-shot「带推理步骤」的示例

仅说「请一步步想」有时不够稳:模型可能写得很空、或步骤风格漂移。此时用 **few-shot CoT**——在示例里同时给出「输入 → 推理步骤 → 最终答案」——往往更有效:

- 示例要覆盖**典型路径 + 至少一条边界路径**(缺字段、冲突规则、需拒答)
- 示例格式保持一致(步骤编号、结论字段名统一)
- 数量通常 1–3 个高质量示例就够用;堆太多可能过拟合表面套路

这和 [Prompt 基本功](prompt-basics.md) 里「示例」一节是同一套纪律,只是示例内容从「输入/输出」升级成了「输入/推理/输出」。

### 3. 成本与延迟权衡

CoT 的代价几乎总是同一件事:**输出变长 → token 费用上升 → 延迟上升**。产品上不要「全站默认 CoT」,而要按任务价值做开关:

| 策略 | 做法 | 适用 |
|------|------|------|
| 任务分流 | 简单问答直出;复杂任务才启用 CoT | 绝大多数 To C / To B 助手 |
| 分类器触发 | 先用轻量模型/规则判断「是否需要多步推理」,再决定是否附加 CoT 指令 | 流量大、成本敏感 |
| 展示折叠 | 推理过程可展开,默认隐藏 | 要可解释、又要界面干净 |
| 长度约束 | 「推理不超过 N 步 / N 字」 | 防止模型写成长篇作文 |

一个实用原则:**只有「答错的业务成本」明显高于「多花的 token + 延迟」时,才值得默认打开 CoT。**

### 4. 和结构化输出怎么配合

生产链路里常见组合是:CoT 负责「想清楚」,结构化输出负责「交得出」。例如要求模型先在内部或可见区域完成推理,最终只把结论字段以 JSON 吐出给下游——格式稳定性另见 [结构化输出](structured-output.md)。若把冗长推理和最终 JSON 混在同一段裸文本里,解析会变脆,PRD 里应提前约定分区。

## 延伸:Self-Consistency,以及 CoT + RAG

### Self-Consistency:用成本换更稳的答案

Self-Consistency(自洽性)是 CoT 的增强玩法:对同一问题**多次采样**不同推理路径,再对最终答案做多数表决(或等价的一致性聚合)。直觉是——单条推理链可能走偏,多条独立路径若收敛到同一答案,可信度通常更高。

代价也很直观:**调用次数/采样次数上去,费用与延迟近似成倍增加**。产品上更适合高风险决策、离线批处理、或「宁可多花一点也要少错」的审核类任务;实时聊天默认上 Self-Consistency 往往不划算。

### CoT + RAG:知识归检索,推理归步骤

RAG 解决的是「材料从哪来」,CoT 解决的是「材料怎么用」。两者经常一起用,例如:

> 根据以下检索到的政策原文,一步步分析该政策对目标用户的影响;只依据给定材料,不要编造未出现的条款;最后给出结论与三条依据引用。

组合时要在 Prompt 里写清两件事:**推理必须锚定检索片段**,以及**材料不足时允许「无法判断」**——否则模型会用漂亮的思维链包装幻觉。更多选型见 [Prompt / RAG / 微调怎么选](../llm/prompt-rag-finetuning.md) 与 [什么是 RAG](../llm/what-is-rag.md)。
