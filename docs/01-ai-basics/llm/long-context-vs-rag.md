# 长上下文 vs RAG:什么时候塞全库,什么时候检索

模型的上下文窗口一路涨到百万 token 级别之后,一个自然的产品问题冒出来了:知识库不大的话,是不是直接把全部资料塞进 Prompt 就行,不用再折腾检索链路?答案不是简单的"是"或"否",而是要按知识库规模、更新频率、并发量、权限模型这几个维度分别算账。本文接着[《RAG 没死:死的是 Naive 固定流水线》](rag-evolution-naive-to-agentic.md)的话题,专门拆这道选型题。

## 一句话说清

**窗口大小决定"能塞多少",不决定"该不该塞"。** 官方给出的可参考分界线是知识库规模;超过这个规模,继续依赖"全量塞进窗口"在成本、延迟和准确率上都会开始吃亏,这时候检索仍是更划算的方案。

## 官方分界线:约 200K tokens(约 500 页)

Anthropic 在《Introducing Contextual Retrieval》一文中给出过一个具体、可操作的判断标准:**如果知识库小于约 200,000 tokens(约 500 页材料),可以考虑直接把整个知识库放进 Prompt,不必上 RAG**;超过这个规模,再考虑检索方案更合理。这个数字是官方给出的经验阈值,不是严格的物理上限,但足够作为产品决策的起点。

需要补充两点背景,避免误用这个阈值:

1. **这个建议是配合 Prompt Caching(提示词缓存)提出的**:反复调用同一段长上下文时,缓存机制能把延迟降低 2 倍以上、成本降低最多 90%,"全量塞入"方案的性价比很大程度上依赖这项能力,不是裸调用长窗口。
2. **这是 2024-09 发布的方法论,不是随模型迭代实时更新的动态指标**——各厂商上下文窗口和缓存机制都在持续演进,选型前建议核对当前模型的最新窗口大小和缓存定价,而不是直接套用一个固定数字。

## 长上下文不等于免费:三笔账

窗口变大买到的是能力上限,不是免费的午餐。产品设计时至少要核算三笔账,详细展开见[《上下文窗口:限制、成本与产品设计影响》](context-window.md),这里只强调和"要不要用检索代替全量塞入"直接相关的部分:

| 账目 | 全量塞入窗口 | 检索(RAG) |
|------|-------------|-----------|
| 成本 | 每次调用都按知识库全量 token 计费(缓存命中时可大幅降低,但仍随库增长而涨) | 只为检索出的少量片段付费,随库规模增长更平缓 |
| 延迟 | 输入越长,首 token 等待通常越久,不适合强实时场景 | 检索本身有开销,但生成阶段输入更短,总延迟更可控 |
| 效果 | 存在"中间遗忘"(Lost in the Middle)风险:关键信息若落在长文本中段,模型的检索/引用准确率会下降 | 提前把最相关片段挑出来、精简靠前地喂给模型,更贴近模型实际"重视"的位置 |

"中间遗忘"是这三笔账里最容易被低估的一项:窗口再大,不代表模型对窗口内所有内容一视同仁地重视,这一点在文档问答、长报告审查这类场景里尤其关键。

## 反方视角:规模化私有知识仍需要检索层

不只是 Anthropic 的阈值建议,向量数据库厂商 Qdrant 在《Is RAG Dead?》一文中也从另一个角度论证了同一个结论:当私有知识库规模达到企业级(如涵盖海量历史数据、需要长期维护和多租户访问)时,单纯依赖更大的上下文窗口在计算成本上会变得不现实,检索层的价值在于用远低于"整库进窗口"的开销筛出真正需要的证据。这类观点出自向量检索服务商,不能直接当作中立数据看待,但它指出的成本结构问题——每次调用把整库塞进窗口,单次问答的计算开销会随库规模线性甚至更快增长——是产品测算时应该验证而不是想当然认为"窗口够大就没事"的。

## 决策树

把决策拆成几个可核查的问题,而不是单看"窗口够不够大":

```
知识库有多大?
├─ 明显小于 ~200K tokens(约 500 页),几乎不更新
│   → 可以考虑全量塞入 + Prompt Caching,先跑通再评估是否需要升级
│
└─ 接近或超过阈值,或规模会持续增长
    → 走检索,再往下细分:
        ├─ 更新频率高(天级/小时级)?
        │   → 检索优先:全量塞入意味着每次更新都要重新走一遍长上下文调用,成本不划算
        ├─ 并发量大、是多用户共享同一知识库?
        │   → 检索优先:检索层可复用索引,全量塞入是"每个请求都重新读一遍全书"
        ├─ 需要精确引用到具体段落/来源?
        │   → 检索优先:检索天然带片段级定位,长窗口生成的引用定位需要额外工程
        └─ 涉及多租户权限(不同用户能看到的知识范围不同)?
            → 必须走检索:权限过滤要发生在"进入 Prompt 之前",而不是靠模型在长文本里"自觉不看"
```

多数真实产品会落在"走检索"这一支——知识库会持续增长、需要多用户共享、需要标注来源,这几个条件单独一条命中就足够让"全量塞入"变得不划算。

## 和 Rerank 的关系:长窗口是"更多证据",不是"取消检索"

一个常见的误解是:窗口够大之后,重排序(Rerank)这一步也可以省了。更准确的判断是——长上下文改变的是"生成阶段能带多少证据",不改变"检索/重排阶段该怎么挑证据"。多路召回保证覆盖、重排保证精度这套"宽进严出"的链路仍然成立,长窗口更适合用来承载"重排后的更多证据"或"多文档对照",而不是替代排序这一步本身。具体的产品判断标准和何时可以弱化独立 Rerank 模型,见面试题[《上下文都到 1M 了,Re-Ranker 还有用吗?》](../../04-interview/basics/reranker-with-long-context.md)。

## 给 AI PM 的启示

1. **别把"窗口够大"当成跳过检索的理由**,先按知识库规模、更新频率、并发、引用需求、权限模型这五个维度核对一遍决策树。
2. **官方阈值是起点,不是终点**——200K tokens 的建议基于特定模型和缓存机制,选型前核对当前模型的最新窗口、缓存定价和实测中文 token 换算。
3. **全量塞入方案要搭配 Prompt Caching 才谈得上性价比**,裸调用长窗口的成本曲线会比想象中更陡。
4. **检索和长上下文是互补关系,不是二选一**:即使选择检索路径,生成阶段依然可以利用大窗口装载"重排后的更多证据",两者叠加往往比单独依赖任何一方效果更好。
