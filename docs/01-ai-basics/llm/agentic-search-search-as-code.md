# Agent-search 与 Search as Code:搜索栈如何可编程

[《Agentic Retrieval:检索如何变成 Agent 的工具》](agentic-retrieval.md)提到,当检索对象从"你自己的知识库"扩展到"整个互联网",一部分前沿产品走得更远:不满足于"让模型调用搜索工具",而是把搜索栈本身拆开,让模型直接编排里面的原子操作。这就是本文要展开的 **Agent-search / Search as Code(SaC)**。

## 一句话说清

**过去是"模型调用一次搜索,拿到一份处理好的结果集";现在部分产品在做的是"模型生成代码,在沙箱里现场组装检索、排序、过滤等原子操作,拼出一条只为这次任务服务的检索管线"。** 变化的不是"要不要搜索",而是模型对搜索过程的控制粒度。

## 从"调用搜索"到"编排搜索原语"

传统搜索——不管是给人用的搜索引擎,还是给 AI 用的 `web_search` 类工具——本质上都是黑盒:输入查询参数,系统跑一套预定义管线,吐出一份处理好的结果集。这个契约对人类用户是合理的:没人想手动调排序权重、微调召回粒度。但对需要在一次任务里发起成百上千次检索操作的 Agent 来说,黑盒契约变成了瓶颈。

Perplexity 在《Rethinking Search as Code Generation》(2026-06)里把这种刚性归纳为三类失败模式,可以直接当作判断"要不要往可编程搜索走"的检查清单:

1. **上下文过粗**:任务需要一条精确信息,但接口只提供偏召回的端到端搜索,结果里塞进大量无关内容;反过来,任务需要大量分散信息时,又被迫对同一个笨重管线重复调用,成本和噪音一起攀升。
2. **无法注入领域知识调整策略**:模型可能清楚"这次该偏关键词还是偏语义""该按什么字段聚合",但如果这些判断没法通过几个查询参数表达,模型就没有办法把这层知识落地。
3. **控制流低效、污染上下文**:fan-out(多查询并发)、去重、多轮过滤这类天然非线性的操作,一旦被迫拆成一轮一轮"模型可见"的调用,不仅慢,中间结果还会堆在上下文里,污染后续推理。

## SaC 三层架构

Perplexity 给出的应对方案把搜索栈拆成三层,彼此紧密耦合:

| 层 | 角色 | 做什么 |
|----|------|--------|
| **模型控制面** | 决策 | 理解任务、拆解成子任务、决定每个子任务需要什么检索/处理策略,生成代码 |
| **沙箱** | 执行 | 提供确定性的代码执行环境,跑批处理、重试、过滤、聚合等操作;中间状态优先走文件系统显式序列化,而非纯内存 REPL,官方测试认为这对长轨迹更稳定 |
| **Agentic Search SDK** | 原语 | 把搜索栈拆成检索、排序、过滤、fan-out、渲染等**原子级**building block,供模型在代码里自由拼装 |

三层缺一不可:没有模型就无法决策检索策略;没有沙箱模型只能被迫串行调用、在 token 空间里处理数据;没有把搜索栈拆到原子粒度的 SDK,模型手上就没有可编排的积木。

## 为什么不只是把 search API 塞进 shell

一个容易想到但效果有限的做法是:直接给模型一个 shell 或 REPL,把现成的搜索 API 包一层,让模型写脚本调用。这和 SaC 的关键区别在于**颗粒度**:如果 SDK 里仍然只暴露"搜索"这一个整体接口,模型能编排的空间就只是"调几次、怎么拼参数",本质上还是黑盒管线,只是换了个调用方式。SaC 强调的是把搜索栈本身重新架构到"检索""排序""过滤""fan-out"这一级原子操作,模型才有真正意义上的组合自由度——这是工程投入(重新拆分底层搜索系统),不是接口包装能替代的。

## 窄搜索 vs Wide Research:能力边界要老实说

Perplexity 官方话语里有一个值得 PM 注意的区分:**窄搜索**(找到一份权威信息回答一个问题)已经相对成熟,当前的难点在于**Wide Research**(宽检索)——在开放集合里找出**全部**符合条件的对象,并给每一条都配上可验证证据,例如"列出符合条件的全部竞品并各自核实一条关键事实"。

2026-07-14,Perplexity 开源了专门评测宽检索的基准 **WANDR**,同时测了自家 SaC 系统与 OpenAI、Anthropic、Google、Exa 等多家系统。结果值得如实转述:SaC 以 0.363 的 soft F1、0.133 的 hard F1 排名第一,第二名(Anthropic)为 0.249 / 0.072,其余系统 soft F1 均不超过 0.121。即便是排名第一的系统,**hard F1 只有约 0.133**——意味着对一个要求提交多条记录的任务,平均只有约七分之一的记录能同时满足"来源可核实、字段完整、类型正确"这三个条件全部达标。这组数字来自 Perplexity 自建并开源的基准(自家系统同时是评测对象之一),第三方系统的对比结果具备一定参考价值,但读者应知道评测设计方与最优系统同属一家。**结论应该是"宽检索仍远未解决",而不是"某家已经领先 X 倍"。**

## 与 Deep Research、MCP、Skills 的关系

- **和 Deep Research 的关系**:[Agent 入门](agent-basics.md)里提到的深度研究 Agent,做的是"自主多轮搜索、阅读、交叉验证、产出带引用报告"这件事;SaC 是深度研究类 Agent 可以选用的**底层搜索执行方式**之一——用可编程管线代替黑盒调用,而不是另一种任务形态。两者不是替代关系,是"任务" vs "执行搜索这一步怎么做"的不同层次。
- **和 MCP 的关系**:[MCP](mcp.md) 标准化的是"Agent 怎么发现、连接外部工具和数据源",每次调用仍是一次模型可见的往返。SaC 针对的是"单次任务需要成百上千次检索操作"这种极端场景,把大量操作收进一次代码执行里完成,减少模型往返次数。SaC 官方文章明确把这个场景下的传统 function calling / MCP 调用方式称为效率瓶颈,但这只是"检索这一类高频操作"在超大调用量场景下的优化,不代表 SaC 要取代 MCP 承担的"接入任意外部系统"这个更通用的角色。
- **和 Skills 的关系**:自定义 SDK 不在模型预训练数据里,模型不会天然知道怎么用。Perplexity 的做法是用 [Agent Skills](agent-skills.md) 教模型使用这套 SDK,并把根 `SKILL.md` 控制在 2000 token 以内,避免占用过多上下文——这与 Skills 专文里"description 要短、正文给可执行步骤"的设计原则完全一致。

## 何时值得做可编程搜索 vs 固定混合 RAG vs 本地 grep

可编程搜索是能力上限,不是默认起点,选型时按下面几条过一遍:

| 场景特征 | 更适合 | 理由 |
|----------|--------|------|
| 单次任务检索操作量小(几次到几十次) | 固定混合 RAG / 现成检索工具 | 黑盒管线已经够用,自建可编程 SDK 的工程投入不划算 |
| 目标明确,已知在哪个知识库/代码库里找 | 本地 grep / 结构化检索 | 精确定位场景,复杂编排反而多余 |
| 单次任务需要成百上千次检索、跨多信息源、需要非线性控制流(fan-out/去重/聚合) | 可编程搜索(SaC 类架构) | 黑盒管线在这个量级下会在延迟、成本、上下文占用上全面吃紧 |
| 需要覆盖"全部符合条件的对象"并逐一验证证据(宽检索) | 可编程搜索,但要预期当前仍是能力边界 | WANDR 等基准显示这类任务即使用最好的系统也远未饱和 |

## 给 AI PM 的判断框架

1. **先看调用量级,再看要不要上可编程搜索**:多数产品的检索需求几十次调用以内就能覆盖,黑盒管线加混合检索已经足够,不必对标 Perplexity 级别的架构投入。
2. **区分"窄搜索"和"宽检索"两类需求**,并对宽检索类任务(尽调、竞品普查、人才盘点)设置保守的准确率预期,产品文案上不要暗示"能找全"。
3. **厂商自报的加速或省 token 数字,只做定性参考**:除非引用方明确标注这是厂商自己的案例研究结果,否则不要把具体百分比写进对外物料。
4. **可编程搜索仍然需要 Skills 教模型用**,自建 SDK 前先确认有没有能力持续维护配套的操作手册和评测集,否则这套架构本身也会变成新的运维负担。
