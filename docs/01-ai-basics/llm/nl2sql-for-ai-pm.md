# NL2SQL:自然语言查库,为什么学术高分上不了生产

"帮我查一下上个月华东区的复购率"——这句话背后不是一次文档检索,而是一次**自然语言转 SQL**(NL2SQL / Text-to-SQL)。很多团队把它当成"顺手接一个功能",直到上线才发现:学术榜单上 90% 起步的模型,一进企业数据库就经常连表都选不对。这篇文章接着[《RAG 没死:死的是 Naive 固定流水线》](rag-evolution-naive-to-agentic.md)的框架往下拆——NL2SQL 不是 RAG 的旁支,而是"结构化世界"里的另一条证据获取路径。

## 检索路径地图里,NL2SQL 排在哪

[《RAG 系统有哪几种检索路径?》](../../04-interview/basics/rag-multi-retrieval-paths.md)把检索路径分成向量语义、关键词、结构化过滤、SQL 查询、知识图谱、实时工具等几类。这些路径共享同一个目标——**给模型找到能支撑答案的证据**,只是证据的存在形式不同:

| 证据形式 | 典型检索路径 | 代表场景 |
|----------|--------------|----------|
| 非结构化文档 | 向量语义检索、BM25、混合检索 | 制度问答、知识库客服 |
| 开放域网页/工具 | Agent 自主规划的实时检索 | 新闻、股价、政策查询 |
| 结构化表格/数据仓库 | NL2SQL、语义层 | 看数、算指标、查订单 |

三条路径面对的核心矛盾其实是一回事:检索目标越明确、越可枚举,固定流水线就越好用;目标越模糊、越依赖多步判断,就越需要模型自己决定"怎么找"。NL2SQL 的特殊之处在于,它的"证据"不是一段可以模糊匹配的文字,而是一条必须**语法正确、语义对齐、权限合规**才能执行的查询语句——错一个 JOIN 条件,答案就从"对"变成"看起来很对但是错的"。

## 学术榜和生产现场的落差:Spider 1.0 vs Spider 2.0

Text-to-SQL 曾是"评测饱和"的代表性任务:在 2018 年发布的 Spider 1.0 基准上,GPT-4o 能拿到约 **86.6%** 的执行准确率(Execution Accuracy),看起来已经接近"解决"。但 2024 年发布的 **Spider 2.0** 换了一套贴近企业真实工作流的测试集——数据库常常超过 1000 列、涉及 BigQuery/Snowflake 等多种 SQL 方言、任务往往要求模型先读懂元数据文档甚至项目代码才能写出正确查询。同一个 GPT-4o,在 Spider 2.0 上的执行准确率直接跌到约 **10.1%**;当时被认为推理能力更强的 o1-preview,也只能解决约 **17.1%** 的任务。

这不是模型退步了,是评测终于逼近生产现场的复杂度。Spider 2.0 官方给出这组对比的用意很直接:**学术榜单的高分衡量的是"能不能在干净、单库、schema 已知的题目上写对 SQL",不是"能不能在企业数据环境里独立完成一次查数任务"**。这条落差,就是评估任何"接个大模型查数功能"方案时该有的第一道警觉。

## 企业级 Text-to-SQL 到底难在哪

把 Spider 2.0 的设计动机翻译成产品语言,企业场景的难点大致集中在:

- **千级列的宽表**:真实数据仓库的表远比教学数据库宽,模型光"选对列"就需要额外的检索/摘要步骤,而不能整表塞进 Prompt。
- **多方言与多引擎**:同一句自然语言,在 BigQuery、Snowflake、MySQL 里的正确写法可能都不一样,模型需要先确定目标引擎的语法边界。
- **指标口径不统一**:"复购率""活跃用户"这类词在不同团队、不同报表里的计算公式经常不一致,模型选错口径不会报错,只会安静地给出一个"能执行但不对"的数字。
- **脏数据与字段命名黑话**:字段名缩写、历史遗留表、注释缺失,都会让模型"猜"schema 语义,猜错的代价是查询能跑通但结果是错的。
- **权限边界**:哪些表、哪些行、哪些用户能查,不能靠模型"自觉遵守",必须在执行层强制。
- **多跳工作流**:很多真实问题不是一条 SQL 能解决的,需要先探查 schema、再生成候选、再根据报错或结果改写,是一个循环,而不是一次生成。

## 生产架构在往哪个方向走

针对上面这些难点,当前生产实践大致收敛到几个方向,彼此往往叠加使用,而不是互斥选型:

1. **Schema 链接(Schema Linking)**:生成 SQL 之前先用检索方式从千级列的全量 schema 中筛出相关表和字段,把"选表选列"当成独立子任务,而不是指望模型直接记住整个数据仓库结构。
2. **语义层(Semantic Layer)**:把"复购率怎么算""活跃用户怎么定义"这类口径提前沉淀成受管控的定义,模型生成查询时优先命中既定指标,而不是每次重新"猜"业务逻辑——本质是把"谁定义指标"挪到了模型开口之前。
3. **Multi-Agent 工作流**:把单次生成拆成"探查 schema → 生成候选 SQL → 执行校验 → 依据报错或异常结果改写"的循环,Spider 2.0 排行榜前列方案大多是这种多代理架构,而非一次调用直出答案。
4. **执行反馈闭环**:生成的 SQL 先在受限环境里试跑,把语法错误、空结果、执行超时等信号喂回模型让它自我修正,而不是把第一次生成结果直接返回给用户。

## 评测:别只盯 Execution Accuracy

即便迁移到了更贴近生产的评测集,Execution Accuracy(执行结果是否和标准答案一致)本身也存在方法论缺陷:它对 SQL 的句法变体很敏感、忽略了同一个问题可能有多种合理写法、还容易被标注错误的标准答案误导——一条"合理但写法不同"的 SQL,可能被判定为错误。

2026 年的 ACL 论文提出的 **ROSE(ReasOning ScorE)** 换了一个视角:不再执着于"是否和标准 SQL 一致",而是用 Prover-Refuter 两阶段机制判断"生成的 SQL 是否真的回答了用户的意图",顺带还能标记出哪些是模糊问题、哪些是标准答案本身就标错了。对 AI PM 而言,不需要复现这套机制,但要理解它指出的方向:**"执行结果对了"和"真的答对了用户想问的问题",不是同一件事**。

另一个值得借鉴的评测视角来自 **NL2SQLBench**,它把 NL2SQL 系统拆成三个可以分别打分的模块:**Schema Selection(选表选列)、Candidate Generation(生成候选 SQL)、Query Revision(执行后改写)**。这和评估 RAG 时"检索准不准、生成好不好"要分开看是同一个思路——见[《如何评估 RAG 知识库的准确率?》](../../04-interview/basics/rag-kb-accuracy-evaluation.md)。定位问题时,先分清是"选错了表"还是"表选对了但 SQL 写错了"还是"SQL 对了但没能从报错里学会改写",排查效率天差地别。

## 产品决策:这几件事必须由人来定

1. **谁定义指标口径**:语义层里的每一条指标定义,应该有明确的业务负责人和评审流程,不能让"模型第一次怎么写的"变成事实上的口径标准。
2. **默认只读,写权限单独审批**:绝大多数查数场景不需要模型拥有写权限;即便是数据修正类需求,也应该走生成 SQL 由人审核执行、而不是模型直连生产库写入的路径。
3. **失败时澄清追问,而不是硬答**:遇到指标歧义、字段缺失、权限不足等情况,产品该设计成"反问用户想问的是哪个口径",而不是让模型选一个猜测口径后自信输出——这是查数场景比文档问答更需要克制的地方,因为一个数字比一段文字更容易被直接当作事实使用。
4. **审计日志**:记录每次查询的自然语言输入、生成的 SQL、命中的 schema/语义层定义、执行结果和最终展示给用户的数值,这条链路是排查"这个数字哪来的"的唯一依据,设计思路可参考 [Agent 安全一文](../../02-pm-skills/ai-product-operations/guardrails-and-agent-security.md)里对审计和风险动作确认的处理方式。

## 排行榜怎么看:方向信号,不是"已解决"

Spider 2.0 排行榜目前排名靠前的方案,大多是前面提到的 Multi-Agent + Schema 链接 + 执行反馈组合,这说明"结构化 + 多代理协作"确实是当前最有效的路线——但把这类头部分数直接当成"NL2SQL 已经解决"是危险的:公开排行榜上的设置、prompt 工程投入和是否使用了额外的元数据/oracle 信息并不完全透明,厂商自报的准确率区间更适合当作"量级印象",而不是可以直接套用到自己业务数据上的承诺指标。判断一个 NL2SQL 方案能不能上线,最终还是要看它在**你自己的 schema、你自己的指标口径、你自己的权限模型**下跑出来的评测结果。

## 给 AI PM 的判断框架

1. **先问"证据在表格里还是文档里"**:如果答案本质是一个数字或一行记录,该走 NL2SQL/结构化检索,而不是把表格数据切成文本块塞进向量库。
2. **把"选表选列""生成 SQL""执行校验"当成三个可以分别验收的环节**,而不是一个黑盒功能,出问题时才能快速定位到底是哪一步。
3. **语义层建设的优先级往往高于"换一个更强的模型"**:指标口径不统一时,再强的模型也只是更自信地给出错误答案。
4. **权限和审计不是模型能力问题,是产品必须兜底的部分**:不要指望靠 Prompt 让模型"自觉"遵守权限边界。
5. **看厂商或榜单数字时,先问"用的是不是我的数据分布"**——学术榜单的分数曲线和你业务数据库上的实测结果,大概率不是一条线。
