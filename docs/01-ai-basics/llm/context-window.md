# 上下文窗口:限制、成本与产品设计影响

## 一句话说清

上下文窗口(Context Window)是大模型单次对话"能看到"的最大文字量,单位是 token。系统提示词、用户输入、检索到的资料、对话历史、模型的输出——所有这些加起来,都要塞进这一个窗口里。超出窗口的部分,模型根本"看不见",不是"记不清",是物理上不存在于它的输入里。

理解上下文窗口,是理解大模型产品能力边界和成本结构的基础一课。

## 上下文窗口到底装的是什么

很多人第一次接触这个概念,会以为"上下文窗口"就是"对话历史"。其实它是一个更大的容器,一次模型调用里所有进出的文字都要占用它的额度:

```
[系统提示词 System Prompt]
+ [历史对话消息]
+ [本次用户输入]
+ [RAG 检索回来的文档片段]
+ [工具调用的返回结果]
+ [模型即将生成的输出]
──────────────────────────
= 全部必须 ≤ 上下文窗口大小
```

也就是说,窗口不是只留给"你说的话",而是要被系统提示词、历史消息、检索资料、工具结果反复分薄。一个挂了很长系统提示词、又接了 RAG 的产品,留给"真正对话"的额度可能比看起来的窗口数字小得多。

## 2026 年 7 月主流模型上下文窗口对比

以下数据均通过官方文档核实,访问日期 2026-07:

| 模型 | 上下文窗口 | 最大输出 | 备注 |
|------|-----------|----------|------|
| Claude Fable 5 / Opus 4.8 / Sonnet 5 | 1M tokens | 128K tokens | Anthropic 已于 2026 年 3 月取消长上下文附加费,超长输入不再额外加价 |
| Claude Haiku 4.5 | 200K tokens | 64K tokens | 面向低延迟场景的轻量模型,窗口显著小于同代旗舰模型 |
| GPT-5.5 | 1.05M tokens | 128K tokens | 单次请求超过 27.2 万输入 token 后,超出部分按 2 倍输入价 / 1.5 倍输出价计费 |
| Gemini 3.1 Pro | 最高 1M tokens | 64K tokens | 官方模型卡标注为生产可用(GA)版本 |
| Gemini 3.5 Pro | 官方宣称 2M tokens | 暂未公布 | 2026 年 5 月发布预告,截至 2026-07 仍处预览阶段,尚未全面开放、定价未公布 |

**几个值得注意的细节**:

1. **"1M tokens" 不是一个固定的字数换算**:以 Claude Fable 5 为例,官方说明约等于 55.5 万英文单词、250 万 Unicode 字符;而且不同模型换代后使用了新的分词器(tokenizer),同样的文本切出来的 token 数量可能相差 30% 左右。中文场景下的实际可用字数,通常要以实测为准,不能直接套用英文估算。
2. **窗口大小与"生产可用"是两回事**:Gemini 3.5 Pro 官方宣传的 2M 窗口截至 2026-07 仍是预览特性,benchmark 和定价都未正式公布,选型时不能当作已交付能力对待。
3. **长上下文计费策略并不统一**:Anthropic 已对长上下文一视同仁计费,OpenAI 的 GPT-5.5 则对超过 27.2 万 token 的请求按更高单价计费——这类"超阈值加价"规则,是做成本测算时容易被忽略的细节。

> 以上数值随模型迭代变化很快,建议查阅时以 [Claude 模型总览](https://platform.claude.com/docs/en/about-claude/models/overview)、[OpenAI 模型文档](https://developers.openai.com/api/docs/models)、[Gemini API 模型页](https://ai.google.dev/gemini-api/docs/models) 的最新数据为准。

## "中间遗忘"问题:窗口大 ≠ 全都记得住

一个常见的误解是:窗口越大,模型对窗口里所有内容的"重视程度"就越均匀。实际情况并非如此。

学术界和工程实践中都观察到一种现象,俗称 **"Lost in the Middle"(中间遗忘)**:当把关键信息放在一段很长上下文的**开头或结尾**时,模型的检索/引用准确率明显更高;而放在**中间位置**时,准确率会下降。这类似于人在读一篇很长的文档时,往往对开头的引言和结尾的总结印象最深,中间大段细节反而容易读了后忘。

这对产品设计的直接影响是:

- 不能假设"塞进窗口 = 模型一定会用好这段信息",尤其是长文档问答、超长对话场景
- 关键指令(如安全规则、格式要求)放在系统提示词的开头或紧邻用户问题的位置,通常比堆在长文档中间更可靠
- 这也是 RAG(检索增强生成)存在的价值之一:与其把整本文档塞进窗口指望模型"自己找",不如提前把最相关的几段检索出来,精简、靠前地喂给模型(参考[《什么是 RAG》](what-is-rag.md))

## 窗口越大越好吗?——不一定,要算三笔账

窗口只是能力上限,不是免费的午餐。产品决策时至少要考虑三个维度:

| 维度 | 说明 |
|------|------|
| **成本** | 按 token 计费,窗口用得越满,单次调用成本越高;有些模型对超长输入还有阶梯加价 |
| **延迟** | 输入越长,模型处理(尤其是首 token 出现前的等待)通常越慢,影响对话类产品的实时体验 |
| **效果** | 如上文所述,塞得多不代表用得好,无关信息过多反而可能稀释模型对关键内容的关注度,甚至引入噪音干扰答案质量 |

**经验法则**:够用比越大越好更重要。与其无脑追求"上下文窗口最大的模型",不如先想清楚业务场景真实需要多长的上下文,再倒推选型和架构(全量塞入 vs. 摘要压缩 vs. RAG 按需检索)。

## 对产品设计的影响

### 1. 长文档处理

法律合同审查、财报解读这类场景,单个文档可能就有几十万字。产品设计上通常有两种路线:

- **全量塞入窗口**:依赖大窗口模型,优点是模型能看到全文语境,缺点是成本高、有"中间遗忘"风险
- **切片 + 检索(RAG)**:把文档切块建索引,按问题检索最相关片段再回答,优点是成本可控、精度可能更高,缺点是需要额外的检索基础设施,且切片策略本身是个技术活

### 2. 多轮对话与"记忆"

上下文窗口 ≠ 记忆。模型不会"记住"上一次会话内容,每次调用都是独立的——所谓"记忆",全部要靠工程手段模拟。常见的三种做法(详见面试题[《大模型的上下文窗口和记忆机制是什么?》](../../04-interview/basics/context-window-and-memory.md)):

- 直接把历史消息原样拼进窗口(简单,但对话越长越贵、越容易触顶)
- 定期把历史对话压缩成摘要,只保留摘要 + 最近几轮原文
- 把关键信息(用户偏好、过往承诺)抽取存入外部数据库,需要时再检索注入——这是目前"跨会话记忆"功能(如 ChatGPT 的记忆、Claude 的项目知识)的主流实现思路

### 3. 记忆功能的产品设计要点

- **窗口临界点的体验**:接近上限时,是粗暴截断最早的消息,还是主动触发摘要?前者可能丢失重要承诺,后者需要额外的模型调用成本
- **用户预期管理**:清楚地告诉用户"我能记住什么、记不住什么",避免用户误以为产品有真正的长期记忆而做出错误假设
- **成本与体验的平衡**:全量保留历史最"聪明"也最贵,合理的摘要 + 检索策略往往是生产环境的现实选择

## 给 AI PM 的启示

- 选型时不要只看"窗口越大越好",先问清楚业务场景真实需要多长的有效上下文
- 长文档、长对话场景要主动设计"中间遗忘"的应对方案,而不是假设模型会一视同仁地处理全部输入
- 上下文窗口和 RAG 不是二选一,而是互补关系:窗口决定"能塞多少",RAG 决定"该塞什么"
- 做成本测算时,注意不同厂商对超长输入的计费规则可能不同,不能简单按"每 token 单价 × token 数"线性估算
