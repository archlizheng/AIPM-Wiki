# 豆包案例拆解：免费入口与付费额度如何共存

**分类**：对话助手

**资料核验**：2026-09-14；本轮为公开资料分析，未验证登录后购买和全部客户端功能。

## 一、产品背景

豆包面向日常问答、学习和创作。讨论它的商业化，应该从可观察的免费与付费边界出发，而不是把 App 活跃用户乘一个假设转化率，写成公司的收入或利润。

旧版引用过不同月份的规模、匿名转化率和增长动机。本次不再用这些材料判断当前市场排名、专业版经营效果或内部战略。用户规模、模型开放平台调用量与豆包 App 收入是三种不同对象。

## 二、核心功能拆解

[中国区 App Store 的开发者介绍](https://apps.apple.com/cn/app/id6459478672)展示日常助手的功能定位，条目列有免费与 App 内购买。它是开发者对产品的说明，并非独立质量测试；评论区体验不作为产品功能的官方证据。

当前开发者介绍明确列出“工作任务模式”，包括内置 Office 与专业技能、理解需求后执行及定时任务。公开材料支持“进入工作任务→描述报告/资料整理需求→处理文档、表格或PPT”的产品链路；它没有证明每次产物的可编辑性、引用质量或后台任务成功率，这些正是后续测试要检查的部分。

可以设计一个“阅读材料—形成草稿—反复修改”的任务，比较免费入口和付费权益的作用。下表是作者建议的测评，不是豆包实测结果：

| 环节 | 用户问题 | 要记录的证据 |
|---|---|---|
| 开始任务 | 当前账号能处理哪些材料 | 客户端、套餐、入口、文件限制 |
| 理解材料 | 结论有没有原文支持 | 对应页码、段落、缺失信息 |
| 形成产物 | 可以直接编辑还是只有预览 | 下载格式、文字和表格可编辑性 |
| 触及额度 | 本次还能否继续 | 剩余额度、恢复时间、任务状态 |
| 修改或失败 | 是否再次扣费 | 消耗记录、重试说明、申诉入口 |

付费墙的关键不是一句“更多能力”，而是用户能否预测自己的任务会消耗多少、失败时怎样处理。若前台显示“可做若干次”，后台却按不同任务的 token 消耗折算，应解释估算口径，不能让用户把参考次数当保证交付次数。

## 三、技术方案推测

多模态理解、资料处理和创作通常需要多个能力协作，但 App 的界面表现不足以确认固定模型路由、内部 RAG 架构或单次成本。火山引擎对外模型价格也不能当作豆包内部推理成本。

若设计同类产品，建议把“材料处理成功”“生成完成”“用户认可产物”分开埋点，并将重试关联原始任务。文档校验方法见 [文档智能产品](../../02-pm-skills/prd-and-design/document-intelligence-design.md)。

## 四、商业模式

[豆包付费服务协议](https://www.doubao.com/legal/ey01)的**更新日为 2026-08-15、生效日为 2026-08-22**。协议区分标准、加强、高级会员，以及创作额度包和云存储扩容；买一种不自动获得另一种。费用以购买页为准，功能消耗可按 token 折算为次数或时长。

因此，当前能确认的是会员与附加资源的收费结构。本轮进一步核到中国区 App Store 开发者订阅说明：标准、加强及500元档连续包月为68/200/500元，连续包年688/2048/5088元，仅作为该渠道公开快照。条目把500元档称“专业版”，协议称“高级套餐”，命名存在差异，购买时应核对实际权益，不能自行认定所有渠道相同。学生价与付费转化仍未核实，因此不保留。App 下载免费也不等于所有 AI 功能永久无限免费。

可复用的订阅评审表：

| 项目 | 应填写的内容 |
|---|---|
| 权益对象 | 模型访问、使用额度、云存储分别列项 |
| 消耗单位 | 次数、时长或 token 折算规则 |
| 有效期 | 订阅到期、赠送额度、加购包分别说明 |
| 异常 | 中断、重试、退款按实际条款与账单验证 |
| 收入判断 | 用真实付费人数、实付金额和退款额，不用下载量推算 |

## 五、PM 视角的启示

1. 免费入口服务日常需求，付费权益要解释可预期的增量价值；具体分层是否有效需用户研究验证。
2. 模型、创作和存储可能形成多套额度，购买页必须解释能否共享与何时到期。
3. 订阅、广告或交易可以组合，但现有公开动作不足以证明某一条已经成为主收入来源。
